### \(b) 机械判据：建立一张 R1 + R6 统一总账

建议不要再维护独立的“十四步完成比例”和“契约债统计”作为两个权威来源。

建立统一 obligation registry：

`machine/fusion-obligations.yaml`

对应审计器：

`runners/audit-fusion-obligations.mjs`

输出：

`runtime/fusion-audit.json`

以及人类阅读投影：

`generated/human/fusion-audit.md`

#### 每条 obligation 的最低字段

```yaml
schema_version: 1

obligations:
  - id: R1-S09
    origin: R1
    title: Experience to Contract Proposal
    lifecycle: active

    depends_on:
      - R1-S08
      - R6-Q3-OWNERSHIP

    required_artifacts:
      - path: runners/propose-contract-from-experience.mjs
        role: producer
      - path: generated/learning/contract-proposals/
        role: output_directory

    required_consumers:
      - consumer_id: contract-proposal-review
        entrypoint: runners/propose-contract-from-experience.mjs

    required_negative_tests:
      - id: contract-proposal-cannot-self-activate
        suite: tests/fusion/contract-proposal.test.mjs

    required_runtime_proofs:
      - kind: real_input_lineage
      - kind: reviewed_disposition
      - kind: artifact_commit

    superseded_by: null
    defer:
      authorized: false
      until: null
      approval_ref: null
```

以上路径和测试名是建议新增的规范，不是声称文件已经存在。

每条还应在验收收据中绑定：

`source_commit`、`artifact_sha256`、`consumer_sha256`、`test_run_id`、`test_result_sha256`、`proof_ref`、`verified_at`。

路径匹配应以控制平面真实工作树为根。`meta-intelligence-facts` 的掩码投影不应被当作第二个权威仓库；它可以提供可审查的投影证据，但不能独立决定完成状态。

#### 状态应分为两个正交维度

不要用一个 PASS 混合“已经做了”和“通过验收”。

| 维度 | 状态 |
|--------|--------|
| 实施生命周期 | `NOT_STARTED` / `IMPLEMENTING` / `IMPLEMENTED` / `DEFERRED_AUTHORIZED` / `SUPERSEDED_VERIFIED` |
| 验证结果 | `GREEN` / `RED` / `UNKNOWN` / `NOT_APPLICABLE` |

例如：

```json
{
  "obligation_id": "R1-S05",
  "implementation": "IMPLEMENTING",
  "verification": "RED",
  "reason_codes": [
    "UNMIGRATED_CROSS_TREE_REFERENCE"
  ]
}
```

而步骤 14 可以是：

```json
{
  "obligation_id": "R1-S14",
  "implementation": "DEFERRED_AUTHORIZED",
  "verification": "NOT_APPLICABLE",
  "reason_codes": [
    "WAITING_FOR_CT07_CUTOVER"
  ]
}
```

这里 `NOT_APPLICABLE` 仅适用于有明确批准且尚未到期的延期，不表示功能已经完成。

同时，**延期项仍留在总账分母里**。延期可合法，但不能从原方案中消失。

#### 单脚本的最小执行逻辑

```text
读取 fusion-obligations.yaml
    ↓
验证 obligation ID 唯一、依赖无环
    ↓
扫描真源文件及内容摘要
    ↓
验证消费者引用与实际执行路径
    ↓
读取对应测试的当前版本验收收据
    ↓
核对测试是否覆盖规定负例
    ↓
验证实际运行 witness / 产物因果链
    ↓
核对延期、替代映射和依赖项
    ↓
逐条计算 implementation + verification
    ↓
生成唯一 JSON 对账结果
    ↓
由 JSON 投影人类阅读表
```

建议最终使用一条命令：

```powershell
node runners/audit-fusion-obligations.mjs --strict
```

该脚本必须检查并输出所有 obligation，而不是运行到首个失败就中止并遗漏剩余欠账。`--strict` 决定退出码：

- 全部当前必需项 GREEN，且延期合法：`exit 0`。
- 任一硬依赖 RED、未经授权延期或应有证据缺失：`exit 1`。
- 台账自身无法解析、证据格式异常、校验器故障：`exit 2`。

UNKNOWN 不得自动变成 GREEN；若 UNKNOWN 所在 obligation 阻塞某个待执行动作，`--strict` 也必须拒绝该动作。

审计脚本本身的存在不构成验收证据。它应有独立测试，测试收据必须绑定测试运行时的代码和配置版本，不能拿历史测试结果验收当前文件。

#### 完成度不要再报一个无解释的百分比

建议每轮同时输出：

```json
{
  "r1": {
    "total": 14,
    "carrier_present": 11,
    "verified": null,
    "partial": null,
    "blocked": null,
    "authorized_deferred": 1
  },
  "cross_cutting": {
    "ownership_contract": "RED",
    "skill_effective": "UNKNOWN",
    "trigger_authority": "UNKNOWN",
    "ct05": "NOT_VERIFIED",
    "ct07": "NOT_STARTED"
  },
  "fusion_total": "RED"
}
```

`verified` 和 `partial` 的空值表示尚未运行完整审计，不代表零。

本轮依据盘点可以确定 **11/14 有载体**，但不能推算出“验收通过率 78.6%”。那会继续混淆文件覆盖率与能力完成度。

### \(c) 明确延期项

- **S04**：原生消费者迁移期间允许保留兼容文件，但不允许无限期维持多重可写权威；终态应立即定案。

- **多仓权威统一**：掩码投影仓继续保持投影角色，不因总账合并就扩大其写权限。

## Q2｜学习闭环：怎样证明真的跑过一次，而不是只证明 runner 能跑？

### \(a) 裁定

**当前学习闭环状态 = UNKNOWN / NO\_QUALIFIED\_END\_TO\_END\_PROOF。**

不是 FAIL，也不是 GREEN。

根据你的盘点，已知有：

- Evidence Index 与 learning candidate 相关 runner；
- `generated/learning/l1-triage.json`；
- `generated/learning/skill-proposals.json`。

但没有已知的、能够把同一个真实来源沿着 Evidence → Candidate → 人审 disposition → 实际文件写入连接起来的完整证据包。

这些文件只能证明部分阶段已有产物，不能证明一条特定候选经历了完整且合规的生命周期。

尤其需要纠正一个等式：

```text
l1-triage.json exists
AND skill-proposals.json exists
⇒ learning_loop_verified
```

**这个推导不成立。**

两份产物可能属于不同运行、不同输入修订，甚至使用了不同的批准依据。

### 第一例应该使用哪个真实 Demand？

我的首选是：

**已有 `machine/TASKS.yaml` 中的 CT-05：普通 Task/Decision 事件覆盖与 State→首页新鲜度保障。**

理由有三个：

1. 它已经是正式 Task，不需要新造一个实验或虚构历史需求。
2. 它当前确有可观察的契约缺口：已列为切换前置条件，但缺少完整验收判据。
3. 它天然可以产生一份真实的契约改进提案，并同时检验 R1 步骤 9。

建议首次候选主题：

`CT-05: State-to-Home Freshness Contract`

但必须严格限制证据语义：

**“CT-05 缺验收判据”是已观察到的治理缺口；“首页曾经因某次 Task 更新而静默过期”目前不是已经证明的生产事故。**

不得把后者伪造成 Experience。

可采用以下真实输入：

| 层次 | 输入 | 可以证明什么 |
|--------|--------|--------|
| Demand | `machine/TASKS.yaml` 的 CT-05 任务记录 | 真实存在的待解决需求 |
| 约束 | DEC-22 的四项切换前置及回滚规则 | 为什么需要可验证的新鲜度契约 |
| 现状 Evidence | CT-05 尚无完整验收判据的原始台账快照 | 真实的验收覆盖缺口 |
| 行为 Evidence | 后续真实 CT-05 测试或合法 Task/Decision 变更的执行结果 | State→首页链路实际表现 |
| Experience Candidate | 基于上述有来源证据得出的可复用经验 | 可提出哪些契约化约束 |

其中，行为 Evidence 尚未出现时，只能形成 `coverage_gap` 类型的候选，不能伪装成已验证的运行成功/失败经验。

如果学习系统的既有 Experience schema 不接受这种覆盖缺口类经验，就先完成一次真实 CT-05 测试取得行为证据，再进入候选生成；不能为了演示全链路强行放宽旧 schema。

这条路比构造一条假的 Evidence 更慢一些，但得到的第一份闭环记录才值得保留。

#### 这次应该生成什么产物？

建议产出一份非权威的契约提案：

`generated/learning/contract-proposals/CT-05-home-freshness.yaml`

提案内容包括事件类别、状态/首页更新关系、receipt hash 链与负例测试要求。

注意：

- 写入 `generated/learning/contract-proposals/`，只代表生成了一个提案。
- 写入 `machine/contracts/`，则代表权威契约变更，需要额外治理审批。
- 不允许通过首次学习闭环把这两步合并。

这样既能证明“学习真正形成了一份产物”，又不会让执行 Agent 借学习闭环取得自行立法的权力。

### \(b) 机械判据：一次合格学习闭环的最小证据包

建议以一个 `run_id` 建立：

`runtime/learning-runs/<run_id>/`

单次学习闭环证据结构

**`runtime/learning-runs/<run_id>/`**

`input-manifest.json`

真实 Demand、Evidence、源版本与 hash

`candidate.json`

候选 ID、类型、来源和内容摘要

`disposition.json`

人审决定、签署人、授权范围

`artifact-receipt.json`

实际产物路径、内容摘要、写入结果

`events.jsonl`

各阶段事件与调用关联

`verdict.json`

独立校验结果和失败原因

这里使用 `runtime/` 是为了存放运行证据，而不是让 runtime 目录成为学习内容来源。真实的 Demand、Evidence 仍必须指向获授权的上游真源。

#### 必需的因果链字段

| 环节 | 必须具备的字段或关系 |
|--------|--------|
| 输入 | `demand_ref`、`demand_sha256`、`evidence_refs[]`、各来源 sha256、`source_snapshot_sha256` |
| Candidate | `candidate_id`、`candidate_kind`、`candidate_sha256`、`input_manifest_sha256`、`generator_sha256` |
| 人审 | `candidate_id`、`candidate_sha256`、`decision`、`reviewer_id`、`approval_ref`、`signature`、授权的产物类型和路径 |
| 写盘 | `run_id`、`invocation_id`、`artifact_path`、`artifact_sha256`、`writer_build_sha256`、`committed_at` |
| Witness | `event_id`、`event_type`、`emitter`、`request`、`attestation`、对应 run/invocation ID |
| 终验 | `verdict`、`verified_input_sha256`、`verified_artifact_sha256`、`verifier_build_sha256`、失败原因 |

建议新建 `learning.artifact_committed` 事件类型。

它与 R6 的 `skill.handler_entered` 共享事件身份、输入来源、版本绑定、签名及重放校验原则，但**不是同一种事件**。

这是必须守住的边界：

- `skill.handler_entered` 证明某个已安装 skill 被真实采用。
- `learning.artifact_committed` 证明一次学习运行确实向规定路径写入了产物。
- 即使后者 GREEN，也不能推导任一 skill 的 effective 为 GREEN。

对于没有经过 skill dispatcher 的学习 runner，不应为了复用 R6 字段而伪造 `skill.install_id` 或 dispatcher 路由决策。

```json
{

  "event_type": "learning.artifact_committed",
  "event_id": "<unique-id>",
  "occurred_at": "<UTC-time>",
  "run_id": "<run-id>",
  "invocation_id": "<invocation-id>",
  "emitter": "learning-writer-hook",
  "request": {
    "ref": "task://CT-05",
    "origin": "workflow",
    "sha256": "<64-hex>"
  },
  "candidate": {
    "id": "<candidate-id>",
    "sha256": "<64-hex>"
  },
  "disposition": {
    "approval_ref": "<approval-id>",
    "approved_candidate_sha256": "<64-hex>"
  },
  "artifact": {
    "path": "<output-path>",
    "sha256": "<64-hex>",
    "kind": "contract_proposal"
  },
  "producer": {
    "build_sha256": "<64-hex>"
  },
  "attestation": {
    "signer_id": "<trusted-writer-id>",

  }

```

其中 `request.sha256` 必须有统一定义，例如取 CT-05 Task 记录经版本化规范化算法得到的摘要。`input-manifest.json` 还需要分别记录整个 `TASKS.yaml` 的文件摘要和被选中 Task 记录的摘要，避免对象级与文件级 hash 混用。

这个 witness 应在文件真正写入并重新读取校验后生成，不允许在生成候选时就提前写“已提交”。

签名也必须覆盖事件实际内容，使用确定的规范化编码；只检查 `signature` 字段非空不合格。

#### 独立人审的最低限制

`disposition.json` 不能只是：

```json
{
  "decision": "approved"
}
```

至少要验证：

```text
reviewer_id 属于授权清单
AND 审批记录签名有效
AND 审批对象 hash = 当前 candidate hash
AND 审批范围覆盖该 artifact kind/path
AND 审批未被撤销或过期
AND 评审者与生产者不存在被禁止的自批关系
```

有一条非显然但很重要的负例：

**先审批 Candidate A，随后修改候选正文变成 Candidate B，仍然复用审批号，应当直接 RED。**

同理，先审批 contract proposal，却写成已激活的 skill，也必须 RED。

#### 学习闭环的绿色逻辑

```js
const eligible =
  validRealDemand &&
  validSourceEvidence &&
  sourceHashMatches &&
  validCandidate &&
  candidateInputMatches &&
  validIndependentDisposition &&
  approvedCandidateHashMatches &&
  actualArtifactExists &&
  artifactHashMatches &&
  validCommitWitness &&
  trustedAttestation &&
  !replayedEvent &&
  !unauthorizedSideEffect;

if (!eligible) {
  return "NOT_VERIFIED";
}

return "GREEN";
```

实际 runner 应区分 `RED` 和 `UNKNOWN`：

- **UNKNOWN**：根本没有合格完整证据，或者关键观测机制尚未建立。
- **RED**：已发现伪造、错配、未授权写入、错误生效等硬违反。
- **GREEN**：全部证据在声明的信任边界内可机械复验。

因此首次闭环的 `verdict.json` 可以是：

```json
{
  "workflow": "evidence-to-contract-proposal",
  "status": "GREEN",
  "scope": "ONE_REAL_DEMAND_ONE_APPROVED_ARTIFACT",
  "run_id": "<run-id>",
  "input_ref": "task://CT-05",
  "candidate_id": "<candidate-id>",
  "approval_ref": "<approval-id>",
  "artifact_ref": "<artifact-path>",
  "valid_commit_witness_count": 1,
  "claims_not_proven": [
    "production_contract_activated",
    "skill_effective",
    "learning_quality_improved"
  ]
}
```

这只是未来可接受的收据格式；当前没有足够依据填写真实 `status=GREEN`。

首次成功应标记为 **ONE\_CASE\_VERIFIED**，不要直接升级为“整个学习系统已经闭环”。

#### 必须补的负向用例

至少覆盖：无 Demand、虚构 Evidence、fixture 被冒充真实输入、输入 hash 漂移、未生成 Candidate、无审批、审批人与生产者相同且不具备独立权限、审批绑定旧 hash、产物不存在、写盘后被修改、重复 witness、事件来源不可验证、runtime 诊断文件被当作原始学习材料。

验证时要特别区分：

- **测试 fixture**：可以使用合成数据来测试防错规则。
- **真实 Experience**：只能来自真实的来源记录和真实的运行或观察事实。

R1 所禁止的不是写负向测试，而是**把为了测试而制造的事件当作系统真的积累了经验**。

### \(c) 明确延期项

本轮不要求：

- 自动把 Contract Proposal 合并为权威契约；
- 自动从一次 Experience 生成有效 skill；
- 为了学习闭环登记一个不存在的 Experiment；
- 把一次候选成功解释成长期收益；
- 做因果归因、收益评分或跨项目智能优化；
- 证明不存在所有可能绕过路径。

还要再次明确 R6 的信任限制：如果执行 Agent 拥有同时改写运行日志、批准记录、信任公钥和校验程序的全部权限，仅靠这些文件内容无法取得独立可信的 GREEN。

盘上机械验收可以做到**证据结构完整且彼此一致**；要做到**不可自证**，还需要受保护的审批权、写入边界或独立审计者。

这一限制不能靠多加几个 SHA-256 字段解决。

## Q3｜CT-05：怎样证明 State→首页不会静默过期？

### \(a) 裁定：CT-05 不能只测试“首页确实变了一次”

**CT-05 的验收对象应该是事件覆盖与投影新鲜度不变量，而不是一次页面更新的成功截图。**

它至少需要证明两件事：

1. 普通 Task/Decision 以及实验、组件健康变化会被正确识别，并按约定影响 State 和首页。
2. 当来源、State 和首页处于不同修订时，系统能够识别不一致，并禁止把过期首页当作当前有效投影。

建议新增的权威验收契约：

`machine/contracts/ct05-event-freshness.yaml`

但由于当前整个 `machine/contracts/` 缺失，必须先解决 R6 的契约加载与强制消费问题，避免再出现“CT-05 YAML 已有，实际 cutover 不读取”的假落实。

### CT-05 应覆盖的四类变化

| 事件类别 | 正例：应发生什么 | 负例：必须拦住什么 |
|--------|--------|--------|
| Task | 合法任务状态、负责人或适用字段变化，被 Task Index 和 State 捕获，再影响首页约定展示 | Task 已变，但 State 或首页仍沿用旧摘要 |
| Decision | 新 Decision 或合法修订被归因并反映到相应 State 与首页摘要 | Decision 修订未被归因、只在 docs 存在，首页仍显示旧决策信息 |
| Experiment | 合法实验输入变化被识别，State 保持 DEC-26 的 `[]`/`null` 语义，首页正确投影 | 无实验和未知实验状态混淆，或 fixture 被当成正式 Experiment |
| Component health | 实际健康检查结果由正常变异常或恢复后，State 与首页健康标记跟随变化 | 健康已异常但旧首页仍显示正常，或者健康输入过期被当成健康 |

这里必须把首页的*可观察行为*纳入契约。

如果 Decision 改了，而首页只更新一个隐藏 hash，用户仍然看不到任何有意义的变化，不能称为 Decision→首页覆盖成功。

可以不展示整个 Decision 正文，但至少应有适当的可见摘要、最近决策状态或与之相关的健康/待办信息。

同样，不要求每个 Task 字段变化都改变首页的可见文本；要先在契约里定义哪些字段属于首页投影范围。否则测试会退化为“改任意文件，强迫首页重建”。

### 正例与负例如何设计

建议分两层：

**第一层：隔离环境中的覆盖测试。**

用 fixture 构造四类合法事件及其无效变体，验证真实的 `build_task_index`、`build_state`、`build_home_projection` 与切换前闸门，不能只测试孤立的字符串处理函数。

这些 fixture 必须标为测试输入，且不得流入正式 Evidence/Experience 台账。

**第二层：真实来源的端到端验收。**

至少取得一条真实普通 Task 变化、一条经过正常授权的 Decision 变化的前后快照和运行收据。

最自然的现成机会：

- CT-05 任务从“只有标题”补齐正式验收条件，是一项有真实目的的 Task 变更。
- DEC-22/DEC-29 若需要补充本轮裁定的执行验收条款，可以走正常 Decision 修订流程。

不能为了测试而伪造一条新的治理决定；只有确实经过授权、且内容有实际用途的修订，才能计入真实验收。

Experiment 和组件健康可先由隔离 fixture 覆盖。没有自然发生的实验变化，不是制造一份假实验的理由。

### 最关键的新鲜度不变量

建议把 State 和首页的每次构建绑定到同一个有标识的来源快照：

**真实来源快照**

Task / Decision / Experiment / Health 输入摘要

**State 构建收据**

source\_manifest\_sha256 + state\_manifest\_sha256

**Home 构建收据**

consumed\_state\_manifest\_sha256 + home\_sha256

**切换及实际读取验证**

active\_entry\_sha256 + current\_snapshot\_id

这里要检查的是当前真实文件，而不只是收据字段之间是否相等。

建议在 CT-05 中冻结以下机械不变量。

| 编号 | 不变量 | 机械失败条件 |
|--------|--------|--------|
| F1 | State 来源完整 | 当前来源摘要与 State 记录的来源快照不一致且没有合法更新处理状态 |
| F2 | State→Home 一致 | 首页消费的 State 摘要不等于对应有效 State 快照摘要 |
| F3 | Home 内容完整 | 实际首页字节摘要与有效构建收据不匹配 |
| F4 | 事件覆盖完整 | 契约规定应进入 State 的 Task/Decision 变化缺失归因记录 |
| F5 | 显示语义正确 | State 变更已进入约定的首页投影范围，但重新生成的首页缺少对应变化 |
| F6 | 切换不得绕过 | 任一硬 RED 存在，CT-07 仍然修改了真实入口 |
| F7 | 无效输入不制造历史 | 测试 fixture、无效事件或无意义变更进入正式事件/Experience 台账 |

特别注意 F1：来源可能在异步构建过程中变化，因此需要明确快照提交边界。如果没有原子发布或版本化快照机制，不能简单比较两个任意时刻的文件 hash，就宣称构建存在缺陷。

最稳妥的方式是将 State 与首页构建为同一发布快照，再原子切换其活动指针。

### \(b) 机械判据：CT-05 PASS 需要的盘上产物

建议建立：

`runtime/acceptance/CT-05/`

最低包括：

| 产物 | 内容 |
|--------|--------|
| `case-matrix.json` | 四类事件的正负例定义与实际结果 |
| `input-snapshots.json` | 每个案例的来源前后 hash |
| `state-receipts.json` | State 构建版本、输入摘要、change attribution |
| `home-receipts.json` | 首页构建版本、State 关联摘要、实际首页 hash |
| `negative-gate-results.json` | 故障注入后确实阻断发布或切换的记录 |
| `live-path-witness.json` | 真实 Task/Decision 变化经过生产路径的证据引用 |
| `verdict.json` | 最终机械裁定与受检代码版本 |

建议 `case-matrix.json` 至少包含 8 个核心案例，即四种类别各一个正例、一个负例。

此外必须单独有以下跨阶段负例：

- 来源已更新，但 State 尚未更新；
- State 已更新，但首页尚未更新；
- 首页内容被手动替换为旧版本；
- 收据存在，但实际文件摘要不匹配；
- 无效输入或纯无效语义变化被误判为真实更新。

因此不建议只把“八个案例成功”作为最终条件，还需要这些全局新鲜度测试。

#### 一个具体的过期首页负例

在隔离副本中执行：

```text
1. 生成 State_A 和 Home_A，确认两者一致
2. 合法修改一个 Task，形成 Source_B
3. 运行 State 构建，得到 State_B
4. 故意保留旧 Home_A，不运行首页构建
5. 调用与 CT-07 相同的入口发布前校验路径
```

预期结果：

```json
{
  "case_id": "CT05-STALE-HOME",
  "state_version": "B",
  "home_consumed_state_version": "A",
  "expected": "BLOCK",
  "observed": "BLOCK",
  "entry_modified": false
}
```

必须同时检查入口指针或目标文件在失败前后的 hash 相同，证明没有发生被禁止的切换副作用。

再做一个相反方向的负例：来源已经变为 B，但 State/Home 都保持 A。只检查 State 与 Home 相等会错误放行这个案例。

**这是 CT-05 最容易漏掉的静默过期：State 和首页互相一致，但两者共同落后于真实来源。**

要抓住它，必须从真实来源清单开始验证，而不能只验证两个生成文件。

#### CT-05 最低 PASS 公式

```text
schema_valid
AND all_required_cases_present
AND all_positive_cases_pass
AND all_negative_cases_block
AND live_task_path_verified
AND live_decision_path_verified
AND source_to_state_lineage_valid
AND state_to_home_lineage_valid
AND active_projection_content_verified
AND no_unapproved_source_mutation
AND acceptance_receipts_match_current_build
⇒ CT05 = PASS
```

其中 `live_task_path_verified` 与 `live_decision_path_verified` 要绑定真实来源的前后版本，不能由测试 fixture 代替。

如果只是所有 fixture 通过，而没有真实生产路径的验收，建议输出：

`CT05 = TESTED_NOT_LIVE_VERIFIED`

这是测试成功，不是完整验收成功。

建议终验格式：

```json
{
  "acceptance_id": "CT-05",
  "status": "PASS",
  "positive_case_count": 4,
  "negative_case_count": 4,
  "staleness_guards_verified": true,
  "live_task_path_verified": true,
  "live_decision_path_verified": true,
  "source_state_freshness": "PASS",
  "state_home_freshness": "PASS",
  "publish_gate_fail_closed": true,
  "artifact_manifest_sha256": "<64-hex>",
  "verifier_build_sha256": "<64-hex>"
}
```

实际 `negative_case_count` 可以高于 4；不可用四个普通负例替代额外要求的过期保护测试。

再次强调，`status` 必须由验收 runner 计算，而不是提前写入文件的期望值。

### CT-07 真实切换：执行顺序与回滚判据

#### 是否需要增补 DEC-22/DEC-29？

**需要增补执行层验收条款，不需要推翻原有裁定。**

DEC-22 现有四项前置仍然有效。R7 应新增对应的机器验收引用，至少包括：

- CT-05 收据结构和有效性；
- 来源→State→首页的版本绑定；
- 切换前强制新鲜度检查；
- 切换后实际活动入口校验；
- stale-home 自动阻断或回滚；
- CT-13 验证结果与当前部署版本的绑定。

可以在 DEC-22/DEC-29 中增加经正常批准的补充条款，也可以采用新的执行契约文件引用既有决定。

不建议执行 Agent 单方面重写原 Decision 正文，再声称这是机器契约的当然延伸。

## 最后推动：把三种容易自欺的记账方式彻底拆开

### 第一处：runner 存在，不等于 R1 方案落实

你这次的盘点比 R6 更准确，因为已经记录了消费者、receipt 和缺口。

但完成度统计仍然存在同一类风险。

建议以后每轮不再使用单独的“✓”作为实施状态，而是至少区分：

`PRESENT`、`CONSUMED`、`NEGATIVE_TESTED`、`LIVE_VERIFIED`。

这四个阶段只能在证据满足时逐级提高。

我会特别盯住三个地方：

- **S05**：四个 runner 已消费 resolver，不能掩盖 20\_ 契约未迁移。
- **S08**：L1 triage 存在，不等于有真实人工 disposition 的学习闭环。
- **S12**：Human View 文件存在、CT-13 演练成功，不等于实际入口切换并保持新鲜。

### 第二处：R1 与 R6 必须合并总账，但不能合并语义

我支持**一张权威义务总账、一个审计 runner、一份汇总报告**。

但不支持把不同证据混成一种进度积分。

总账应允许这样的结果同时成立：

```text
R1-S03 Task Index           GREEN
R1-S05 Logical URI          PARTIAL
R1-S09 Contract Proposal    RED / NOT_IMPLEMENTED
R1-S14 Legacy Retirement    DEFERRED
R6-Q1 Skill Effective       UNKNOWN
R6-Q2 Trigger Authority     UNKNOWN
R6-Q3 Ownership Contract    RED
CT-05 Event Coverage        NOT_VERIFIED
CT-07 Real Cutover          NOT_STARTED
```

特别是 `DEFERRED` 不应该成为可持续隐藏欠账的垃圾桶。

R1 步骤 14 目前顺序延期合理，但必须把延期理由和退出条件正式落盘，之后才能获得 `DEFERRED_AUTHORIZED`。R1 当初说“最后做”，不自动等于如今已经拥有机器可验证的延期授权收据。

总账还应该有一个字段：

`blocking_actions`

这样你就能区分：

- 阻塞真实入口切换；
- 阻塞技能激活；
- 阻塞新草稿写入；
- 阻塞宣称 R1 全面完成。

不同阻塞项不应不加区分地把所有工程工作都冻结。

### 第三处：问诊记录不应该“永远不能进入证据层”

这里需要纠正一个从 R6 可能被过度推广的原则。

**问诊记录可以成为证据，但只能证明它实际有资格证明的事情。**

| 记录 | 有资格证明 | 无资格证明 |
|--------|--------|--------|
| 自记的 consultation event | Agent 声称执行过问诊工作流 | 外部问诊确实完成 |
| 具来源认证的问诊答复归档 | 某次问诊答复确实存在，内容可核对 | 答复裁定已经被执行 |
| 经授权的 Decision receipt | 某条裁定被正式采纳 | 对应代码已运行 |
| Implementation verification | 指定实现通过相关验收 | 真实 dispatcher 已调用 skill |
| 独立 dispatch witness | 指定 skill revision 被真实采用 | 产物质量或学习收益必然提高 |

所以建议为问诊记录设置正式地位：

`CONSULTATION_INPUT`

若原始答复归档具备可验证来源，则可升级为：

`CONSULTATION_ARCHIVED`

经过授权者正式采纳之后，才可以生成：

`DECISION_ACCEPTED`

但是绝不允许直接从 `CONSULTATION_ARCHIVED` 推导 `IMPLEMENTATION_VERIFIED`。

本轮锚点 `FUSE7-T-94CE72A6` 也只能用于识别这次问诊材料，不能充当真实执行 witness、独立签名或授权批准。

这就解决了你担心的循环：问诊记录不是永远被排除在证据体系之外，而是被限制在与自身来源能力相符的证据层级。
