## Q1｜done\_when 登记机制：不能只把必填字段搬到表单里

裁定：①登记工具 + ②写入闸门 + ③保留 Gate33，三层同时存在

### \(a) 裁定

选择组合方案，但三层责任不同：

| 层次 | 负责什么 | 不负责什么 |
|--------|--------|--------|
| 登记工具 | 引导填写并在提交前校验结构、占位符及验收依据 | 不代替批准者判断目标价值 |
| 写入闸门 | 控制 CT 何时可以进入权威 `TASKS.yaml` | 不自行生成 done\_when |
| Gate33 | 对最终索引及真实消费路径进行独立复核 | 不作为日常补漏的唯一机制 |

#### 1\. 增加 CT 登记工具，但允许草稿未完成

建议新增：

`runners/register-ct.mjs`

它应有两个明确动作：

```text
register-ct --draft
register-ct --commit
```

**Draft：** 可以缺少 `done_when`，但只允许写入隔离的登记草稿区域。

**Commit：** 只有完成结构校验、实质性最低检查、权限核验后，才能原子地将 CT 写入权威 `TASKS.yaml`。

这样既不逼人在任务构想阶段编造验收条件，也不会允许一条半成品 CT 进入正式 Task Index。

建议状态：

```text
DRAFT_UNREGISTERED
READY_FOR_REGISTRATION
REGISTERED
REJECTED
```

`DRAFT_UNREGISTERED` 不是正式 CT 记录，也不能被正式流程当成已登记任务消费。

不要用 `status: registered` 加 `done_when: 待定` 的方式模拟草稿。那只是把缺失字段伪装成有效字段。

#### 2\. done\_when 必须通过两层检查

**第一层：格式与占位符拒收。**

建议对提交前的文本进行 Unicode NFKC 规范化、空白压缩及首尾清理。

最低拒收规则可配置为：

```regex
^(?:待定|待补|待填写|暂无|后续补充|稍后完善|TBD|TODO|TBC|N/A|NA|无|任务完成|符合要求|完成即可)$
```

再拒绝：

```text
缺字段
空字符串
纯空白
只有标点
规范化后与占位符完全相同
重复的验收条件
```

建议对 `TODO:`、`待补充：` 等明显占位前缀设置单独规则。

但**不能认为“不命中占位符正则”就等于验收条件有意义**。

例如：

> 完成所有相关工作并确保质量。

它不会命中上述正则，却依然无法机械验收。

**第二层：验收依据检查。**

建议每个条件都关联明确的验收对象。即使目前冻结 schema 把 `done_when` 定义为字符串，也可以在受控的 sidecar 里记录机器验收元数据，不必擅自修改 task-v2。

例如：

```yaml
task_id: CT-31
done_when_sha256: "<sha256>"

criteria:
  - criterion_id: CT31-C1
    expected_result: BLOCK
    verifier_ref: "test://ct-registration/missing-done-when"
    evidence_kind: test_receipt

  - criterion_id: CT31-C2
    expected_result: PASS
    verifier_ref: "test://ct-registration/valid-registration"
    evidence_kind: test_receipt
```

这份 sidecar 只用于引用和约束，不能成为另一套有权覆盖 `TASKS.yaml` 的完成标准。

验收测试尚未实现时，可以登记预期的测试 ID 与验收目标，但不能填写一份不存在的成功测试收据。

**注册时证明条件可判定；完工时才证明条件已满足。**

这两个阶段必须分开。

#### 3\. 真正的写入闸门应该由谁把守？

**由控制平面受控写入器及其上游发布/合并策略把守，而不是由登记发起 Agent 自行宣布通过。**

建议：

`runners/ct-registration-gate.mjs`

真实写入流程为：

**登记发起者提交 CT 草稿**

包含 done\_when、来源和验收依据

**ct-registration-gate**

校验语法、来源、占位符、权限和冲突

**受控写入器原子提交**

验证现有 TASKS hash 未变化，写入并重新读取校验

**Task Index → Gate33**

重新建立来源 receipt，验证消费者端未漂移

注册器必须使用带预期旧版本 hash 的写入条件，避免两个会话同时读取旧 `TASKS.yaml` 后相互覆盖。

如果当前文件 hash 已变化：

`CT_REGISTRATION_CONCURRENT_MODIFICATION`

不得自行合并或强制覆盖。

#### 4\. 必须回答“绕过登记工具直接改文件怎么办”

这是本题最重要的权限边界。

如果其他会话仍然可以用文件编辑工具直接改写 `machine/TASKS.yaml`，那么无论 `register-ct.mjs` 多完善，**都无法保证盘上的权威文件始终没有缺失 done\_when 的 CT**。

至少需要两道独立保护：

1. 正式发布、合并或切换前，必须验证当前 `TASKS.yaml` 和 Task Index；任何缺失不得进入被认可的权威快照。
2. 如果要求连本地工作树都不能短暂写入不合格 CT，就必须用 OS 文件权限、受控单写者服务或等价隔离阻止直接改写。

Git pre-commit hook 有价值，但不能被当成不可绕过的权限边界，因为本地 hook 可以被跳过。

所以我建议把目标精确定义为：

**所有已接受、已发布的控制平面快照中，`done_when` 缺失类违规恒为零。**

而不是在所有允许自由编辑的临时工作树中宣称永远为零。

### \(b) 机械红绿判据

建议新建一份登记验收收据：

`runtime/acceptance/ct-registration/verdict.json`

最低字段：

```json
{
  "schema_version": 1,
  "gate": "CT_REGISTRATION",
  "source_manifest_sha256": "<64-hex>",
  "writer_build_sha256": "<64-hex>",
  "registration_policy_sha256": "<64-hex>",
  "committed_ct_missing_done_when": 0,
  "committed_ct_placeholder_done_when": 0,
  "committed_ct_missing_acceptance_ref": 0,
  "unauthorized_direct_write_count": 0,
  "gate33_done_when_violations": 0,
  "negative_tests_passed": true
}
```

其中 `unauthorized_direct_write_count` 不能仅靠检查文件最终内容算出来；它需要受控写入审计或受保护的发布机制支持。

建议必须通过以下负例：

| 负例 | 机械预期 |
|--------|--------|
| 草稿缺 done\_when | 允许存在于草稿区；禁止正式登记 |
| done\_when 为“待定” | 登记拒绝，`TASKS.yaml` hash 不变 |
| 非空但没有可定位验收条件 | 登记拒绝 |
| 直接向权威文件写入缺字段 CT | 发布/合并闸门 RED |
| 并发登记使用旧文件 hash | 拒绝陈旧写入 |
| 注册器报错后留下半条 CT | RED，且原权威文件应保持不变 |
| 新 CT 合格但 Task Index 未重建 | Gate33 或发布新鲜度闸门拒绝 |
| 新 CT 来源未获授权 | 拒绝，不因 done\_when 完整而放行 |

#### 绿色条件

```text
已发布 CT 全量集合 = Task Index 中 CT 集合
AND 每条 CT 有合法 done_when
AND done_when 关联可定位的验收依据
AND 占位符检查通过
AND 来源权限检查通过
AND 当前 TASKS 与索引 receipt 匹配
AND 直接绕过登记工具的负例被发布闸门拒绝
AND Gate33 done_when 违规 = 0
⇒ CT_REGISTRATION_GREEN
```

还应设一个可持续观察的指标：

`post_registration_done_when_repair_count`

它统计**正式发布后因为漏字段而进行的补救次数**，不能通过删除失败日志使其回零。

根治验收至少需要真实的一次合法新 CT 注册，以及一次缺字段注册被前置拒绝。

五次历史漏填应作为旧问题保留，不要求重写历史让计数看起来从未发生。

### \(c) 明确延期项

本轮不做：

- AI 从标题自动生成并批准 done\_when；
- 将自然语言完成标准自动等价转换为可执行测试；
- 重写 task-v2 冻结 schema；
- 为所有旧 CT 重新填写完成标准；
- 删除 Gate33 事后复核；
- 为所有普通 Task 建设同一套交互表单。

普通 Task 的权威仍在对应看板；CT 注册工具只处理 CT 的控制平面权威。

**更不能用“登记工具已经发布”作为完成证据。必须用一次真实合法登记与一次真实拒收证明入口有效。**

## Q2｜代际链保留：允许归档分层，不允许清理器自行改写历史真实性

裁定：先做只读清理计划；物理删除必须另过授权与 Gate38 语义验收

### \(a) 裁定

你已经有 mirror-drift 7 代、growth-census 4 代，而且曾经因为目录型 artifact 的归档粒度错误产生过大量合法留档。

这说明确实需要管理存储增长，但**当前证据还不足以证明必须立即执行删除**。

尤其注意现有契约：

```yaml
unreferenced_min_generations: 2
referenced_generations: until_explicit_release
approved_evidence: preserve_with_decision
```

这里的 `min_generations: 2` 是**最低保留数量**，不是“超过两代就自动可以删除”的授权。

更关键的是：按你此前描述，Gate38 会校验代际 manifest 链及快照字节。

因此如果清理器直接删除一个未引用快照，Gate38 仍然要求验证它的字节，就会出现：

```text
清理器按保留策略认为可以删除
           ↓
Gate38 因快照文件缺失而 RED
```

**这不是调整清理器扫描规则就能解决的，而是必须先裁定 Gate38 对“合法退役的未引用代”采用什么校验语义。**

#### 我的建议：分两阶段建设

**阶段 A：只读保留审计** (现在允许)

新建 `runners/plan-generation-retention.mjs`。

扫描所有已知代、引用者、批准件、历史证据与保留策略，只生成待处理清单，不移动也不删除字节。

---

**阶段 B：受控归档或清理** (条件具备后开放)

新建独立的 `runners/apply-generation-retention.mjs`。

只有计划获得授权、引用闭包完整、当前输入未发生变化、Gate38 支持对应保留语义且负例通过后，才允许执行。

在当前规模下，我更推荐先通过减少重复归档、隔离冷存储或内容去重降低增长，而不是急着开放不可逆的快照删除。

### 1\. 谁有权运行？

需要区分三种权限：

| 操作 | 允许主体 |
|--------|--------|
| 扫描并生成保留计划 | 只读审计 runner，可由定时任务触发 |
| 批准清理计划与例外释放 | 拥有归档保留/销毁权限的授权者 |
| 执行已批准计划 | 受控清理执行器，只能处理获批路径和版本 |

执行 Agent 可以提出计划，不能单凭自己运行了扫描器就批准销毁。

对于有正式引用的代，必须首先经过**引用解除**程序。即使清理器由有权限的账户运行，也无权自动解除批准件或活跃 Evidence 对该代的引用。

### 2\. 引用判定必须扫描完整闭包

你提出的三个来源——Evidence Index、Candidate 的 `snapshot_ref`、approvals——都是必要来源，但**不够完整**。

建议至少扫描：

| 来源 | 要保护的内容 |
|--------|--------|
| 当前 Evidence Index | 当前正式索引引用的具体代 |
| 历史 Evidence Index / 归档 receipt | 曾被保留用于复核的代 |
| L1 triage、Candidate、Experience | 学习来源中钉住的代 |
| Skill Proposal / Contract Proposal | 提案形成时的 Evidence 代 |
| 已批准契约及审批附件 | 裁决时点封存的原始证据 |
| Decision 与 Task 验收收据 | 决策或验收所依赖的代 |
| distill / Gate 运行收据 | 仍处于审计保留期的验证依据 |
| 人工保留清单 | 法定、治理或故障调查性质的保留 |
| 尚未迁移的 legacy 引用 | 无法安全归属时暂时冻结相关代 |

不能只从“今天最新的 evidence.json”判断历史某代有没有引用。批准过的提案可能已经退出当前索引，但仍承担长期审计责任。

建议建立：

`runtime/generation-retention/reference-inventory.json`

每条引用至少有：

```json
{
  "referrer_id": "<object-id>",
  "referrer_type": "approved_contract",
  "referrer_sha256": "<64-hex>",
  "artifact_id": "mirror-drift",
  "generation_id": "gen-000001",
  "content_sha256": "<64-hex>",
  "retention_status": "PINNED",
  "release_ref": null
}
```

若某个引用源尚无法解析或无法枚举，扫描器应报告 `REFERENCE_INVENTORY_INCOMPLETE`，而不是默认没有引用。

**扫描不完整时，删除资格必须为零。**

#### 一个容易被忽略的区别

Manifest 的 `previous_generation_id` 是代际结构关联，不能简单当作普通业务引用。

否则：

```text
gen-000007 → gen-000006 → ... → gen-000001
```

每一代都因为被后继代引用而永久 PINNED，保留策略实际上永远不会生效。

所以需要两个不同概念：

- `chain_predecessor`：用来验证历史顺序，manifest 元数据必须保留；
- `evidence_pin`：来自真实业务证据、批准或审计需求，决定快照字节是否需要保留。

不过，即使某代没有 `evidence_pin`，在当前 Gate38 仍逐字节验证所有快照的情况下，也**不能直接删除它**。

要让未引用快照合法退役，必须先发布新的、经授权的生命周期校验规则。

### 3\. 保留计划怎样计算？

建议按 artifact（目录型 artifact 则进一步按有稳定身份的成员文件）分别计算。

定义：

\[
KEEP = PINNED \cup RECENT_N \cup HOLDS \cup UNKNOWN
\]

其中：

- `PINNED`：任何正式引用仍有效的代；
- `RECENT_N`：每个保留序列最新至少 N 代；
- `HOLDS`：被授权保留的调查、故障或审计材料；
- `UNKNOWN`：引用状态无法可靠判明的代。

只有不属于上述集合的代，才可以成为**待批准的清理候选**。

不是立即可以删除。

建议的计划收据：

```json
{
  "schema_version": 1,
  "plan_id": "<id>",
  "mode": "PLAN_ONLY",
  "lifecycle_contract_sha256": "<64-hex>",
  "generation_inventory_sha256": "<64-hex>",
  "reference_inventory_sha256": "<64-hex>",
  "reference_inventory_complete": true,
  "total_generations": 111,
  "pinned_generations": [],
  "recent_retained_generations": [],
  "held_generations": [],
  "unknown_generations": [],
  "proposed_actions": [],
  "estimated_reclaimable_bytes": 0,
  "destructive_write_count": 0
}
```

`111` 仅用来示意结构。真实总数必须重新从盘上计算，并区分 artifact 代、目录成员代与 manifest 记录数，不能把此前的 111 行直接当成 111 个独立可清理快照。

每个 `proposed_actions[]` 元素至少包含：

```text
artifact_id
generation_id
snapshot_path
snapshot_sha256
snapshot_bytes
action
eligibility_reason
reference_scan_ref
retention_contract_ref
```

路径还必须经过规范化和受管目录校验，不允许通过软链接、相对路径穿越或意外目录匹配删除其它文件。

### 4\. 物理清理的两个可选终态

#### 方案 A：冷归档，保留可复验字节

建议优先采用。

将很少访问的历史快照迁移到受控的不可变内容存储，原有引用仍能通过受保护的位置映射取回对应字节。

必须注意：**不能直接修改已经封存的 manifest，把原来的 snapshot\_path 改成一个新路径，再说历史没变。**

应使用新的版本化存储位置映射：

```text
immutable generation manifest
           +
versioned storage-location registry
           ↓
same snapshot bytes
```

校验器需要同时验证原始 content hash 和有效的存储位置映射。

这种方案可以降低热存储占用，但只有冷归档位于不同物理存储或采用实际去重/压缩时，才会节省相应资源；在同一磁盘简单搬目录不会减少总占用。

#### 方案 B：真正删除未引用代的快照字节

这必须延期到新的生命周期契约与 Gate38 验证器获批之后。

未来可以保留原 manifest、hash、sequence、前代关联和一份受审批的清理 tombstone：

```json
{
  "artifact_id": "<id>",
  "generation_id": "<id>",
  "content_sha256": "<64-hex>",
  "retention_state": "PRUNED_UNREFERENCED",
  "prune_plan_sha256": "<64-hex>",
  "approval_ref": "<approval-ref>",
  "pruned_at": "<UTC-time>"
}
```

新的 Gate38 应区分：

```text
RETAINED
ARCHIVED_RETRIEVABLE
PRUNED_UNREFERENCED
MISSING_UNAUTHORIZED
```

`PRUNED_UNREFERENCED` 不能再被称为“快照字节完整可复验”。

其历史 manifest 链或许仍完整，但被删的原始字节已经无法逐字复验；这是审计能力的真实降级，必须有明确批准。

**绝不允许仅仅为了维持 Gate38 GREEN，就把“原始字节不存在”改名为“完整性通过”。**

### \(b) 清理后的机械红绿判据

#### 第一阶段：只读计划 GREEN

```text
所有受管 artifact 均已扫描
AND 所有引用来源已枚举
AND 未知引用均标为保护
AND 每条待清理代有明确资格依据
AND 每个 artifact 最新 N 代受到保护
AND 所有已批准证据保持 PINNED
AND 计划绑定当前契约及清单 hash
AND destructive_write_count = 0
⇒ RETENTION_PLAN = GREEN
```

这意味着计划正确，不代表任何磁盘空间已经释放。

#### 第二阶段：受控清理 GREEN

执行前必须重新读取并验证：

```text
当前 generation_inventory_sha256 = 已批准计划的输入
AND 当前 reference_inventory_sha256 = 已批准计划的输入
AND approval 精确绑定计划 hash
AND 当前 Gate38/契约版本支持该操作
AND 没有新引用出现
AND 没有未解除的 evidence pin
```

执行后必须留下：

`runtime/generation-retention/<run-id>/apply-receipt.json`

至少含：

```json
{
  "plan_sha256": "<64-hex>",
  "approval_ref": "<approval-ref>",
  "gate38_before": "GREEN",
  "gate38_after": "GREEN",
  "referenced_snapshot_missing_count": 0,
  "retained_snapshot_hash_mismatch_count": 0,
  "manifest_chain_broken_count": 0,
  "unauthorized_delete_count": 0,
  "processed_actions": [],
  "actual_reclaimed_bytes": 0
}
```

`gate38_after` 必须由真实 Gate38 运行结果产生，不能由清理器自填。

`actual_reclaimed_bytes` 必须实际测量，不能把拟删除文件大小之和直接当成空间回收量，尤其在去重或硬链接情况下。

#### 必须通过的负向回归

| 负例 | 预期 |
|--------|--------|
| 某代被已批准契约引用 | 清理拒绝 |
| 某代不在当前索引，但被历史批准件引用 | 清理拒绝 |
| 存在未知格式的引用来源 | 拒绝破坏性清理 |
| 计划批准后出现新 Candidate 引用 | 输入漂移，原计划失效 |
| 清理器尝试删除最新 N 代 | 拒绝 |
| 清理器尝试删除 manifest 结构记录 | 拒绝 |
| 快照实际缺失，却无合法归档/清理收据 | Gate38 RED |
| 非法删除后强行把 Gate38 置绿 | 验收失败 |

### 频率裁定：限的是无意义快照，不是合法观测

**不建议设一个机械的“每天最多产生 X 代”上限。**

如果探针确实观察到一天内多次不同结果，硬性限代可能直接造成证据丢失。

但你提到“索引重建导致归档代数增长”，这应该作为实现缺陷处理，而不是正常生产频率。

最低不变量：

```text
纯 Evidence Index 重建
⇒ new_generation_count = 0

同一输入、同一生成器的幂等重建
⇒ new_generation_count = 0
```

对于探针，即使观测字节完全相同，也可能需要保存“今天确实执行过检查”的观察事件；但可以将**观察事件记录**与**相同内容的快照字节存储**分离，避免重复占用空间。

对于 growth-census，必须按实际发生修改的成员文件归档，不能因为目录中一个文件变化就无条件复制所有十个文件。

推荐频率：

- 保留计划：每日探针运行后只读计算一次，或由容量阈值触发；
- 清理执行：初期按周或实际容量压力安排，需要独立审批；
- 增长预警：基于每个 artifact 的新增代数、快照字节和引用保留比例；
- 真实覆盖：仍按真实生产节奏，不为维持代数预算丢弃观测。

### \(c) 明确延期项

- 物理删除历史快照；
- 将所有代迁移到外部对象存储；
- 自动解除历史 Evidence pin；
- 自动修改已批准契约的保留期限；
- 根据文件年龄推断可以删除；
- 对全部历史清理责任进行一次性重分类。

**R13 最小合格交付应该是：一份能够证明“哪些能考虑清理、哪些绝对不能清理”的只读计划，而不是一个已经可以执行 `rm` 的脚本。**

## Q3｜Gate33 审计身份：schema\_sha256 与稳定 violation\_id 值不值得做？

### \(a) 裁定

**两项都值得做，但优先级和用途不同。**

| 改进项 | 边际价值 | 优先级 | 主要解决什么 |
|--------|--------|--------|--------|
| `schema_sha256` | 高 | P1 | 证明违规是针对哪一份确切规范判定的 |
| 稳定 `finding_key` | 中高 | P1 | 同一个问题跨运行能持续追踪 |
| 内容寻址 `violation_id` | 中高 | P1/P2 | 精确区分同一问题在不同输入或规范版本下的发生实例 |

你提到 NEG-11 已经证明 Gate 本身不防 schema 篡改、防线在基线。

这个事实不意味着 `schema_sha256` 的价值降低到可以忽略。

它的真正用途不是防止别人修改 schema，而是：

**让历史审计结论无法在丢失判定依据的情况下，被解释为“按当前 schema 验证过”。**

举例：

```text
Run A:
  Task-v2 schema hash = H1
  CT-31 → violation

Run B:
  Task-v2 schema hash = H2
  CT-31 → PASS
```

如果没有记录并验证 H1、H2，就无法判断违规消失究竟由于：

- Task 被合法修复；
- Task 经批准迁移；
- Schema 正式修订；
- Schema 被未经授权放宽。

所以我裁定：

**schema\_sha256 必须补齐；但它必须与受授权的版本绑定清单核对，不能只由 validator 自己对当前 schema 计算一个 hash 再自称可信。**

### 1\. schema\_sha256 的权威校验

最低关系：

```text
validation_receipt.schema_sha256
=
SHA256(validator 实际读取的 schema 字节)

且

validation_receipt.schema_sha256
=
approved_spec_binding.schema_sha256
```

如果 schema 通过 `$ref` 引用了其他文件，还需为完整引用闭包建立规范化 manifest 摘要。

否则攻击者只需不改主 schema、改被引用的子 schema，顶层 hash 仍保持一致。

建议一次验证至少记录：

```json
{
  "binding_id": "task-v2",
  "schema_ref": "machine/schemas/task-v2.json",
  "schema_sha256": "<64-hex>",
  "schema_closure_sha256": "<64-hex>",
  "spec_binding_sha256": "<64-hex>",
  "approval_ref": "<approved-schema-revision>",
  "validator_build_sha256": "<64-hex>"
}
```

其中批准的绑定清单本身也应有可信来源，例如经过受保护发布流程验收的 commit、授权记录或签署的版本清单。

如果 schema 与 binding 都由同一执行 Agent 随意修改，仅比较两者是否相等仍然是自证。

#### 机械判定

```text
实际 schema hash = 收据 schema hash
AND 完整 $ref 依赖闭包 hash 匹配
AND 受授权 spec_binding 指向该 schema
AND 当前版本具备有效修订批准
AND 原冻结 v1 字节未被改写
⇒ SCHEMA_IDENTITY_GREEN
```

反例：

```text
改动 schema 文件
同步更新收据中的 schema_sha256
但未取得规范修订批准
⇒ RED_UNAUTHORIZED_SCHEMA_REVISION
```

这条反例比简单“修改 schema 后 hash 不匹配”更有价值，因为它能够检验是否真的存在独立于报告生产者的规范权威。

### 2\. violation\_id：建议拆成两个 ID

**不建议把跨运行稳定性和逐字节内容寻址压进同一个 ID。**

因为你实际上有两种不同的问题：

1. 这是不是同一个长期存在的缺陷？
2. 这是不是同一份输入、同一版规范下的完全相同违规？

建议同时记录：

- `finding_key`：语义上的长期问题身份；
- `violation_id`：一次确定输入与规范组合下的内容寻址违规身份。

#### finding\_key

建议计算：

\[
K=\operatorname{SHA256}(
v \Vert binding \Vert object \Vert pointer \Vert reason
)
\]

其中：

```text
v             = finding-key 算法版本
binding       = 绑定类型与稳定身份
object        = 实例的稳定业务 ID
pointer       = 规范化 JSON Pointer
reason        = 稳定 reason_code
```

不包含：

```text
run_id
运行时间
遍历顺序
错误序号
随机 UUID
```

这样同一个 CT 的 `done_when` 缺失问题，跨多次运行仍然具有相同的 `finding_key`。

#### violation\_id

建议进一步绑定内容和规范：

\[
V=\operatorname{SHA256}(
K \Vert instanceHash \Vert schemaClosureHash \Vert validatorPolicyHash
)
\]

这意味着：

- 同一实例、同一 schema、同一违规：ID 不变。
- 实例内容变化：violation\_id 变化，但 finding\_key 可以不变。
- Schema 换代：violation\_id 变化。
- 验证政策变化：violation\_id 变化。
- 不同运行顺序：两者都不变。

必须固定规范化编码方法，例如版本化的 canonical JSON 和明确的 UTF-8、路径及 JSON Pointer 规范化规则。

否则同一结构可能因键顺序或操作系统路径格式差异得到不同摘要。

推荐输出：

```json
{
  "finding_key": "fk1_<64-hex>",
  "violation_id": "v1_<64-hex>",
  "binding_id": "task-v2",
  "instance_id": "CT-31",
  "instance_ref": "<path-or-uri>",
  "instance_sha256": "<64-hex>",
  "schema_ref": "<schema-ref>",
  "schema_sha256": "<64-hex>",
  "schema_closure_sha256": "<64-hex>",
  "validator_policy_sha256": "<64-hex>",
  "json_pointer": "/done_when",
  "reason_code": "REQUIRED_FIELD_MISSING"
}
```

对应基本正则：

```regex
^fk1_[0-9a-f]{64}$
```

```regex
^v1_[0-9a-f]{64}$
```

但字符串匹配只是格式检查，真正的验收必须重新计算哈希。

### \(b) 机械红绿判据

#### 两个最关键的稳定性测试

测试 A：相同输入，重复校验

Run 1

`finding_key = K1`

`violation_id = V1`

Run 2

`finding_key = K1`

`violation_id = V1`

重新运行、调整扫描顺序，都不得改变 ID。

---

测试 B：同一问题，输入修订

原实例

`finding_key = K1`

`violation_id = V1`

修订后仍违规

`finding_key = K1`

`violation_id = V2`

长期问题保持可追踪，具体违规实例因内容变化而更新。

需要补齐五项负向回归：

| 测试 | 预期 |
|--------|--------|
| 完全相同输入连续校验两次 | 两种 ID 均一致 |
| 打乱实例扫描顺序 | 两种 ID 均一致 |
| 修改实例其它字段但保留同类违规 | finding\_key 一致，violation\_id 随实例摘要变化 |
| 修改 schema 但没有授权 | 规范身份 RED，不允许凭违规消失宣布合格 |
| 合法迁移 v1→v2 | 新旧违规分别绑定准确的 schema 版本与迁移收据 |

还应验证：

```text
reported_violation_count
=
distinct(violation_id).count
```

但是要注意：如果同一输入中真的存在两个不同约束产生完全同位置、同 reason code 的错误，还需要将稳定的约束 ID 纳入 `finding_key`，避免错误合并。

建议标准输出添加：

```json
{
  "total_violations": 0,
  "distinct_violation_ids": 0,
  "distinct_finding_keys": 0,
  "schema_identity": "GREEN",
  "id_determinism_tests": "GREEN"
}
```

R13 当前 Gate33 为 79 实例 0 违规。

因此**不能仅靠当前真树 0 违规证明稳定 ID 算法已经正常**。

必须在隔离环境构造至少两种真实 schema 约束失败，分别运行多次，并检查上述性质。

### \(c) 明确延期项

- 历史所有 Gate 的 violation\_id 全量回填；
- 对 R1\~R10 旧报表追溯生成稳定 ID；
- 跨所有类型 Gate 推出统一全局问题 ID；
- 利用 finding\_key 自动合并不同审计系统的语义问题；
- 修改冻结的 task-v1/state-v1；
- 把哈希校验升级宣称为防恶意修改的完整安全机制。

本轮只要求 Gate33 先具备版本化规范身份与稳定审计键，再视实际用途推广。

**优先级判断：schema\_sha256 值得尽快补，稳定 ID 也值得做，但它们都不应插队到 CT 前置登记和持续新增的不合格 L1 写入之前。**

## 三项追加追问：R13 还有三个应该进入主线的缺口

### 1\. 学习链 pinned evidence：必须单独立项

**裁定：是。建议状态 `LEARNING_PINNED_CONSUMPTION = UNKNOWN`。**

R11-A 已证明 URI resolver 能够跨代准确读取旧快照。

R12-A 已证明部分索引和 Gate 消费路径可以使用封存字节。

但这两个事实不能合起来替代：

```text
真实 Demand / Evidence
    ↓
真实 pinned_evidence
    ↓
学习 Candidate
    ↓
审核 disposition
    ↓
获准产物
```

它仍然缺少一条从真实学习输入到被审核产物的完整引用链。

建议在统一总账新增：

`LEARNING-PINNED-E2E`

最小验收包：

| 证据 | 必须证明 |
|--------|--------|
| `input-manifest.json` | 真实 Demand、L1、Evidence 的 ID/hash，且 L1 writer gate 合格 |
| `candidate.json` | 候选引用显式 generation 和快照 hash |
| `resolver-receipt.json` | 解析到确切旧代，读到预期字节 |
| `disposition.json` | 人审绑定当前 Candidate 内容 |
| `artifact-receipt.json` | 规定产物实际写入且 hash 匹配 |
| `verdict.json` | 以上引用链全部由校验器复验 |

再补一个关键负例：

```text
生成 Candidate 时引用 gen-000003
    ↓
探针写出 gen-000004
    ↓
重新验证 Candidate
```

必须仍然读取 `gen-000003`，不能自动变成 `gen-000004`。

对于 R12-A 的“改绑最新已归档代”，应额外做一次身份审计：

```text
同一 Evidence ID
不得在两次 index build 后
静默指向不同 generation
```

如果现在的实现只是生成新的 Evidence ID 指向新的代，同时历史 ID 不变，则满足这一要求。

如果历史 ID 被覆盖或重解释，应判：

`EVIDENCE_IDENTITY_REBOUND_RED`

并修复，而不是把它当作普通的索引刷新。

首例真实学习链应使用已经存在的合法 Demand 与自然产生的 pinned evidence，不需要为了验收制造一条假的漂移事件。

### 2\. 跨会话 L1 写入：这不是教育问题，是入口权限问题

**裁定：必须建立统一 L1 写入协议，并让所有执行会话共用同一个受控写入边界。**

你现在看到不合格 L1 从 25 增至 27，而历史 P0×3 已经修复。

这说明存量修复有效，但仍然持续产生新的欠账。

如果每次只在出问题后“提醒另一个会话下次注意 SOP”，这个数字仍可能增长。

建议新增一条强约束：

```text
任何新 L1 进入正式学习输入目录
    必须具备合法产物意图
    以及来源、作者权限和版本绑定
```

不符合时可以保存为隔离草稿，但不能进入正式 Evidence→Experience 生产路径。

最小改造：

- 所有新 L1 由共同 writer 接口接收，写盘前执行 `l1-writer-gate`；
- 各 Agent 的任务入口引用同一份受控写入规范，不得各自复制一份容易漂移的 SOP；
- Agent 无权调用直接写正式 L1 的绕过路径；如果操作系统层面仍可直接改写，正式发布/学习消费边界还必须再验证；
- 所有拒绝事件输出统一 reason code；
- `build-l1-repair-queue` 只处理真正形成的历史欠账，不承担代替实时写入控制的责任。

建议统计：

```text
new_l1_committed_without_intent
new_l1_quarantined_without_intent
new_l1_writer_gate_bypassed
```

验收目标：

```text
new_l1_committed_without_intent = 0
new_l1_writer_gate_bypassed = 0
```

隔离草稿可以存在，但必须不可被正式 Candidate/Distill 消费。

还需要一个跨会话负例：模拟另一执行会话通过直接写文件的方式提交缺意图 L1，证明它不能进入正式学习路径。

**修复队列是对旧债的管理；写入边界才是防止新债的办法。不能把“27 条均已入队”当成缺陷根治。**

### 3\. 代际密度和重建频率：应该纳入治理，但不要制定错误的频率上限

**裁定：增加增长预算、幂等检测与容量预警，不以固定时间间隔限制合法观测。**

建议新增：

`runtime/generation-growth-report.json`

最少记录：

