# GPT Extended 问诊：:3100 API 转发网关常驻方案评审（2026-08-29）

## 一、核验令牌（回复首行必须原文引用，证明实读本文档）
GW-STABLE-SVC-2026-0829-9RB6-VERIFIED

## 二、背景
- :3100 = 多厂商 LLM API 聚合转发网关（OpenAI 兼容 /v1/chat/completions），入口 `D:\项目\services\search_gateway\api_gateway.py`（约 1200 行，纯 stdlib，`ThreadedServer("0.0.0.0", 3100)`）。
- 现状常驻机制：两个「登录触发一次」的计划任务：
  - `SearchGateway`：`python.exe D:\项目\services\search_gateway\api_gateway.py`
  - `SearchGatewayWatchdog`：`cmd /c D:\项目\services\search_gateway\watchdog_gateway.bat`（每 30 秒 `netstat` 查 :3100 是否 LISTENING，无则 `schtasks /Run /TN SearchGateway`）
- 用户症状：网关反复「莫名被关掉」，过段时间又打不开；另一项目 `D:\DeepSeek\deepseek-harness` 由另一 AI 工作台 qoder 自带守护进程托管，一直稳定。
- 本机：Windows 11 Home 笔记本（电池型号 R15B06W）。

## 三、已验证事实（均可机器复核）
1. 两个计划任务均 `DisallowStartIfOnBatteries=true` + `StopIfGoingOnBatteries=true` → **拔电源=进程被系统强杀；电池状态无法启动；插回电源也不会自动恢复**（LogonTrigger 仅登录时触发一次，RestartOnFailure 不覆盖「被电池策略停止」）。已用 `schtasks /Change` 改为 false（2026-08-29，已验证生效）。
2. `SearchGatewayWatchdog` 上次运行结果 `0xC000013A`（Ctrl+C 终止）；`SearchGateway` 上次运行结果 `0x8007042B`（进程被终止）。
3. 已尝试「原生服务直接跑 python」：`New-Service -BinaryPathName "python.exe api_gateway.py"` → 服务启动 30 秒后失败，System 事件 **7000/7009**（service did not respond to the start or control request）→ 普通 python 脚本不调用 `StartServiceCtrlDispatcher`，**不能直接作为 Windows 服务**，必须用包装器（NSSM / winsw / pywin32）。
4. 已给 `api_gateway.py` 加端口自愈（commit `875fa19`）：新增 `_bind_server(port, handler, retries=3)`，仅当 bind 失败（端口被占）时用 `netstat` 定位监听该端口的 PID（跳过自身）`taskkill /F` 后重试，最多 3 次；正常路径不杀任何进程。
5. 计划任务与看门狗当前已 `Disable`，:3100 当前无监听（服务未注册，待本评审后再动）。

## 四、拟议方案（待评审）
A. **NSSM 包装 api_gateway.py 为 Windows 服务**（服务名 `API3100Gateway`）：
   - `AppDirectory = D:\项目\services\search_gateway`
   - `AppStdout/AppStderr` → `runs\_svc_3100.out.log / _svc_3100.err.log`，`AppRotateFiles 1`
   - `AppExit Default Restart` + `AppRestartDelay 3000`（崩溃 3 秒后自动重启）
   - `Start = SERVICE_AUTO_START`（开机自启，早于用户登录）
   - 服务账户：默认 LocalSystem（待评估）
B. 停用旧计划任务 + 看门狗，**单一控制源 = 服务**。
C. 保留端口自愈补丁（服务崩溃重启时若端口被残留占用可自愈）。

## 五、待裁决/评审问题
1. 服务化（NSSM）vs 其他方案（winsw / pywin32 win32serviceutil / 维持计划任务+看门狗）——综合稳定性与运维成本，最优是哪个？deepseek-harness 的「一直稳定」是否等价于「系统服务托管」？
2. **LocalSystem 账户运行网关的风险**：网关要读写 `D:\项目\data\search_gateway\`（本地凭证信任域 channels.json 等）并写日志；LocalSystem 与用户会话的差异（代理、环境变量、网络）会不会导致渠道访问异常？是否值得为此改用「用户账户运行服务」（代价：需要密码，无法纯自动化）？
3. `AppExit Default Restart` 是否会让「管理员主动停止服务」也被误重启（想停停不掉）？NSSM 优雅停止/更新部署（换代码后重启）的正确姿势？
4. 端口自愈补丁（bind 失败 taskkill 监听 3100 的进程）是否有误杀风险（可能杀掉另一个正常运行的实例）？是否应加「命令行必须含 api_gateway 才杀」白名单约束？
5. 验收判据建议：给出「服务崩溃→自动重启」「拔电/插电不断线」「开机自启」的可机器验证判据（参照否定性判据需 scan/count 的纪律）。
6. 开机自启时若 D 盘未就绪（LocalSystem 早于用户会话/磁盘就绪），网关启动会不会失败重试死循环？需要 `AppExit` 区分「端口被占(应重试)」与「D 盘不可达(应等待更长)」吗？
