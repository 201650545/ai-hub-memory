# R10 裁定：规范换代、证据代绑定、L1 修复与学习闭环的授权边界

**总裁定：R8 的四项裁定已有实质落地，但 R10 不能以“新增契约通过”“Gate38 变绿”或“done\_when 缺失清零”推导出整个融合控制平面已经完成迁移。**

本轮应坚持三个边界：

1. **业务事实不能为适配旧 schema 而篡改；旧 schema 也不能由 adapter 私自修订。**
2. **证据可以跨代继续有效，但历史引用不能在没有明确迁移的情况下自动改绑。**
3. **L1 可以补救，却不能通过补字段、重建候选或追认新索引来补造历史授权。**

## R10 总裁定速览

| 事项 | 裁定 | 下一步 |

## Q1｜三个 spec 冲突：正式换代是对的，但不是三个都简单放宽

### \(a) 裁定

**同意你提出的一次正式 schema 修订轮，原则上采用 v1→v2 并行换代，不允许覆盖冻结的 v1 字节。**

但我不同意把这三个问题统称为“schema 太严，需要放宽”。

它们分别是：

- `frozen`：两个不同状态维度混在一个字段。
- `demand_id:null`：尚未区分“不适用”和“尚未归因”。
- `phase`：事实权威已经迁出旧位置，但新的生产机制缺席。

它们都需要修订，不过修订内容不同。

### 冲突①：`frozen` 不应该直接成为第八个普通 Task 状态

**裁定：优先将业务执行状态与治理冻结状态拆开，而不是直接给七值 enum 添加 `frozen`。**

DEC-32 的冻结是真实事实，不应为了通过 schema 将其改为 `done`、`blocked` 或其他七值之一。

但“被冻结”和“业务做到哪一步”可以同时成立：

```text
业务状态：in_progress
治理状态：frozen
冻结依据：DEC-32
```

一个 Task 解冻后，原则上应该恢复其原有业务进度，而不是从一个含混的 `frozen` 值猜测解冻后的状态。

建议 v2 结构：

```yaml
task_status:
  workflow:
    known: true
    value: "<one-of-existing-seven-values>"

  freeze:
    state: frozen
    decision_ref: DEC-32
    scope: "<authorized-scope>"
    effective_at: "<UTC-time>"
    released_at: null
```

如果原先业务状态没有可信来源，应该写：

```yaml
task_status:
  workflow:
    known: false
    value: null

  freeze:
    state: frozen
    decision_ref: DEC-32
```

不能凭冻结事实倒推原来是 `in_progress`。

`known=false` 应由 v2 schema 显式允许，并限制其适用范围，不能成为所有业务状态缺失的通用豁免。

**什么时候才允许把 `frozen` 增加到普通 status enum？**

只有当权威业务定义明确认为“冻结是与 done、blocked 等互斥的生命周期阶段”，而不只是管理性暂停时，才采用第八枚举值。

就本轮事实而言，DEC-32 更像治理冻结，因此我裁定优先采用正交的 `freeze` 维度。

修订时旧实例必须：

- 保留原始 `status=frozen` 的 v1 输入字节及摘要；
- 生成显式的 v1→v2 迁移记录；
- 保留 DEC-32 的关联；
- 不凭空恢复冻结前状态；
- 由 v2 验证器判定新结构，而不是给 v1 schema 偷偷加一个枚举。

### 冲突②：`demand_id:null` 不要改成空字符串

**裁定：不能统一改成 `""`，也不建议只把原字段改为 `string|null` 就收工。**

因为你列出的七条至少存在两种不同语义：

- `scope:local`：可能本来就不需要外部 Demand。
- 工作流或成长项没有 Demand：可能只是尚未完成归因。

二者不能被同一种 `null` 淹没。

建议 v2 改为带判别字段的归因关系：

```yaml
demand_binding:
  kind: linked
  demand_id: "<valid-demand-id>"
```

或者：

```yaml
demand_binding:
  kind: not_applicable
  demand_id: null
  reason_code: LOCAL_SCOPE
```

或者：

```yaml
demand_binding:
  kind: unattributed
  demand_id: null
  reason_code: ATTRIBUTION_PENDING
```

最低约束：

| `kind` | `demand_id` | 机械要求 |
|--------|--------|--------|
| `linked` | 非空字符串 | 指向真实、可解析 Demand |
| `not_applicable` | null | 必须存在合法的不适用依据 |
| `unattributed` | null | 必须进入待归因台账，不得伪装为已完成归因 |
| 缺失/未知值 | 任意 | RED |

特别提醒：**不能把七条原始 `null` 全部自动迁移成 `not_applicable`。**

需要依据各 Task 的授权来源和实际用途分别分类。分类决定可由人批准，但分类之后的字段形态、引用、来源与审批绑定必须可以机械校验。

`unattributed` 可以成为合法的数据表示，但它并不自动满足所有下游流程的需求归因要求。

例如 contract proposal 如果必须有 Demand 来源，那么：

```text
demand_binding.kind = unattributed
⇒ 禁止提升为 Demand-backed Proposal
```

这保证了“schema 合法”和“业务具备执行资格”没有被混为一谈。

### 冲突③：`phase` 应从权威状态事件得出，不应写回 project.yaml

**裁定：保留 phase 的 State 归属，禁止通过新增 `registry.phase` 静态字段解决缺失问题。**

FA\_PHASE\_FORBIDDEN 已经禁止 project.yaml 自行拥有 phase。既然 phase 被迁移到 State，就不应该通过 registry 另建一个会变化的阶段真源。

建议分工：

| 对象 | 负责内容 |
|--------|--------|
| Project Registry | 项目身份、阶段模型标识、允许的阶段取值及映射 |
| Task/Decision/授权状态事件 | 真实阶段变更事实及生效依据 |
| `build_state.mjs` | 根据事件与阶段模型确定当前 phase |
| State projection | 记录 phase 值、来源和归因 |
| 首页 | 消费 State，不自行推断 phase |

当存在明确的阶段设置事件时，可形成：

```json
{
  "phase": {
    "kind": "known",
    "value": "<phase-value>",
    "source_event_ref": "<event-ref>",
    "source_event_sha256": "<64-hex>",
    "phase_model_ref": "<model-ref>"
  }
}
```

当没有合法阶段事件时：

```json
{
  "phase": {
    "kind": "unknown",
    "value": null,
    "reason_code": "NO_AUTHORIZED_PHASE_EVENT"
  }
}
```

`unknown` 只能表示没有证据，不能被当作一个正常业务阶段。

如果部分 State 类型根本没有 phase 语义，v2 可增加 `kind=not_applicable`，但需要在 State 类型契约中显式授权。

**不允许从最近一条 Task 的状态、项目标题或某个看板栏目自动猜 phase。**

如果早期 project.yaml 曾真实保存过 phase，允许通过一次受审批的迁移事件把当时的值带入 State。但该迁移必须绑定旧文件版本、来源摘要和生效时点，不可通过读取当前 project.yaml 重新创建第二个阶段权威。

### v1→v2 的正式修订程序

建议使用一次总修订批次，但分别发布：

`task-schema-v2` 和 `state-schema-v2`。

不要为了修复 Task 的两个字段，就强迫无关 State 消费者同步更换 schema。

1. **冻结 v1**
   
   记录当前 30\_ 原始规范、外部 binding、适配器的版本摘要。原规范字节保持不变。
2. **形成有实义的规范修订动议**
   
   `proposal_kind=contract_change`，分别声明修改目标、字段语义、迁移规则和负向测试。经 Gate37 资格闸后进入审批。
3. **权威批准**
   
   由具备规范修订权限的批准者裁决，并明确授权外部 v2 binding。一般 Task 维护者不能凭编辑权限自行修改冻结规范。
4. **发布独立 v2 schema**
   
   在获批准的 `machine/schemas/` 路径发布；`spec_binding.yaml` 新增版本化绑定，不覆盖 v1 标识。若要求将 v2 纳入 30\_ 原生规范，则另走其所有权批准程序。
5. **显式迁移既有实例**
   
   保存 `source_schema_ref`、`source_sha256`、`target_schema_ref`、`output_sha256` 和迁移授权引用。遇到未知事实不得补造。
6. **双版本验证并逐消费者切换**
   
   v1 实例按 v1 验证，v2 实例按 v2 验证。所有生产消费者明确记录使用的 schema 版本，禁止按“哪个能过就用哪个”的方式自动回退。

要特别反对一种伪迁移：

```text
v1 校验失败
    ↓
自动换用更宽松的 v2
    ↓
标记 PASS
```

这其实是校验降级。

版本应由有效的实例迁移记录或授权绑定决定，不应由校验成功与否决定。

### \(b) 机械红绿判据

每项修订至少输出：

`runtime/schema-migrations/<migration-id>/verdict.json`

最低检查：

```text
v1 原始 hash 未变化
AND v2 有独立 schema_id/version/hash
AND v2 的发布批准可验证
AND binding 精确指向 v2
AND 每条迁移实例有源/目标 hash
AND 迁移规则与 schema 版本绑定
AND 原有业务事实没有被静默删除
AND 全部适用负例通过
```

三个冲突的专项验收：

| 冲突 | GREEN 条件 | RED 条件 |
|--------|--------|--------|
| frozen | 冻结事实与 DEC-32 对应；业务状态与冻结状态分别表示；未知旧状态不补造 | frozen 被硬改为其他业务状态、无 DEC-32 来源、解冻时凭空恢复状态 |
| demand | 七条原始异常逐一完成合法分类；linked ID 可解析；非 linked 不冒充有 Demand | `null→""`、无依据自动 `not_applicable`、未归因却进入 Demand 必需的下游 |
| phase | 4 条 State 逐一有合法事件来源，或有获允许的 unknown/not\_applicable 状态 | 从禁止的 project.yaml 或静态 registry 猜 phase、没有来源却填正常阶段 |

再补两个全局负例：

```text
无授权 v2 binding
⇒ BLOCK

已迁移实例的 source_sha256 与原始字节不匹配
⇒ BLOCK
```

Gate33 目标不是“把现有 15 条从错误清单里删掉”，而是：

```text
原始 15 条 violation 全部有处置记录
AND 相关 v2 实例通过对应 schema
AND 非相关 v1 实例仍按 v1 验证
AND migration provenance 全部有效
AND 未分类 violation 数量为 0
AND 当前 Gate33 全量运行无其它违反
⇒ Gate33 GREEN
```

旧违规可以因授权的 v2 迁移得到合法修复，但不得回写历史，声称旧实例当时符合原始 v1 schema。

### \(c) 明确延期项

本轮不进行：

- 对 30\_ 冻结规范的原地改写；
- 所有历史实例的强制批量升级；
- 自动猜测 Demand 归因；
- 根据任务进度自动推断 phase；
- 立即删除旧 v1 验证器；
- 通过一次迁移直接宣布所有消费者支持 v2。

建议先完成 15 条的身份与原因对账，再提交一次正式规范修订动议。**你关于换代程序的预判正确，但对三个字段的语义不能一概采取放宽策略。**

## Q2｜Evidence Index / Gate35 / Gate36：必须让引用绑定“代”，不能让 URI 偷偷绑定“最新”

### \(a) 裁定

**原则同意你提出的四处修改，但建议调整实施顺序，并明确分开“当前观察引用”和“历史证据引用”。**

尤其不同意这句话中的潜在歧义：

> resolve-uri 对 evidence\:// 条目优先解析快照路径。

如果“优先”意味着遇到旧引用就自动寻找某个可用快照，那依然可能违反 R8 的禁止滚动追认原则。

应该改为：

**显式带代的引用，必须精确解析该代；没有带代的历史引用，不得自动选择最新代、最相近 hash 的代或任何碰巧存在的快照。**

### 1\. 最小修改面

| 组件 | 本轮应修改 | 不应扩张 |
|--------|--------|--------|
| `lifecycle-check.mjs` | 提供已验证的 generation/manifest 查询能力 | 不负责批准 evidence 迁移 |
| `resolve-uri.mjs` | 解析显式 generation + hash；校验目标存在及受管范围 | 不对历史裸 URI 自动选择代 |
| `build-evidence-index.mjs` | 保存代绑定、快照位置、来源 manifest hash | 不重写引用方的旧 Evidence ID |
| `check-evidence-integrity.mjs` | 校验 pinned generation 的原始快照字节 | 不用当前 live hash 代替旧代 hash |
| Gate35/36 | 消费新完整性结果，保留原有其他判据 | 不因 lifecycle 已声明就直接 GREEN |
| Gate37 | 未裁决提案检查 pinned evidence；已裁决件检查历史封存完整性 | 不以当前探针内容重判历史事实 |
| `build-learning-candidates.mjs` / distill | 明确处理旧引用、已固定引用和无法解析引用 | 不自动重写旧 Candidate 的来源 |

Gate32、候选线和 distill 也应纳入本次端到端验收。

否则可能出现 Evidence Index 绿色，而候选生成器仍依赖 live path 的情况。

### 2\. 显式引用格式

建议采用类似下列版本化 URI：

```text
evidence://mirror-drift?gen=gen-000001&sha256=<64hex>
```

这只是建议的语法；必须和现有 `evidence://` 解析格式做无歧义兼容。

三个关键字段：

```text
artifact_id
generation_id
content_sha256
```

解析结果必须满足：

```text
URI.artifact_id = manifest.artifact_id
AND URI.generation_id = manifest.generation_id
AND URI.sha256 = manifest.content_sha256
AND SHA256(snapshot_bytes) = manifest.content_sha256
```

而且 `snapshot_path` 必须解析到获准的快照存储根目录内。不能通过路径穿越或符号链接让 manifest 指向任意文件。

对于 live reference，建议使用明确的引用用途：

```json
{
  "reference_kind": "current_observation",
  "artifact_id": "mirror-drift"
}
```

它可以查询当前一代，但只能用于当前状态判断，不能被固化为历史 Experience 的无版本来源。

对于历史 Evidence：

```json
{
  "reference_kind": "pinned_evidence",
  "artifact_id": "mirror-drift",
  "generation_id": "gen-000001",
  "content_sha256": "<64-hex>"
}
```

**凡是进入 Candidate、Proposal、Disposition 的正式历史证据，必须使用 `pinned_evidence`。**

### 3\. 旧引用迁移不可由 Index Builder 自行决定

建议另外维护迁移记录：

`machine/evidence-reference-migrations.yaml`

最低字段：

```yaml
schema_version: 1
migrations:
  - migration_id: "<id>"
    old_ref: "<exact-legacy-ref>"
    old_referrer_sha256: "<hash-of-referring-record>"
    new_ref: "<pinned-evidence-uri>"
    target_generation_manifest_sha256: "<64-hex>"
    reason_code: LEGACY_REFERENCE_PINNING
    approval_ref: "<authorized-approval>"
    status: approved
```

这里应注意：

- `old_referrer_sha256` 绑定原来引用这条证据的 Candidate/Proposal 等具体对象，避免同名 URI 在不同上下文中被一刀切改绑。
- 迁移记录只能指向能独立复验来源的已有快照。
- 旧数据如果确实没有封存原始字节，不能靠当前 `drift.json` 的内容补造过去的 generation。
- 迁移应产生新版 Candidate 或明确的修订关系，不得覆盖旧 Candidate 并假装它当初就带有代绑定。

特别是你当前两条 phantom Candidate：**先确认原始引用当时是否有合法快照**。如果没有，就应从如今可验证的真实输入重新生成新候选，而不是修改旧候选引用让它变绿。

### 4\. 修改顺序：先负例，后基础解析，再迁移消费端

### \(b) 机械判据：四处最终应出现什么读数？

#### Evidence Index

新增以下字段：

```json
{
  "evidence_id": "<evidence-id>",
  "reference_kind": "pinned_evidence",
  "artifact_id": "mirror-drift",
  "generation_id": "gen-000001",
  "content_sha256": "<64-hex>",
  "generation_manifest_sha256": "<64-hex>",
  "snapshot_ref": "<immutable-snapshot-ref>",
  "lifecycle_contract_sha256": "<64-hex>",
  "integrity": "VERIFIED"
}
```

目标：

```text
unbound_mutable_evidence_count = 0
snapshot_hash_mismatch_count = 0
generation_manifest_mismatch_count = 0
silent_rebinding_count = 0
```

其中 `unbound_mutable_evidence_count=0` 指进入正式历史证据索引的受管项目。未进入证据链的临时 live observation 不必伪装成历史快照。

#### Gate35/36

建议输出两个正交检查结果：

```json
{
  "historical_integrity": "GREEN",
  "current_freshness": "NOT_APPLICABLE",
  "other_gate_checks": "<computed>",
  "overall": "<computed>"
}
```

判定方式：

| 情形 | 历史完整性 | 当前新鲜度 |
|--------|--------|--------|
| 已绑定 gen-000001，快照完整，今日已有新代 | GREEN | 若用于当前状态，需另判是否过期 |
| 旧 URI 没有绑定任何可验证历史代 | RED 或 UNKNOWN，按缺失/无法证明原因区分 | 不可推导 |
| 快照字节被篡改 | RED | 不可推导 |
| gen-000001 完整，但当成今日最新健康状态 | GREEN | RED |
| 新代产生且旧引用保持 gen-000001 | GREEN | 当前状态由最新代另判 |

Gate35 和 Gate36 的最终状态仍须执行原有完整断言。没有原始谓词清单，不应该承诺它们一定同时变 GREEN。

#### Gate37 / Candidate 引用

最低要求：

```text
candidate.evidence_ref 是显式 pinned reference
AND pinned snapshot 可读取
AND source manifest/hash 可核对
AND candidate 来源链绑定确切输入
AND 提案资格闸与授权闸均通过
⇒ 对应候选证据子闸 GREEN
```

如果引用迁移缺少来源依据，即使最新索引完全正常，旧 Candidate 也不得因此变绿。

#### 四处读数验收矩阵

| 子系统 | 成功验收的核心读数 | 禁止出现 |
|--------|--------|--------|
| Evidence Index | 正式活水证据未固定引用为 0，快照完整性错误为 0 | 旧 evidence\_id 自动指向最新代 |
| Gate35 | 生命周期相关 reason code 消失，其他断言仍独立运行 | 缺快照也因契约声明而 PASS |
| Gate36 | 历史完整与当前新鲜度分离 | 用旧快照证明当前状态 |
| Gate32/37/候选 | 新候选消费真实 pinned evidence；旧失败保留原 verdict | 重新构建索引后旧 Candidate 自动 GREEN |

#### 最有价值的跨代负例

用真实代的隔离副本或受控验收路径执行：

```text
初始：
  ref_A → gen-000001 → hash_A

下一次合法探针覆盖：
  latest → gen-000002 → hash_B

必须仍然满足：
  ref_A → gen-000001 → hash_A
```

断言：

```text
resolve(ref_A).generation_id == gen-000001
AND sha256(resolve(ref_A).bytes) == hash_A
AND latest_generation_id == gen-000002
AND ref_A != latest_reference
```

如果解析后的旧引用悄悄指向 `gen-000002`，立即 RED，即使 `hash_B` 本身完全有效。

## Q3｜L1 修复队列：现在就建，但不要让队列成为另一份自记真源

### \(a) 裁定

### \(b) P0/P1/P2 在本机怎么落？

这里需要明确推回你一个可能的推断：

**“两条新 L1 与 Gate32 的 phantom 同时出现”不等于已经证明这两条 L1 分别就是那两个 Candidate 的来源。**

你给出了数量和时间关联，但没有给出 22 条 L1 的具体 ID 与 Candidate `source_l1_id` 映射。

所以我不能诚实地直接列出哪几条具体 ID 是 P0。

正确做法是让修复队列生成器从盘上做精确关联。

#### 归类规则

| 优先级 | 机械条件 | 动作 |
|--------|--------|--------|
| P0 | 当前活动的 Candidate、Proposal、distill 或正式写入流程引用了该 L1 的确切 ID/hash，且该 L1 存在 writer gate 硬缺陷 | 立即维持阻断，优先修复授权 |
| P1 | L1 关联仍开放的真实 Demand/Task，但目前没有活动下游消费 | 进入有期限的修复队列 |
| P2 | L1 仅有历史引用，且已证明没有活动下游消费 | 保留历史欠账，允许有审批的延期 |
| UNDETERMINED | 缺少足够索引信息，不能确认有无当前消费者 | 不得自动降到 P2；保持受影响写入阻断 |

P0 不应仅靠文件创建时间决定，也不能因为一个 L1 缺陷影响很多历史记录，就自动认定它正在被生产流程消费。

#### 具体如何从本机重算

建议新增：

`runners/build-l1-repair-queue.mjs`

它至少读取：

| 输入 | 用途 |
|--------|--------|
| L1 writer gate 全量结果 | 枚举 22 条 `NEEDS_REPAIR` 的真实 ID/hash |
| `generated/learning/l1-triage.json` | 找出已进入 triage 的 L1 |
| 当前 Candidate 产物 | 找出 L1→Candidate 关联 |
| `generated/learning/skill-proposals.json` | 找出仍有效的提案消费链 |
| distill 当前运行收据与 `distill-blocked.json` | 找出被阻断的 L1→L2/L3 路径 |
| 活动 Task/Demand 索引 | 确认尚开放的真实需求 |
| 已批准的授权记录 | 确认是否存在可复验的补救依据 |

必须按 `l1_id + source_sha256` 关联。

不能只靠 basename、最近修改时间或文字相似度把不同 L1 认成同一来源。

推荐生成一张消费关系矩阵：

| L1 | Candidate 消费 | Distill 消费 | 活动 Demand | 优先级 |
|--------|--------|--------|--------|--------|
| 精确 L1 ID A | 有可验证引用 | 无 | 有 | P0 |
| 精确 L1 ID B | 无 | 有可验证引用 | 有 | P0 |
| 精确 L1 ID C | 无 | 无 | 有 | P1 |
| 精确 L1 ID D | 无 | 无 | 无，且历史归档完整 | P2 |
| 来源关联不足 | 未知 | 未知 | 未知 | UNDETERMINED |

这张表是机械规则示例，不是对你本机 A/B/C/D 的事实判断。

尤其是 R10 新增的两条 L1，应该**优先检查其与当前两个 phantom Candidate 的精确引用关系**。若匹配，就是 P0；若不匹配，不能强行配对。

这里还要保留两层独立的失败：

```text
L1 intent 缺失
⇒ L1_WRITER_NOT_AUTHORIZED

Candidate drift evidence 失效
⇒ CANDIDATE_EVIDENCE_UNRESOLVED
```

修复 Evidence 代绑定，可能解除第二个错误，但不能自动解除第一个。

### 1\. lifecycle 契约同日发布、Gate38 绿，但跨代尚未验证：必须单列中间态

**是，应该单独记账。**

但不要因此否认已经取得的成果。

|--------|--------|

| lifecycle schema | 已有机器可读契约 |
| 探针写入改造 | 已有两个写入点的覆盖前留档实现 |
| 快照读取 | 已成功产生 gen-000001 |
| Gate38 | 当前单代真实产物 PASS，沙盒负例通过 |
| 实际覆盖后旧代稳定性 | 尚无真实双代验证 |
| 历史证据跨代消费 | 尚无真正的引用方实证 |

建议在统一总账新增：

```json
{
  "obligation_id": "R10-LIFECYCLE-CROSS-GENERATION",
  "implementation": "IMPLEMENTED",
  "verification": "UNKNOWN",
  "reason_code": "CROSS_GENERATION_NOT_VERIFIED",
  "required_witness": [
    "real_generation_1",
    "real_generation_2",
    "pinned_reference_to_generation_1",
    "resolution_after_generation_2"
  ]
}
```

这不意味着 Gate38 应该被改回 RED。

正确读数可以是：

```text
Gate38 当前已实施的检查       GREEN
跨代引用验收                 UNKNOWN
lifecycle 完整端到端能力     NOT_VERIFIED
```

如果 Gate38 的官方职责已经宣称包含完整跨代验证，那么它的 GREEN 判据也必须相应扩展。

**契约存在、生产者已接入和消费者真实验证，是三个不同的里程碑。**

尤其不能拿五个沙盒判例加一个 gen-000001，代替一次真实探针覆盖后的旧引用解析。

### 2\. Gate37 的 observation 分类确实可能被滥用

**必须为 observation 建立独立资格门槛，但不应强迫 observation 提出契约修改。**

观察记录也应该具有足够的实质内容。

最低字段建议：

```yaml
proposal_kind: observation

observation:
  claim: "<specific-observed-fact>"
  subject_ref: "<subject>"
  observed_at: "<UTC-time>"
  source_refs:
    - "<pinned-evidence-ref>"
  scope: "<observation-scope>"
  evidence_limitations: "<limitations>"

normative_change:
  requested: false
  change_operations: []

allowed_destination: learning_observations
```

最重要的两条硬约束：

```text
proposal_kind = observation
AND change_operations 非空
⇒ CONTRACT_ELIGIBILITY_RED
```

```text
proposal_kind = observation
AND 尝试直接发布为有效权威契约
⇒ UNAUTHORIZED_CONTRACT_PUBLICATION
```

不过 observation 可以引用某个现有契约作为被观察对象，不能仅仅因为提到了契约名字就判成 contract change。

建议 Gate37 同时校验：

- 内容有明确观察对象、时间、范围与具体主张；
- Evidence 可验证；
- 没有请求权威规则自动变更；
- 目的地符合观察类的存储与消费权限；
- 不存在通过 observation 身份执行 contract-change 专属副作用。

如果文本实际提出“应新增某个硬闸”，却故意标成 observation，在不做语义人工审核的情况下，程序未必能可靠理解全部自然语言含义。

因此应把**产物请求的实际副作用**作为最后的机械边界：无论声称什么 `proposal_kind`，凡是请求改变规范或激活规则的写入动作，必须经过 contract-change 审批。

这比用正则搜索“必须”“应当”等字眼可靠得多。

对于已被重新分类为 observation 的首例，可以保留其历史批准、纠正链和观察证据，但不再算作合格契约修订案例。

### 3\. 19 条 done\_when 会话内逐条过目、整体拍板，算不算授权评审？

**形式上算。前提是批准者确有相应权限，而且批准对象的确切版本可追溯。**

不需要强迫批准者对每一条 CT 分别签 19 次。

但“整体拍板”必须是对一个冻结的、可复验的内容集合拍板，而不是只批准一句“这些看起来都对”。

建议归档：

`machine/approvals/ct-done-when-19.json`

```json

  "approval_id": "<approval-id>",
  "decision_kind": "TASK_DONE_WHEN_BULK_APPROVAL",
  "approved_by": "<authorized-actor>",
```

```text
AND 批准引用可复验
```

这里要警惕 R6 已经指出的自记问题：

`acceptance_source=human_decision` 是一个事件分类字段，不自动构成独立的人审证明。
