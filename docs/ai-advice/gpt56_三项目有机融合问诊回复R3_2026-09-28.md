Q1. Skill 与自动化流程的边界
裁定：反对把 适用范围 当作唯一分类判据。保留它，但只用于限制适用边界。
“全局”不等于可复用方法；全局定时流程仍然是流程。反过来，某个子项目中发现的方法，也可能经过参数化成为通用 skill。把这两个维度合并，会同时造成误收和漏收。
机械化替代判据是让写者显式声明结构化的产物意图和固定运行绑定，而不是让提炼器从自由文本中猜。声明为方法、且不存在不可替换的项目运行绑定，才进入 skill 草稿候选；声明为自动化、或必须依赖特定项目运行绑定，进入流程局部候选。无法确定的保留未判，不默认归入任一类。
这里必须承认一个限制：机器可以验证声明是否合法、绑定是否存在，却不能仅凭字段证明作者的声明正确。两类产物也并非天然互斥，流程可以调用 skill。
等信号： 13 条样本不足以证明分类准确，更不能估计误判率。必须等到出现真实的跨场景复用、固定绑定导致的失败，以及局部方法成功迁移的执行记录，才决定自动晋升和更细的分类规则。
判错后果是把一次性流程包装成通用 skill，或把可复用方法锁死在项目契约里。本轮最多自动生成候选草稿，不把候选身份等同于复用已经成立。
Q2. 类型 的单值约束
裁定：禁止多值，由写者规范闸门当场拒绝；不扩展值域，不交给提炼器裁定。

对于 workaround / pitfall，不自动拆分，也不规定一个全局优先级。两者描述的是不同信息维度，不是已经被证明存在优先关系的竞争标签。作者必须决定这条记录的主类型；确实需要分别表达时，应由作者形成独立的合格记录，而不是让机器偷偷拆出两份经验。
历史上的五条不合格类型记录保持原始字节，标为待修复，不回填推测结果。
这个问题不必等信号。单值是当前明确契约，已有实际违规输入。现在放宽它，会让后续类型统计、提炼和追溯的含义漂移；让提炼器猜，则会把数据契约错误伪装成模型能力。
Q3. frozen 与冻结 Schema
裁定：frozen 不应塞入 Task 生命周期。它是与生命周期正交的冻结治理属性。
但我不接受通过这个裁定直接宣布 Gate 33 转绿。
机械表达应当分成两个互不替代的事实：Task 的生命周期字段只能接收冻结 Schema 已允许的值；原始看板的冻结状态由 spec_binding.yaml 中的绑定元数据保留，至少记录冻结标记、来源任务行和原始状态词头。绑定校验负责确认来源确实存在且状态一致。
这里必须正面回答 Schema 问题：如果冻结 Schema 本身没有可合法容纳冻结属性的位置，就无法在该 Schema 内新增第三态，同时又声称 Schema 未变。 可行的是在冻结 Schema 外的绑定层表达并校验，不能冒充 Task Schema 已经支持它。
因此：
frozen 不能自动写成 completed、blocked 或 cancelled；同样不能因为看板写了 todo 就默默制造 queued。只有独立、明确、可追溯的合法生命周期值，才能填入相应字段。
如果来源只提供冻结状态、没有合法生命周期事实，对应实例仍应红。以后若确实需要冻结状态成为正式 Task 字段，再通过明确的 Schema 版本迁移解决，而不是这轮暗改 30_。
判错后果是冻结任务被误认为完成、阻塞或取消，进而污染任务统计和自动调度。现阶段保留红灯，比伪造一个合法枚举更正确。

Q4. State 的 phase 从哪里来
裁定：必须来自 State 所描述流程的真实阶段，不允许从 demand 生命周期直接猜测。
机械判定：State 生成器必须读取有明确所有权的阶段来源，且产出的 phase 属于冻结 Schema 允许的值域。next_step 只能说明下一步动作，不等于当前阶段。
只有当 demand 生命周期与 phase 存在已明确授权、无歧义的对应关系时，才允许确定性推导。否则不能因为 demand 处于某个状态，就假定流程也处于某个阶段。
取不到必须红，不允许缺省。 当前四份 State 应保持不合格，直到生成器能取得真实阶段。
