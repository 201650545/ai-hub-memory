结论

这轮方向总体对，但我会推翻两个当前设计点。

第一，test_gate.verdict(cid, model, caller) 不应该继续扩张成“能不能测 / 该不该测 / 测了说明什么”的万能函数。应该统一到同一个测试策略模块，但拆成三个独立判定层：authorize_probe() 只回答“允许不允许”；schedule_probe() 回答“现在该不该测”；classify_result() 回答“这次结果证明了什么”。否则额度、TTL、失败语义会逐渐塞进一个越来越不可测试的 verdict()。

第二，OpenRouter 新免费模型自动写进编排必须撤掉。证据文件一方面明确规定“席位增删/替换必须人拍板，唯一自动例外是已有免费席出现非 0 费用时摘除”，另一方面当前 or_free_refresh 又会筛完后直接改编排。两者是硬冲突，不是实现细节。自动发现可以，自动提出候选可以，自动新增席位不可以。

对你四个具体问题，我的裁定是：

caller 三分不够，而且 caller 本身抽象错了一层。 现在 (cid, model) 已经无法唯一表示一个“席位身份”，你自己遇到的 zscc 双档就是证明。不要再通过“这个 cid/model 出现在哪些链”倒推身份。闸门输入必须带稳定的 seat_id + route_id/tier + intent。health 也过于含糊，本机 /healthz、外部渠道健康探测、写后验证不是同一种意图。当前从“仅当档集合恰为 {paid-fast} 才拦”来补洞，只是继续依赖反向推断，应该废掉。
github.com

优先级建议确实以硬资金红线开头，但不是简单的“资金风险 → 存在性 → 容量”，而是：

绝对禁止规则 → 身份/存在性解析 → 席位探测资格 → 调度状态 → probe 自身预算。

其中五个付费渠道、paid-fast、sealed 都属于第一层，无条件 fail closed；unknown_channel 属于第二层；某个明确免费席是否可测属于第三层。

生产额度警戒不要进入测试闸。 当前实时余额、生产日额度、并发饱和、生产 rate-limit/circuit breaker、用户请求预算，都应该继续属于 runtime admission/routing。测试体系只能有自己的 probe_budget。否则一次测试预算耗尽可能被错误解释为“模型不可用”，或者生产额度变化反过来污染探针结论。

streak 与 TTL 不要共用状态机。 可以共用事件存储和 seat_id，但必须是两套派生状态。streak 是“观测结果状态”；TTL/长期零流量是“何时需要重新取证的调度状态”。两者生命周期和重置条件完全不同。

另外，当前“已不在编排 或探针不再覆盖 就删孤儿键”的后一半我会直接否掉。探针不再覆盖 ≠ 席位不存在。 应该改成 inactive_reason=not_probed，保留历史；只有稳定席位 ID 已从经过完整校验的 canonical inventory 消失，才进入 tombstone/GC。你这次 9 个孤儿清理本身有证据支撑，但把“coverage 变化”作为通用删除规则，未来一定会误删。
github.com

更优方案

我建议把现在的 test_gate 升级成一个 probe_policy，但不要做成大函数。逻辑上是这样：

canonical seat
    │
    ├── authorize_probe(ctx)     # 能不能测
    │     └── PolicyDecision(ALLOW/DENY, code, evidence)
    │
    ├── schedule_probe(ctx,state)# 该不该现在测
    │     └── DueDecision(DUE/NOT_DUE/DEFERRED, reason)
    │
    └── classify_result(ctx,res) # 测了说明什么
          └── Observation(class, severity, evidence)

核心身份从：

(cid, model, caller)

改成至少：

seat_id
cid
model
route_id
tier
intent
probe_spec_version

intent 可以先有 DAILY_MEMBER / MANUAL_CONSOLE / WRITE_VERIFY / TTL_REVERIFY，以后加 shadow 不需要再次扭曲 caller。

尤其“测了说明什么”必须做强类型化。你现在的两个连续 6 天失败都是 429，这只能证明该时间窗口、该身份、该请求路径下拿不到容量，不能证明模型不存在，也不能和 404 混成同一种“FAIL streak”。证据文件本身也明确记录它们是上游 429。
github.com

至少应拆：

OK
RATE_LIMITED       # 429
MODEL_NOT_FOUND    # 404/明确不存在
AUTH_OR_POLICY     # 401/403
CONTRACT_ERROR     # 400/响应结构不兼容
UPSTREAM_ERROR     # 5xx
TRANSPORT_ERROR    # timeout/DNS/proxy
LOCAL_POLICY_SKIP
NOT_DUE

因此将来自动“提出席位替换建议”不能只看 fail_streak >= N。例如连续六天 429 可以提出“降权/暂停/人工复核容量”的建议，但不应生成“模型死亡，建议删除”这种结论。

routes_writer 也建议再加一道授权边界。它现在解决了“怎么安全写”，还没有机械保证“谁允许写什么”。应让自动调用只允许：

AUTO_SAFETY_REMOVE
  AND provider == openrouter
  AND seat currently in free route
  AND evidence == NONZERO_PRICE
  AND operation == REMOVE

任何 ADD / REPLACE / 普通 REMOVE 都要求 approval_id 或明确 human actor。这样“必须人拍板”不是文档约束，而是代码不变量。

最后，routes_writer 的写后验证不能只满足 /healthz == 200。mtime 热加载下存在一个明显竞态：文件已替换，但 healthz 可能仍在验证旧的内存编排。建议 runtime 暴露 loaded_routes_sha256 或 generation；writer 原子替换后要求：

healthz == healthy
AND loaded_routes_sha256 == expected_sha256

否则回滚。这样才能真正证明“新编排被加载且健康”，不是“进程还活着”。

风险

目前我认为有五个值得在终态前消掉的风险。

最高优先级：OpenRouter 自动新增违反你自己的硬约束。 这会让“证据自动提出、人拍板执行”的最终治理模型失真。现有自动新增必须改为 proposal；自动摘除非零价格可以保留。
github.com

席位身份仍不稳定。 (cid, model) 在多链复用时天然有歧义。这正是 paid/free 双档问题的根，而不是 paid_chain 判定条件写错这么简单。

一个 fail streak 会过度压缩语义。 429、404、401、400、timeout 连续六天代表完全不同的问题；如果后面让自动系统基于 streak 出建议，它会产生错误治理动作。

孤儿 GC 有误删历史的风险。 route rename、临时撤下、probe coverage 改动、inventory 加载失败、同 cid/model 多席，都可能造成假 orphan。尤其不要在 canonical config 加载异常时执行任何 GC。

“原子写文件”不等于“原子切换运行状态”。 当前证据已经证明 routes_writer 的 apply/reject/rollback 分支工作，但如果 healthz 不确认 loaded revision，仍有旧配置通过检查的窗口。
github.com

另外 _test_console 第二次重复踩“私有字段泄漏上游”说明一个更底层的问题：不要继续维护参数黑名单。 应反过来构造 upstream payload allowlist，或者先统一剥离所有 gateway-private namespace。例如所有内部字段统一改成 _gw_*，进入 adapter 前一次性移除 _gw_ 前缀字段。你已经连续两次证明 blacklist 模式会漏。
