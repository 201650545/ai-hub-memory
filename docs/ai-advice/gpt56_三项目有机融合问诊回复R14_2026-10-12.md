# R14 裁定：阶段封板可以，验收闭合尚不可；最后一红必须回到写入责任链

原因不是单纯的“13 绿 1 红”，而是本轮回执仍存在三项不同性质的验收缺口：

1. **提炼演习仍 RED**：`DRAFT_LINEAGE_STALE` 尚未解除，不能因修复队列接管就视为已修复。

3. **学习链 pinned evidence 尚无完整消费案例**：跨代解析、候选生成和人工审批必须由同一条因果链连接，不能拼接不同运行的成功结果。

# Q2｜剩余一红：DRAFT\_LINEAGE\_STALE 应由谁修？

## \(a) 裁定：责任在源头，队列负责治理，不替写入者背锅

**明确裁定：写入会话承担自己所产生 L1 的修复责任；修复队列负责统一分派、阻断、追踪和升级；授权批准者保留意图分类的最终裁决权。**

不能把这三种责任混成一个“修复队列会处理”。

| 角色 | 必须承担的责任 |
|--------|--------|
| L1 写入会话 | 对本次生产的 L1、来源引用、产物意图及拒收原因负责；收到失败后提出修复 |
| `l1-intake.mjs` | 在正式写入前校验，不合格写入隔离区并生成可关联拒收收据 |
| `build-l1-repair-queue.mjs` | 汇总历史/活动欠账，建立生产者与消费者关联，计算 P0/P1/P2 |
| 工作流调度入口 | 下一次运行前读取与当前任务有关的未解决反馈 |
| 授权者 | 批准缺失的意图分类或其他不能由生产者自宣的授权事实 |
| distill runner | 复验精确 L1 版本、授权与来源链；失败时保持写入阻断 |

这里有一个必须正视的变化：

R14 已新增 `l1-intake.mjs`，不合格 L1 理应先进入 `L1_隔离/`。

但你报告不合格条数继续从 27 增至 30。

这不一定表示入口约束失效，却必须查清增长构成：

- 是此前存在、最近才被 sweep 扫到的历史 L1？
- 是新写入但已经被隔离的 L1？
- 还是另一会话绕过 intake，直接写进正式 `L1_经验/`？

这三种情况的治理性质完全不同。

**如果第三种仍在发生，不能称跨会话写入边界已真正闭合。**

### 1\. 跨会话反馈闭环：拒收即产生任务可见的反馈

建议每次 intake 拒收生成：

`runtime/l1-intake-rejections/<attempt_id>.json`

最低字段：

```json
{
  "schema_version": 1,
  "attempt_id": "<unique-id>",
  "writer_session_id": "<session-id>",
  "writer_run_id": "<run-id>",
  "task_ref": "<source-task>",
  "source_l1_id": "<l1-id>",
  "source_sha256": "<64-hex>",
  "intended_destination": "L1_经验/",
  "actual_destination": "L1_隔离/",
  "decision": "QUARANTINED",
  "reason_codes": [
    "INTENT_DECLARATION_MISSING"
  ],
  "feedback": {
    "owner_ref": "<responsible-owner>",
    "status": "OPEN",
    "ack_ref": null
  }
}
```

`writer_session_id` 和 `owner_ref` 必须来自真实的任务分派或写入身份记录。如果无法确定责任者，应记为 `OWNER_UNKNOWN` 并升级，而不是由修复队列按文件名猜测。

**必须直接把拒收结果返回给写入调用方**，同时留下盘上收据。只在次日巡检报告里出现，不算即时反馈。

### 2\. 下一次运行时，要不要先查修复队列？

**要，但应查与当前执行身份和任务有关的未解决项，不应因为全库有 30 条历史缺陷，就冻结其它无关工作。**

建议在每个 Agent 工作流入口添加：

`runners/l1-preflight.mjs`

检查：

```text
当前 writer 身份
当前 Task/Demand
当前 L1 来源范围
当前 downstream invocation
```

只要存在与本次执行相关的 P0 未解决项，就在正式产物生成前拒绝相关动作。

推荐状态：

| 反馈状态 | 含义 | 允许行为 |
|--------|--------|--------|
| `OPEN` | 已发现失败，未确认接收 | 不得继续提交受影响正式产物 |
| `ACKNOWLEDGED` | 写入者已读取并确认问题 | 可准备修复，不代表已经授权 |
| `AWAITING_APPROVAL` | 修复内容已准备，但仍缺独立审批 | 不允许解除源头闸门 |
| `REVERIFY_REQUIRED` | 获批后等待 writer gate、triage、distill 重验 | 仅允许校验 |
| `VERIFIED` | 当前确切 L1 版本经复验合格 | 可按下游契约继续 |
| `SUPERSEDED` | 旧 L1 被明确退役或替代 | 旧引用不得自动重定向到新版本 |

`ACKNOWLEDGED` 不得被误当 `VERIFIED`。

这里也无需每个会话进行一次新的人工确认。允许会话内已有获授权的意图记录被机械复用，只要它准确绑定当前 L1 内容及产物类型。

### 3\. 修复队列不能制造重复修复

如果某条 L1 被三个下游消费，不能由三个消费方分别为它补交三个互不相关的授权声明。

建议以：

`l1_id + source_sha256 + reason_code`

建立稳定缺陷身份。

再分别关联多个 `consumer_ref`。

一条来源缺陷可以有多个受阻动作，但源头修复应该对应明确的版本和授权范围。

### 4\. DRAFT\_LINEAGE\_STALE 必须区分原因，但不能自动降级成 PASS

我同意你关于“合法覆盖不等于证据篡改”的质疑。

但还要推回去半步：

**旧草稿引用旧 L1，不一定表示旧草稿无效；同样也不一定表示旧草稿可以继续参与当前提炼。**

需要把原因和当前使用资格拆开。

建议至少定义：

| 原因码 | 含义 | 当前草稿 |
|--------|--------|--------|
| `SOURCE_REVISION_ADVANCED` | 来源已有新版本，旧版仍可读取且当时合法 | 重新验证适用性 |
| `SOURCE_VERSION_MISSING` | 旧版来源字节无法取得 | 阻断当前正式使用 |
| `SOURCE_AUTHORIZATION_CHANGED` | 旧版授权不再覆盖当前用途 | 阻断 |
| `UNAUTHORIZED_SOURCE_MUTATION` | 来源未经授权发生变更 | RED，并触发治理调查 |
| `DRAFT_SOURCE_HASH_MISMATCH` | 草稿声明的来源与实际引用字节不一致 | RED |
| `CURRENT_LINEAGE_STALE` | 当前演习要求最新来源，而草稿没有满足 | 当前演习 RED |

不能仅凭发生了 hash 变化，就推断恶意篡改。

但也不能因为变化属于正常业务演进，就让旧草稿直接进入生产。

#### 推荐旧草稿处理规则

**旧草稿 D 引用 L1\@H1**

**当前 L1 = H2，H2 与 H1 不一致**

**H1 可验证且授权有效**

保留旧草稿作为历史版本；若要当前使用，重新裁定适用范围。

**H1 缺失或授权无效**

旧草稿不能获得当前使用资格；需要从合法输入重新生成。

对于明确被替代、且不再属于活动提炼输入范围的历史草稿，可以经受控退役流程退出**当前演习集合**。

但不得为了让 Gate 变绿，直接修改扫描 glob、删除失败台账或把旧草稿改名隐藏。

应该留下：

`DRAFT_SUPERSEDED`

并记录：

`old_draft_ref`、`old_source_sha256`、`replacement_ref`、`retirement_approval_ref`、`active_set_before_sha256`、`active_set_after_sha256`。

之后总闸可以根据真实活动集合重新裁定，但历史失败仍应可重现。

# 三项顺手追问的裁定

## 1\. 基线文件还叫“迁移前”，是否应该改名？

**裁定：应该修正展示层命名，但不应直接重命名已经被历史收据引用的基线文件。**

“迁移前”是历史语义。

如果今天的活动基线实际冻结的是 R12 之后的受管工作树，那么继续在人类看板上把它称作“迁移前基线”，确实会引起误读。

但原始基线文件是有 hash 和引用链的审计产物。直接改文件名可能破坏既有引用。

建议使用版本化元数据：

```yaml
baseline_id: fusion-baseline-r14
display_name: R14 已批准融合基线
lifecycle_status: active

captured_from:
  commit: "<exact-commit>"
  tree_sha: "<tree>"

supersedes:
  baseline_id: fusion-pre-migration
  baseline_sha256: "<original-hash>"

approval_ref: "<approved-transition>"
```

建议：

- 保留旧 `fusion_pre_migration.tsv` 的原始字节。
- 新基线使用准确的版本身份。
- 旧路径继续作为历史审计对象，而不是被重解释为当前基线。
- 由受控的活动基线指针决定当前验证器读取哪一版。
- 如需修改展示名称，仅改人类阅读投影和已批准的元数据。

机械负例：

```text
修改旧基线字节
OR 新基线覆盖旧 ID
OR 活动指针指向未经批准的版本
⇒ BASELINE_TRANSITION_RED
```

不能为了修正文字，把首次 GREEN 的历史证明链破坏掉。

## 2\. DRAFT\_LINEAGE\_STALE 是否应区分合法演进与证据篡改？

**应该，而且这是 R14 最有价值的语义完善之一。**

但是仍需区分：

- 变化原因是否正当；
- 旧草稿是否历史有效；
- 旧草稿是否可以继续当前生产。

这三个问题不能由一个 `STALE` 代答。

建议在诊断层细分原因，同时保持生产闸门 fail-closed。

```json
{
  "draft_ref": "<draft>",
  "source_l1_ref": "<l1>",
  "draft_source_sha256": "<old-hash>",
  "current_source_sha256": "<new-hash>",
  "lineage_reason": "SOURCE_REVISION_ADVANCED",
  "historical_integrity": "VERIFIED",
  "current_eligibility": "BLOCKED"
}
```

对于合法的来源修订，即使旧内容存在并可验证，也不能自动替代当前来源。

如果当前 distill 要求消费最新获授权 L1，则旧草稿应经过重新生成或明确的历史版本适用性审批。

**建议 Gate 不再把所有 STALE 都描述为损坏或篡改；但任何仍处于活动集合的未解决 STALE，都不能被默认为 PASS。**

## 3\. done\_when 已写在 note 中却漏填正式字段：要的就是“没填就拒收”吗？

**是，但准确地说，是“正式字段没填，就不允许进入正式权威入口”。**

五次、随后第六次灯下黑，说明 note 并不是可靠的完成标准承载位置。

必须明确：

```text
note 包含完成条件
AND done_when 正式字段缺失
⇒ CT_REGISTRATION_REJECT
```

不能：

```text
note 有相关文字
⇒ 自动抽取为 done_when
⇒ 默认合格
```

如果确实希望保留 note 中的草稿文字，可以在登记工具里提示用户将其明确确认并填写到 `done_when`。

但必须由有权限的提交者确认正式字段，注册器不应代替其完成授权表达。

最终是两道不同的闸：

```text
done_when 缺失
⇒ 结构性拒收

done_when 存在但占位或无验收依据
⇒ 内容资格拒收
```

只有二者都通过，才允许正式登记。

R14 的 `register-ct.mjs` 已在设计上覆盖这两层。剩余问题是实际生产路径是否强制使用它，以及绕过工具直接修改文件是否被发布闸门阻断。

**这一点需要真实验收，不需要再发明一个新的登记概念。**
