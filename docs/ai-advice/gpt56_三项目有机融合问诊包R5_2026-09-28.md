## Q1 闸门报 FAIL 时，这一轮还允不允许产出新草稿？

**我做了什么（需要你判它对不对）**：旧草稿血缘不成立时，提炼器仍然把新的合格候选写成草稿，只在收尾打 `GATE|DISTILL|FAIL|reason=DRAFT_LINEAGE_STALE` 并以 exit=1 结束。我的理由是：草稿落「草稿区」不改变任何 Agent 的真实行为，用历史未处理去冻结新增，等于让闭环只记账不出货。

**风险我自己看到两条**：(a) 一个闸门「既报红又照样产出」，读数上 exit=1 但产物在增加，容易掩盖「本该停下来清历史」的信号；(b) 如果红不产生物质后果，久了人会习惯忽略这条红。

**请给**：
1. 裁定：这个边界成立还是不成立。
2. 可编码判据：什么条件下 FAIL 仍允许写新草稿，什么条件下必须整轮拒绝、一条都不写。判据要能用「本轮已有的东西」算出来，不能依赖人临时判断。
3. 这条判据该不该同样适用于证据环（Gate 35/36 报红时是否允许重建索引/快照），还是两个环的规则应当不同——如果不同， differing 的根据是什么。

## Q2 装第一条真 skill 之前，最小「生效」判据是什么？

**现状**：S3 要装第一条自产 skill 进运行时目录（需人工点头，我没有自装）。但机器上已经有反例：一条已安装的自产 skill 缺顶层 `SKILL.md`，**装着、永不触发**，账面还是「已安装」。另外 skill 级探针（问「这条方法今天还成立吗」的那个）还没建。

**请给**：
1. 「装上且生效」的机械验收清单——必须是可由脚本一次跑完、能判红绿的检查项，不接受「人工确认一下」。请说明每一项拦住的是哪类失败（例如：文件不存在／目录嵌套错层／front matter 关键字段缺失／触发词根本没注册／装了但没有任何调用记录）。
2. 探针还没建的情况下，允不允许先装？如果允许，装完之后到探针就位之间，用什么临时判据防止它变成「装了没人管」；如果不允许，那探针本身又该由谁触发创建（避免死锁：探针要求 skill 存在、skill 要求探针存在）。
3. 「已安装」这个状态该由谁写、凭什么证据写。我们现在的写法是真源 README 的一列由人手维护，实测已经和盘上不一致。
