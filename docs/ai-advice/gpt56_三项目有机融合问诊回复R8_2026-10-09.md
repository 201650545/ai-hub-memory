# R8 裁定：漂移产物生命周期、Gate33 数据通路与基线重拍

**总裁定：R7 的三项交付取得了实质进展，但 R8 暴露出一个更深的问题：系统已经能证明“某个产物在某个时点存在”，却还没有统一规定“这个证明能在多长时间内、对什么主张有效”。**

这次不应靠重建索引、补填 `done_when` 或重拍基线来追求表面全绿。三个问题要分别处理：

| 问题 | 裁定 | 当前状态 |
|--------|--------|--------|
| Q1：artifact\_lifecycle | 建立授权的产物生命周期契约，将历史证据有效性与当前新鲜度分离 | 生命周期契约缺失，相关阻断继续 RED |
| Q2：Gate33 done\_when | **选方案②**：CT 行在权威 `TASKS.yaml` 声明，统一 Task Index 透传，adapter 从索引消费 | 34 条违规须逐条消除 |
| Q3：基线重拍 | **两阶段收口**：先确认已提交变更的差异清单，未提交域继续挂账；最后一次正式重拍 | BS\_DRIFT 继续 RED，不提前洗绿 |

另外，本轮需要对首例 contract approval 作出一个不太舒服但必要的判断：

**“证据可追溯 + 来源合法”是提案的入场资格，不是“值得成为契约”的充分条件。首例只有 drift 观察记录、没有规范性修改内容，就不应该计入已验证的契约提案批准案例。**

这不意味着必须删除该记录，也不抹消已经发生的人审决定。但应将其从“合格契约动议”重新分类，并修复 Gate37 的验收规则。

以下裁定以你给出的控制平面实测情况为依据。我没有直接访问 `D:\Work\元智能\` 的工作树，因此区分“包中已证实的现状”和“建议新增、尚待实跑的机械判据”。

## Q1｜漂移活水的 artifact\_lifecycle：谁能声明、怎么封存、如何判绿？

### \(a) 裁定

(禁止无授权的自动滚动追认)

你看到的两条风险都成立。

尤其是这一种实现绝对不能接受：

```text
drift.json 内容变化
    ↓
重建 evidence.json
    ↓
新 SHA-256 覆盖旧登记
    ↓
Gate35/36 自动 GREEN
```

这条链的实际含义是：**生产者每次覆盖证据，索引就替它重新定义什么叫正确证据。**

它不是证据验证，而是移动验收基准。

### 1\. artifact\_lifecycle 的授权归属

建议设立：

`machine/contracts/artifact-lifecycle.yaml`

并把它纳入现有所有权契约和 `fusion-check` 的强制依赖。

权力分离如下：

| 角色 | 可以做什么 | 不可以做什么 |
|--------|--------|--------|
| 产物生产者（探针、生成器） | 写入产物、生成摘要与运行收据、提出生命周期需求 | 自批生命周期类型、保留期限、证据豁免 |
| 规则提案者 | 提交 lifecycle proposal 及理由、测试和影响清单 | 直接修改生效契约 |
| 契约批准者 | 审核并批准路径范围、版本规则、保留策略 | 用口头解释替代可复验的契约 |
| 契约发布器 | 按批准的内容写入 `machine/contracts/` | 擅自扩大已批准范围 |
| Gate35/36/索引构建器 | 读取契约并机械执行 | 根据当前文件特征自行推断生命周期并给绿 |

批准权应依据 DEC-16 之后控制平面的授权决策登记，而不是根据“谁能编辑 YAML”决定。

**批准后的生命周期声明同样不能追溯生效到没有证据的历史时期。**

如果此前的 `drift.json` 已经被覆盖，且没有存下当时的原始字节，今天新建生命周期契约不能让丢失的历史快照重新变得可验证。

### 2\. 建议采用三类生命周期

**A. `mutable_observation`：覆盖型探针产物**

适用于每日覆盖的 `drift.json`。当前文件代表最新一次观察，但历史引用必须绑定某一代不可变快照。新一代出现不得自动改写旧证据引用。

---

**B. `immutable_snapshot`：不可变留档产物**

适用于已批准的证据快照、裁决附件和审计基线。路径或标识一旦发布，不允许原位替换内容；修订必须产生新代及明确关联。

---

**C. `derived_projection`：可重建投影**

适用于满足确定性重建要求的 `runtime/home-projection.json` 一类产物。允许重建覆盖，但必须绑定生成器版本及输入快照；如果它被正式引用为证据，则该次内容也必须快照化。

`runtime/home-projection.json` 是否真正属于第三类，不能仅凭文件名判断。只有它实际由受约束的生成器生成、可复算，并且输入与代码版本完整记录，才能赋予 `derived_projection` 类型。

相应地：

- `drift.json`：重点是观察时间、采集来源和历史代数。
- `home-projection.json`：重点是构建输入、生成器和投影新鲜度。
- 已裁决证据：重点是原始字节封存、裁决时点与历史可验证性。

三者不应套用一个笼统的“文件可以覆盖”豁免。

### 3\. 最小 YAML 声明形态

下面是建议的新契约格式，并非声称现有仓库已支持这些字段。

```yaml
schema_version: 1
contract_id: artifact-lifecycle-v1
status: active
approval_ref: "<authorized-decision-ref>"

artifacts:
  - artifact_id: mirror-drift
    path: "<actual-path-to-drift.json>"
    producer_id: "<registered-probe-id>"
    lifecycle: mutable_observation

    generations:
      require_monotonic_sequence: true
      snapshot_before_overwrite: true
      immutable_archive: true
      manifest_required: true

    retention:
      unreferenced_min_generations: 2
      referenced_generations: until_explicit_release
      approved_evidence: preserve_with_decision

    evidence_policy:
      bind_generation_id: true
      bind_content_sha256: true
      require_archived_bytes: true
      current_freshness: separately_checked
      historical_revalidation: archived_snapshot

  - artifact_id: home-projection
    path: "runtime/home-projection.json"
    producer_id: "<registered-generator-id>"
    lifecycle: derived_projection

    build_policy:
      require_input_manifest: true
      require_generator_sha256: true
      require_output_sha256: true
      require_reproducibility_check: true

    evidence_policy:
      snapshot_if_referenced: true
      require_archived_bytes: true
      current_freshness: separately_checked
```

这里的 `unreferenced_min_generations: 2` 只是一个最低比较窗口示例，不是对整个审计保留期限的裁定。

我不建议简单定为“保留最近 N 代，超出就删”。

**凡是仍被批准决定、开放 Task、正式 Evidence 或有效审计记录引用的代，必须保留到该引用按授权程序解除。** 即使已经超过 N 代，也不能自动删除。

未被引用的普通观察代，才可以按批准的 N 代或时间窗口清理。

### 4\. 必须同时保存代数与内容

每一代最低形成一条 manifest：

```json
{
  "artifact_id": "mirror-drift",
  "generation_id": "<unique-generation-id>",
  "sequence": 42,
  "observed_at": "<UTC-time>",
  "captured_at": "<UTC-time>",
  "previous_generation_id": "<previous-id>",
  "producer_id": "<probe-id>",
  "producer_build_sha256": "<64-hex>",
  "source_snapshot_sha256": "<64-hex>",
  "content_sha256": "<64-hex>",
  "content_bytes": 1234,
  "snapshot_path": "<immutable-archive-path>",
  "lifecycle_contract_sha256": "<64-hex>"
}
```

证据引用必须变成：

```text
artifact_id + generation_id + content_sha256
```

不能只引用活动路径 `drift.json`。

建议索引分别保存：

```text
latest_generation_id
latest_content_sha256
referenced_generation_ids[]
generation_manifest_ref
```

一个提案如果基于第 42 代，后来探针生成第 43、44 代，其证据引用仍指向第 42 代。

只要第 42 代的原始字节和可信来源链完好，就能证明它在当时的内容，不因第 44 代出现而失效。

但若某个当前健康结论依赖第 42 代，则仍要单独检查是否过期。**历史真实与当前有效是两个不同的判断。**

还必须加入防代数断链规则：

```text
sequence 非连续
OR previous_generation_id 不匹配
OR 快照 hash 与 manifest 不一致
OR 上一代尚未留档就发生覆盖
⇒ LIFECYCLE_CHAIN_BROKEN
```

实际运行中如果探针丢失了一代，允许如实记为 `GENERATION_GAP`，但不能假装链条连续。

这类代数连续性最好由写入边界或受控包装器保证；事后从最新文件无法推回已经消失的中间代。

### \(b) Gate35、Gate36、Evidence Index 的机械红绿判据

这里先划一条准确性边界：问诊包给出了 Gate35/36 的红因是漂移活水及缺失 lifecycle，但没有给出两个 Gate 的完整谓词定义。

因此不能把“加了 YAML 就断言 Gate35=GREEN、Gate36=GREEN”当作验收。

正确做法是**先消除生命周期导致的具体 reason code，再运行两个 Gate 原有的全部其他判据**。

建议三处分别采用：

| 检查点 | 可判 GREEN 的最低条件 | 必须保持 RED 的条件 |
|--------|--------|--------|
| Evidence Index | 每条受管证据绑定合法 generation、hash、可读快照和有效 lifecycle 契约 | 只登记最新 live hash；代数缺失；引用代无字节 |
| Gate35 | 原有 Gate35 条件全部通过，且相关证据的生命周期完整性校验通过 | 无声明、声明未获批准、快照断链、原有硬失败 |
| Gate36 | 原有 Gate36 条件全部通过，并正确区分历史证据与当前有效性 | 使用过期观察证明当前状态、历史快照无法复核、原有硬失败 |

具体输出建议为：

```json
{
  "lifecycle": {
    "declared_artifact_count": 2,
    "unknown_lifecycle_count": 0,
    "missing_generation_count": 0,
    "missing_snapshot_count": 0,
    "hash_mismatch_count": 0,
    "unauthorized_policy_count": 0
  },
  "index": {
    "generation_binding": "GREEN",
    "snapshot_integrity": "GREEN"
  },
  "gate35": {
    "lifecycle_checks": "GREEN",
    "overall": "<computed-original-gate-verdict>"
  },
  "gate36": {
    "lifecycle_checks": "GREEN",
    "overall": "<computed-original-gate-verdict>"
  }
}
```

不能由这个诊断文件自填 `overall=GREEN`；必须由实际 Gate runner 重新计算。

#### 五条必测负例

| 负例 | 预期裁定 |
|--------|--------|
| 活水文件没有有效生命周期声明 | RED：`LIFECYCLE_UNDECLARED` |
| 第 42 代已被第 43 代覆盖，但 42 无快照 | RED：`EVIDENCE_SNAPSHOT_MISSING` |
| 索引重建后旧提案自动指向新一代 | RED：`EVIDENCE_GENERATION_REBOUND` |
| 历史快照有效，但被拿来证明最新健康状态 | RED：`CURRENT_EVIDENCE_STALE` |
| 生成器投影的实际字节与 receipt 不匹配 | RED：`PROJECTION_HASH_MISMATCH` |

`LIFECYCLE_UNDECLARED` 应该是**受管证据进入正式验收时的硬 RED**，不是简单的 UNKNOWN。因为这时系统知道一个必需契约不存在。

至于没有被用于正式证据、且尚未进入受管范围的临时文件，可以维持 `UNCLASSIFIED`，不必让所有临时文件阻塞融合。

#### 声明后合理的预期读数

就 R8 这三项漂移红而言：

- Evidence Index 中由“活动文件 hash 漂移”引起的红，应转换为“快照代数完整性”检查，不再随着合法覆盖而反复跳红。
- Gate35/36 中由“合法跨代覆盖”引起的红，应消失。
- 没有历史快照的旧引用仍保持 RED 或 UNKNOWN，不允许追溯补绿。
- 两个 Gate 如果存在其他独立硬失败，最终仍然 RED。

**目标不是让漂移消失，而是让系统能区分合法的版本演进和证据篡改。**

### \(c) 明确延期项

本轮不做：

- 全历史 `drift.json` 的回溯恢复；
- 所有生成文件的统一生命周期化；
- 基于长期漂移趋势的自动智能评估；
- 自动决定保留期限或覆盖范围；
- 自动将历史证据升级为当前有效证据；
- 让生命周期契约反向修改生产者、owner 或 Gate 的授权边界。

本轮只应覆盖**已知导致三个红灯的受管活水产物及其直接证据链**。

另外，保留 N 代的默认数值、实际存储后端与跨仓归档方式可以延期，但“正式证据所引用的代不得被常规清理删除”这一不变量不能延期。

## Q2｜Gate33 done\_when：选择方案②，禁止 adapter 绕过 Task Index

### \(a) 裁定

**明确选择方案②：在 `machine/TASKS.yaml` 为全部适用的 CT 行补充真实的 `done_when`，由 `build_task_index.mjs` 透传，再由 task adapter 从统一索引消费。**

不选方案①的直接原因是：它会引入第二条 Task 读取路径。

目前已有：

```text
10_/20_ 看板 §八
       ↓
build_task_index.mjs
       ↓
generated/index/tasks.json
       ↓
task adapter
       ↓
Gate33
```

如果让 adapter 额外直接打开 `machine/TASKS.yaml`，就会变成：

```text
task adapter
   ├── Task Index
   └── TASKS.yaml 直接读取
```

以后 Task Index 的来源 receipt 已经过期，adapter 却可能从另一条路径拿到新的 `done_when`，形成同一个 Task 的版本混合。

这并不是控制平面拥有 CT 数据的错，而是**消费层不该拥有两套可独立变化的真相**。

### 正确的修改边界

**`machine/TASKS.yaml`**

CT Task 的授权来源。人或获授权主体填写真实、可判定的 `done_when`。

**`build_task_index.mjs`**

按 `source_kind` 选择权威字段，校验字段来源、生成 index 和来源 receipt。

**`generated/index/tasks.json`**

统一输出 `done_when`、来源路径、来源对象摘要和索引生成版本。

**task adapter → Gate33**

从索引消费标准化 Task，不绕过索引读取其他源文件。

建议索引的标准化记录至少包含：

```json
{
  "task_id": "CT-16",
  "source_kind": "core_task",
  "source_ref": "machine/TASKS.yaml#CT-16",
  "source_record_sha256": "<64-hex>",
  "done_when": [
    "<可机械验收条件>"
  ],
  "done_when_origin": "core_task",
  "done_when_source_sha256": "<64-hex>",
  "index_build_sha256": "<64-hex>"
}
```

如果冻结的 task binding 要求 `done_when` 为字符串而不是数组，应在索引中规范化成符合冻结 schema 的字符串；不要为适应这个示例而更改 30\_ 的原生 schema。

此外，`source_record_sha256` 必须明确其规范化算法和版本，并保留整个来源文件的 SHA-256。两个粒度不能混用。

### 如何防止 core 成为看板后门？

用来源域进行强制分流，而不是允许 adapter 自由择优：

| Task 类别 | `done_when` 唯一权威 | 其他来源的处理 |
|--------|--------|--------|
| CT Task | `machine/TASKS.yaml` 对应 CT 行 | 看板不得产生 CT 的另一份权威记录 |
| 普通 Task | 对应看板 §八的有效记录 | core 不得覆盖普通 Task 的完成条件 |
| 来源分类不确定 | 无权威来源 | RED |
| 两端存在冲突的权威记录 | 不自动选较新的 | RED |

建议不变量：

```text
task_id 属于 CT 命名空间
⇒ source_kind == core_task

task_id 属于普通任务命名空间
⇒ source_kind == board_task

source_kind 与实际来源不一致
⇒ RED_SOURCE_AUTHORITY_VIOLATION
```

DEC-21 授权控制平面持有 Task 权威，是该方案成立的前提。但授权**持有**不等于允许**无约束改写**。

CT 行的 `done_when` 仍需有实际验收内容。

例如，不合格：

```yaml
done_when: "任务完成"
```

更合格的 CT-05 条件可以是：

```yaml
done_when:
  - "Task 与 Decision 的真实输入变更有可追溯的 State 归因记录"
  - "隔离负例中首页落后于 State 时发布闸门必须阻断"
  - "来源落后检测、State receipt 和首页 receipt 通过对应测试"
```

但如果 frozen binding 要求字符串，应将这些条件规范化编码为符合现行格式的文本。

**不能仅靠字符串非空，就认定完成条件有意义。**

机械系统至少要验证其包含可引用的测试 ID、预期状态和可追溯的产物引用。自然语言描述是否真正覆盖任务目标，仍可能需要授权评审。

### \(b) Gate33 的机械红绿判据

第一步不是直接追求 Gate33 整体变绿，而是要求输出按来源和失败原因分类的违规分布。

建议：

`runtime/gate33-task-binding-distribution.json`

```json
{
  "gate": 33,
  "binding": "task",
  "violations": {
    "ct_done_when_missing": 0,
    "ct_done_when_not_indexed": 0,
    "ct_done_when_source_mismatch": 0,
    "ordinary_task_done_when_missing": 0,
    "schema_other": 0
  },
  "source_integrity": {
    "index_receipt_valid": true,
    "source_hashes_match": true,
    "unauthorized_ct_board_entries": 0
  }
}
```

这里的数字是**目标结果**，不是当前实测结果。

| 阶段 | 预期读数 |
|--------|--------|
| R8 原始状态 | `done_when` 相关违规 34 |
| 只修 CT-16\~19 | 最多应消除这 4 条，原有 30 条继续挂账 |
| 修复全部 34 条适用记录并重新构建索引 | `done_when` 缺失/未透传违规 0 |
| 完整 Gate33 重验 | 所有 schema 及来源完整性条件通过才 GREEN |

若旧 30 条中存在其他独立原因，不能假设全部由本次修改清除。必须让审计器逐条输出 `task_id → reason_code`，最终依实际报告裁定。

#### 五个必须失败的负例

1. **CT 源行缺 `done_when`**：索引不得补造默认值，Gate33 RED。
2. **CT 源行有 `done_when`，但索引没有透传**：RED，不能由 adapter 直接回读 core 补救。
3. **索引值被篡改、源文件未变**：receipt 或记录摘要不匹配，RED。
4. **普通 Task 在 core 出现冲突 `done_when`**：不得静默覆盖看板权威，RED。
5. **CT 行出现在看板并被误当普通 Task**：触犯判据3，RED。

还要增加一个关键正例：

`machine/TASKS.yaml` 中合法改变 CT 的 `done_when` 后，**不先重建索引时 Gate33 不能继续沿用旧绿色收据**。

这是防止“索引有字段，但已经落后于真源”的必要测试。

### Gate33 通过的公式

```text
所有适用 Task 有合法 done_when
AND 每条 Task 的来源域符合权威契约
AND index 来源摘要匹配当前源
AND adapter 只消费统一 index
AND 冻结 task schema 校验通过
AND 所有负例确实被拒绝
⇒ Gate33 task binding GREEN
```

建议正式状态必须同时保留：

- `schema_valid`
- `authority_valid`
- `source_fresh`
- `negative_tests_verified`

不能用 schema GREEN 隐藏来源权威 RED。

### \(c) 明确延期项

- 不改动 30\_ 的冻结 schema。
- 不引入通用的 Task 跨源自动合并机制。
- 不让 AI 从 Task 标题批量推断 `done_when` 并自动批准。
- 不借 Gate33 修复重新解释所有历史 Task 的完成状态。
- 不把所有看板 Task 迁进 `machine/TASKS.yaml`。

尤其是历史 30 条：允许批量检查字段格式和引用有效性，但完成条件的具体内容必须有真实任务依据。**不能为了消灭 34 条红而批量补一句“符合验收标准”。**

## Q3｜基线重拍：先封存已提交差异，最后统一发布新基线

### \(a) 裁定

(当前不得整体重拍)

我支持你暂不重拍的决定，也支持**两阶段处理**，但必须严格定义两阶段的权限。

**第一阶段允许确认已提交变更，不允许因此改变当前正式基线；第二阶段才允许发布新基线。**

因为目前至少存在三类不同事实：

| 变更类别 | 可以立即做什么 | 不允许做什么 |
|--------|--------|--------|
| 本轮已提交的 4 个落地文件 | 依据确定的 commit/tree 对象生成待批准差异清单 | 直接算入新的已生效基线 |
| R5\~R7 遗留未提交修改 | 逐文件分类、找回责任与来源、要求提交或撤销 | 被重拍脚本顺手吸收 |
| 1 个缺失/改名路径 | 建立旧路径→新路径迁移映射并验证内容身份 | 直接从基线删除旧路径后宣布无漂移 |

对于改名项，尤其不能仅因 Git 检测到了 rename 就认为语义完全一致。还需要检查原路径用途、引用关系和新路径实际内容。

### 建议的两阶段程序

#### 阶段一：冻结差异说明，不改正式基线

建议产出：

`runtime/baseline-reconciliation/`

包含：

```text
original-baseline-ref.json
committed-delta-manifest.json
dirty-worktree-manifest.json
rename-mapping.json
approval-record.json
reconciliation-verdict.json
```

具体操作：

1. 固定原始 baseline 的 SHA-256，禁止覆盖原文件。
2. 固定当前 `HEAD` commit 和 tree hash。
3. 在干净、只包含目标提交的工作树中读取已提交内容，避免把当前工作目录的未提交修改混入。
4. 对 20 项变更和 1 项缺失逐一分类。
5. 将已提交的 4 项列入一个明确的待批准 delta manifest。
6. 其余项继续归类为未解决，不将它们从基线覆盖清单中移除。

这里可以使用专门的干净 Git worktree 或直接从 Git tree 对象读取内容，而不是从混杂着未提交改动的活动目录采样。

#### 阶段一的机械输出

```json
{
  "phase": "RECONCILIATION",
  "baseline_change_authorized": false,
  "original_baseline_sha256": "<64-hex>",
  "source_commit": "<git-commit>",
  "source_tree": "<git-tree>",
  "committed_delta": {
    "reviewed_count": 4,
    "manifest_sha256": "<64-hex>"
  },
  "unresolved": {
    "paths": "<computed-count>",
    "rename_cases": "<computed-count>"
  },
  "status": "PENDING_FINAL_REBASE"
}
```

不要将 `unresolved.paths` 的初值机械写死为 16，因为“20 变更 + 1 缺失”涉及路径归类，改名、提交范围与未提交状态可能重叠。应从真实 Git 差异及基线 manifest 逐项计算。

即使所有 4 个已提交变更通过批准，**BS\_DRIFT 仍然 RED**，因为正式基线还没有改变，剩余差异也没有解决。

这不是失败，而是如实保留账面事实。

#### 阶段二：统一发布新基线

只有达到以下条件才启动：

```text
所有基线范围内的相关变更已提交或明确撤销
AND 所有新增/删除/改名都有分类与批准
AND 工作树在受管范围内无未提交修改
AND 没有未解释的缺失文件
AND 差异 manifest 已被授权批准
AND 重拍工具和冻结范围通过负向测试
```

再执行：

1. 冻结提交及 tree。
2. 由受控 capture runner 计算候选基线。
3. 生成旧基线→新基线的完整 diff manifest。
4. 验证批准引用绑定该 manifest 的确切 SHA-256。
5. 发布新的基线版本，而不是抹掉旧的基线。
6. 重新运行基线检测和 `fusion-check`。
7. 记录新旧基线的继承关系与生效时点。

### 谁执行、是否要逐文件会签？

建议采用**逐文件审查、按清单整体会签**。

也就是说：

- 所有变化文件必须列在差异清单里，不能遗漏。
- 每个文件都要有类型、旧/新 hash、来源提交、原因和处置分类。
- 不要求为每个普通文件分别签署一份批准文书。
- 审批者可以一次批准覆盖精确文件清单及其 hash 的 manifest。
- 改名、删除、权威身份、契约规则与冻结域变更等高风险项目，应在 manifest 中有明确的单项批准结果。

生产者可以准备清单、执行 capture，但不应自行批准其捕获范围及基线替换。

尤其不能接受：

```text
approval_ref = "郭老师已同意重拍"
```

却没有相应的版本、范围或签署证据。

真正的审批对象应该是**哪一组确切字节和路径变更被接受为新的基线**。

### 1\. 首例契约放行件：应该重开，而且应作为反例

**裁定：需要重开其“契约动议合格性”，但不要抹掉原来发生过的人审事实。**

目前首例的链条是：

```text
    ↓
合法 Candidate

    ↓

    ↓

    ↓
```

这里 Evidence→Candidate 的真实性与可追溯性可能是成立的。

但从 `Proposal` 到 `Contract Approval` 缺少一个不可省略的判断：

**到底提出了哪一条可执行、可验证的规则变更？**

如果只是描述一次 drift 观察：

- 没有目标契约字段；

```json
{

  "target_contract_ref": "<contract-ref>",
  "change_operations": [
    {
      "op": "add",
      "target": "<contract-field-or-rule>",
      "proposed_value": "<normative-rule>"

  "evidence_refs": ["<version-bound-ref>"],
  "enforcement": {
    "consumer_refs": ["<runner-or-gate>"],
    "positive_case_refs": ["<test-ref>"],
    "negative_case_refs": ["<test-ref>"]
  },
  "review": {
    "required_authority": "<approval-role>"
  }
}
```

字段必须通过 schema，且 `change_operations` 不能是空列表或无实际效果的空操作。

对于无法由 schema 完全判定的“规范是否有意义”，最低要求是批准者单独签署：

`normative_substance_accepted=true`

该批准绑定提案 hash，不得只继承证据有效性的 approve。

`RECLASSIFIED_AS_OBSERVATION`

`CONTRACT_APPROVAL_SUSPENDED_PENDING_SUBSTANCE_REVIEW`

具体选哪种应由原授权批准者决定。不要由 Gate 擅自撤销人的历史决定。

原始 proposed、approve 与裁决记录全部留档，以新的纠正事件关联旧记录。


要避免 Gate37 继续被“1/1 证据可解析”刷成绿色。

### 2\. P7 封存语义：历史裁决可以不随活文件漂移，但不能免除证据真实性

**裁定：P7 的方向正确，但当前契约不充分。**

你做对的是：

> 不能因为今日探针覆盖了 `drift.json`，就自动宣布昨天基于真实观察作出的裁决在昨天也不合法。

但是另一个极端也必须禁止：

> 只要昨天写过 verdict\_ref，从此不检查原始证据，裁决永远有效。

正确做法是把两个状态分开。

| 状态 | 检查对象 | 后续漂移的影响 |
|--------|--------|--------|
| `historical_evidence_integrity` | 裁决时点封存的证据字节、版本、来源与批准对象 | 合法新代不影响旧代真实性 |
| `current_applicability` | 该契约或结论现在是否仍满足前提和时效 | 可能因当前状态改变而失效 |

例如，昨天批准了一项“镜像漂移应产生诊断提醒”的规则。今天镜像恢复正常，不会使昨天的漂移观察变假。

但今天若仍用昨天的漂移报告断言“当前镜像异常”，就是证据过期。

#### 建议给已批准件增加

```yaml
evidence_seal:
  evaluated_at: "<UTC-time>"
  source_generation_id: "<id>"
  snapshot_ref: "<immutable-ref>"
  snapshot_sha256: "<64-hex>"
  integrity_status: verified

applicability:
  mode: historical_or_current
  current_validation_required: true
  revalidation_trigger:
    - governing_contract_changed
    - source_semantics_changed
    - evidence_freshness_expired
  on_failure: suspend_current_effect
```

对于纯历史观察，`current_validation_required` 可以为 false；对于持续生效的运行规则，则应按授权契约决定复验时机，不能一律 false。

若 P7 旧放行件只有 `verdict_ref`，没有封存的原始证据字节及可信来源证据，则应该输出：

`HISTORICAL_EVIDENCE_UNVERIFIABLE`

而不是把“裁决时点封存”作为没有文件支持的假定。

### 三个必须分开的裁决结果

```text
历史批准确实发生          → APPROVAL_RECORDED
历史证据可完整复验        → HISTORICAL_INTEGRITY_GREEN
该批准目前仍适用          → CURRENT_APPLICABILITY_GREEN
```

后者不能由前两者自动推出。

**P7 应该封存历史，不应该冻结真理。**
