我按 R4 原文来裁，不沿用 R1/R2/R3 的记忆替代原文。先给总判断：你这轮遇到的三个问题，本质上分别是证据对象的生命周期类型混淆、历史对象在规则升级后的授权语义断裂、以及为了恢复吞吐而诱发的追溯性伪造风险。其中 Q1 有一个目前技术上不能决定、也不该假装已经解决的边界；Q2 可以现在裁大半；Q3 我会反对你强制“三选一”，因为对 14 条统一套一个选项反而会制造你最不想要的假经验。原文中探针正常重写导致四处 hash/drift 红、三份旧草稿变为 DRAFT_LINEAGE_STALE、以及历史 14 条全部无声明而使候选池归零，正是这三个问题的实际触发条件。

Q1：运行态快照撞上 hash-pinned 证据模型

(a) 裁定

要区分“不可变工件”和“运行态快照”，但我不同意把这个分类首先写进 generated/index/evidence.json，也不赞成借 machine/fact_authority.tsv 的 role 偷塞生命周期语义。

权威声明应该放在已有契约的来源声明中，evidence.json 只投影，不成为第二个可人工修改的真源。 fact_authority.tsv 如果目前回答的是“谁对事实有权威”，就继续只回答这一件事；“谁能写”和“写出来以后允许不允许被同一生产者覆盖”是不同维度，混进 role 最后会使一个字段同时承担 authority、ownership、lifecycle 三种含义。

谁能写这个分类：契约的授权维护方能写；运行中的 probe 不能写或降低自己的完整性等级。 否则生产者一旦出问题，完全可以一边改证据一边把自己重新声明成“mutable”，等于让被监督对象修改监督规则。分类变化本身应当被视为契约变更，而不是一次正常 probe 输出。你明确不想造第五个写口，这正是应该把它留在已有契约写口而不是 evidence index 的理由。原文已经说明这些 runtime 文件本来就会由定时 probe 覆写，同时又被前一天登记成 hash 钉死证据；目前的四处红因此是模型错误暴露，不是四次独立篡改事件。

我也赞成你排除的三条路。重捕基线会把“授权看板变更”和“未裁定的两个快照变化”一起吸收掉，确实是在消红而不是解释红；冻结的 30_元智能 不该为了这个问题被反向修改；probe-owned 产物也不能靠手工改回旧 hash 来伪造一致。

但这里要明确推翻一个隐含前提：对一个允许原生产者反复覆盖、而又没有独立可信生产证明的文件，不存在某种更聪明的“当前文件判据”既允许正常改写、又仍能证明没被第三方篡改。 新鲜度做不到，文件内的 probe_self_test: pass 也做不到，因为篡改者若能改整个文件，也能一起改这两个字段；“上一次 hash + 当前允许不同”同样不能回答当前变化是谁写的。这不是 Gate 写得够不够复杂的问题，而是信息不足。

因此，我不选你列出的三种作为“SHA 的等价防篡改替代品”。在现状下，对 snapshot 应明确降低声明强度：

snapshot 的 Gate 可以证明“当前快照满足有效性契约”，不能宣称“当前快照具有 immutable hash 所代表的防篡改证明”。

它仍然可以检查新鲜度、结构、必要字段、跨字段约束、probe 执行结果等；但这些叫 validity/liveness，不叫 tamper-proof integrity。若你要求后者，就必须等将来出现独立于可覆写文件本身的生产者证明后再裁具体机制。现在不能决定，硬选一种会制造虚假的安全保证。

关于“运行态快照根本不该进证据索引”，我不会一刀切赞成。如果 evidence.json 的契约定义是“所有供裁决引用的证据位置”，snapshot 可以在里面，但必须投影出 snapshot 语义；如果它的定义本来就是“hash-pinned immutable evidence 集”，那 snapshot 就根本不该进去。 R4 没给出这个索引自身的完整语义定义，所以这一点现在不能凭文件名决定。

(b) 可编码机械判据

最小判据可以写成：

artifact_lifecycle 只能从契约来源声明读取。若为 immutable，当前字节 SHA 必须等于登记 SHA；若为 snapshot，禁止拿“与昨日 SHA 不同”本身作为失败条件，而改验 snapshot validity contract。若生命周期声明不存在，则不是猜一个默认值，而是报规格缺口。

snapshot validity 至少应是确定性的布尔表达式：生产物存在、schema 合法、必填生产时间可解析、年龄不超过契约规定窗口、producer-specific invariants 全部成立。注意：最后这些只是“有效快照”的判据，不应输出“未篡改”结论。

Gate 红的归类，我建议用一个非常机械的语义规则，而不是按 Gate 编号分：

已知业务事实违反契约 → 业务红；证据本身失效、所以业务事实无法可靠判定 → 证据有效性红；规则缺失导致无法知道应该怎么判 → 规格缺口；检查程序本身异常 → 内部错误。

因此你现在的 UR_HASH_MISMATCH/EI_HASH_MISMATCH 若对象已经被正确声明为 snapshot，正常 probe 重写不应该降级成另一种红，而应该根本不产生 hash-mismatch 红。但如果 snapshot 过期、缺字段、格式坏了，它仍该红，只是原因是证据失效而不是业务事实为假。这能避免把“正常字节变化”与“事实冲突”混在一起。原文当前正是把正常 probe 重写投射成多个 hash/drift 红，这个口径需要纠正。

失败模式也要写死。对于 freshness/schema 方案，绿但实际被篡改的情形是：第三方把内容、时间戳以及自检字段一起改成仍满足契约的值；现状下 Gate 无法识别，这是必须公开承认的 blind spot。红但实际正常的情形包括：调度器迟到、probe 执行时间偶发超长、时钟漂移、合法格式升级先于契约升级。相反，immutable hash 的正常误红主要来自本来就不该重生成的对象被合法重生成——这实际上说明对象的 lifecycle 分类错了，而不是应该放宽 hash。

(c) 等哪些运行时信号

不要现在拍脑袋定 freshness 的 N。先收集真实 probe 的计划间隔、启动延迟、执行耗时、失败重试以及时钟偏差分布，再据此定容忍窗口；尤其应看尾部延迟，而不是平均数。

还要等一个更重要的信号：这些 snapshot 到底被哪些下游裁决消费，以及它们是否需要“历史时刻可复验”而不仅是“当前状态可读”。 如果没人需要回溯某次裁决所见的确切 snapshot，那么没有必要为了“像证据”而强行制造不可变历史；如果后续确实出现审计/争议需要，才有理由引入独立历史证明。现在不要提前复杂化。

Q2：旧规则产出的三份草稿失去血缘

(a) 裁定

“几周前写 L1 的那个 Agent”不能仅凭“逻辑上还是我”就自动拥有追溯声明权。Agent 名称、模型实例或角色连续性不是可靠的历史授权凭据。

机械意义上的“写者声明”应当是：声明来自原始写入事务，或能由原始、可寻址、在回填之前已经存在的写入上下文直接证明。 如果今天只是重新读旧 L1 后推测“当时大概想做 method”，那是 retrospective inference，不是 writer declaration。

因此，对历史 L1，我会允许 Agent 回填的范围非常窄：原始会话/事件里已有明确、唯一的产物意图，只是当时 schema 尚无这个字段，今天做的是投影缺失字段；如果原始材料只能靠解释“适用范围”重新猜，那正是 R3 已经否掉的语义捷径，不能借“原 Agent 回来了”复活。

没有这样的原始证据时，就需要人类确认。这个结论现在能裁，不用等运行时。

三份现有草稿则现在不要硬删。它们已经有逻辑 URI，而且 R4 明说已有引用风险；在没有“撤销/退役 URI”的既定语义前，hard delete 会把一个已知 lineage 问题变成引用完整性问题。

眼下正确状态是：保留文件、保持 DRAFT_LINEAGE_STALE 可见、禁止它们进入 promotion/install 路径，等血缘被有效补齐或明确撤销。如果将来确实撤销，留痕应该落在当前负责授予和解析逻辑 URI 的权威登记处，而不是塞到某个 Gate 日志里。如果系统目前根本没有“URI 已撤销但历史上存在”的状态语义，那不是删除命令缺一行，而是一个规格缺口；先别删。

DRAFT_LINEAGE_STALE 我同意你不能为了全绿降成 info。但“红”还应进一步区分含义：它表示 lineage contract 不成立，并不自动等于业务结果错误。只要一个 stale draft 仍被系统视为有效、可晋升对象，它就必须失败；只有在它已被契约明确置于不可晋升/已退役状态后，才没有理由继续把它作为当前有效集合的失败项。

(b) 可编码机械判据

历史补声明可编码成：

接受 agent_backfill 当且仅当它的依据指针指向回填动作之前已经存在的原始来源，并且该来源能确定唯一枚举值；否则拒绝 Agent 声明，进入 human-confirmation 状态。

其中“旧 适用范围 经过当前分类器又推出来一个值”应明确不算有效依据，因为这等于把已废弃分类规则重新作为权威。

对草稿撤销，机械规则是：

只要 logical URI 有任何有效入引用，或者 resolver 没有已定义的 retired/tombstone 语义，就禁止 hard delete。 无法表达撤销状态时，报规格缺口，而不是直接减 URI 数。

对 stale 严重度：

lineage_valid=false && artifact_is_promotable=true ⇒ fail；lineage_valid=false && artifact_is_explicitly_retired=true ⇒ 不进入当前有效集合。

这比“永远红”或“统统降 info”都更机械。

(c) 等哪些运行时信号

等的不是“红看起来烦不烦”，而是两件事：一是这三份草稿实际有没有进入任何 promotion/install 尝试；二是未来的人类核验中，Agent 严格证据回填被推翻的比例是多少。

如果 stale 对象虽然地址可寻址，却已经被所有执行路径强制隔离，那么它不应该长期污染“业务失败数”，但 lineage/conformance 状态仍应显式存在。这个口径最好在你确认真实消费路径后再定。

Q3：历史 14 条让吞吐变成 0/14

(a) 裁定

这里我要直接反对“14 条统一三选一”。

纯选 1 风险最大，因为它很容易把“今天的 Agent 对过去文字的解释”伪装成“当时写者的声明”，从而产生你问到的假的可复用经验。纯选 2 在语义上安全，但确实把存量吞吐完全绑定到人类带宽。纯选 3 不造假，却把历史资产永久判死，而且“历史 schema 缺字段”并不等于“历史经验本身永远无资格”。

所以应该逐条按证据分流，而不是按库存整体选项：能从原始写入上下文机械恢复唯一意图的条目，允许受约束的 Agent backfill；其余必须人类确认；两者都没有时继续不参与路由。

这并不是重新设计架构，而是给你已有三条路径一个判定边界。

因此 0/14 今天并不是一个应该靠降低标准立即修掉的故障。它说明“旧库存尚未获得新契约需要的授权语义”。用户想要以后每日自动更新，并不推出“今天必须让旧 14 条自动变候选”。吞吐指标不能反过来授权数据。

(b) 可编码机械判据

挡住“假的可复用经验”，我会用这一条硬检查：

任何 declared_by=agent_backfill，都必须带一个不可为空的依据指针；该依据必须在此次 backfill 之前已经存在，并且依据类型只能是“原始写入上下文中的明确意图证据”，不能是当前 Agent 新生成的解释、旧 适用范围 的重新分类结果，或由待补字段本身派生的循环证明。否则闸门拒绝。

也就是说，Agent 可以补录过去已经说过但 schema 当时没槽位装的东西；Agent 不能替过去的自己现在补一个当时没说过的意图。

如果一条旧记录没有这种证据，机械结果不是猜 unknown 来让管线继续，也不是默认 method，而是“需要人类声明 / 暂不路由”。

这同时回答了 Q2(a)：所谓“当初那个 Agent”有没有权，不看角色名，看是否能出示原始声明证据。

(c) 等哪些运行时信号

先观察四个量：严格 backfill 后实际恢复多少候选、人工复核推翻率、被恢复候选最终成功提炼/使用的比例、以及新 schema 下新 L1 的自然候选率。尤其重要的是人工推翻率：如果严格证据型 Agent backfill 很少被推翻，才说明这条自动路径有扩大价值；如果推翻率明显，就应该收紧而不是因为吞吐低而放松。

对于“是否值得处理全部 14 条存量”，也应该等真实收益：如果新经验每天已经持续产生足够候选，历史清仓可能没有紧迫性；如果新流量很低而旧库存中反复出现高价值事件，再投入人工确认才有依据。

最后再点一下你这轮最容易踩的两个坑。第一，不要把“证据 hash 变了”与“证据被篡改”画等号；对于生产者定义上就会覆写的 snapshot，这个等号本身就是错误模型。第二，不要把“吞吐为零”当成必须恢复的健康指标；如果零是因为系统拒绝替历史写者编造声明，它恰恰可能证明闸门正在按设计保护语义。原文里你已经看到一次护栏在无人盯守时正确阻止了错误结论，这轮应该继续保住这种性质，而不是为了数字好看穿透它。
