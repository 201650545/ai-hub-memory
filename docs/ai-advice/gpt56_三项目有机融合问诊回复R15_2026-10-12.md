# R15 复裁定：不要把“治理覆盖”偷换成“内容合格”；不要把“有责任”偷换成“已修复”

先给总判断：

**R15 的方向正确，但当前状态不是“剩余问题”，而是治理模型正在从“结构正确性”进入“语义质量控制”。**

前几轮解决的是：

- 有没有入口；
- 有没有 witness；
- 有没有 hash；
- 有没有 contract；
- 有没有 owner。

现在剩下的 23 条 L1 恰好暴露了下一层问题：

> 一个字段齐全的 L1，不一定是一个可信经验。

因此这一轮不能再用 R5～R13 的思路处理：补字段、过 schema、恢复绿灯。

---

# Q1｜23 条 L1 内容缺陷：责任边界

## (a) 裁定

### 裁定一：23 条 L1 不进入修复队列“代修”，而进入“退回责任链”

明确分工：

| 角色 | 责任 |
|-|-|
| 原写入会话 | 解释经验含义、补充缺失语义、确认类型和触发条件 |
| repair queue | 管理状态、催办、阻断下游、统计债务 |
| reviewer/授权人 | 判断是否接受修订后的经验 |
| Agent | 可以辅助整理，但不能替代事实判断 |

这里需要硬推回：

你之前最大的风险是：

> “修复队列会不会变成永久追赶？”

答案是：**如果 repair queue 负责修内容，它一定会永久追赶。**

因为它没有原始上下文。

例如：

```
listenloop:
"遇到 X 问题，用 workaround Y"
```

缺少：

- 触发信号；
- 适用范围；
- 时间窗口；
- 失败边界。

修复队列看到的是残片。

它最多知道：

```
FIELD_TRIGGER_MISSING
```

不能知道：

```
trigger = "首次启动监听服务且 websocket reconnect 超过 N 次"
```

后者属于经验拥有者。

---

### 裁定二：建立 L1 缺陷状态机，不允许直接编辑回绿

建议：

```

 ↓
ASSIGNED
 ↓
AUTHOR_RESPONSE_PENDING
 ↓
AUTHOR_SUBMITTED
 ↓
REVIEW_REQUIRED
 ↓
VERIFIED
```

禁止：

```
DETECTED
 ↓
AI补字段
 ↓
PASS
```

这是本轮最重要的防线。

---

### 裁定三：23 条不是全部同优先级

建议分类：

| 类别 | 处理 |
|-|-|
| 已被 candidate 消费 | P0 |
| 已进入 distill 输入 | P0 |
| 仅存在库中未引用 | P1 |
| 已废弃经验 | P2/RETIRE |

不要按发现时间排队。

按**影响半径**排序。

# Q2｜BS_DRIFT：不要让基线成为开发刹车

## (a) 裁定

三选一：

> ①每次改文件重拍：错误  
> ③降 WARN：错误  
> ②里程碑重拍 + delta ledger：正确

原因：

你的基线目前承担两个冲突职责：

1. 冻结参考点；
2. 活跃开发状态同步。

这两个必须拆。

---

建议：

```
Baseline
    |
    +-- immutable reference
    |
    +-- authorized delta ledger
```

不是：

```
Baseline = 当前所有文件
```

---

## 基线应该回答：

不是：

> “现在是不是等于过去？”

而是：

> “现在的变化是不是被允许？”

---

## (b) 机械判据

新增：

```
machine/baseline-delta.yaml
```

每个变化：

```yaml
path:
baseline_sha256:
current_sha256:
change_type:
authorization_ref:
commit_ref:
scope:
```

---

### GREEN：

```text
所有变化都有 delta entry

AND

所有 delta:
  有 commit
  有 owner
  有 authorization

AND

冻结域:
  byte_equal=true

AND

无未知文件变化

=> BASELINE_CONTROL_GREEN
```

---

### RED：

以下任一：

```
baseline changed
AND
no delta record
```

或者：

```
delta exists
AND
authorization missing
```

或者：

```
approved scope != actual diff
```

---

### 特别指出

37 条 L1 意图补声明导致漂移，不应该直接归：

```

```

应该拆：

```
BASELINE_CHANGED
+
AUTHORIZED_DELTA_PENDING_REBASE
```

否则你的红灯会永远报告“世界在变化”。

世界变化不是问题。

**不可解释变化才是问题。**

---

# 追加问题裁定

---

# 1. CT-31/32/33 主动填写 done_when 算不算机制根治？

答案：

**算行为反馈证据，不算机制根治。**

区别：

行为证据：

```
人看到错误
↓
人改变行为
```

机制证据：

```
换一个人
↓
忘记填写
↓
系统拒绝
```

你现在证明的是：

```
反馈有效
```

还没证明：

```
入口不可绕过
```

所以状态：

```
DONE_WHEN_BEHAVIOR_IMPROVED = GREEN

DONE_WHEN_ENFORCEMENT_LIVE = UNKNOWN
```

---

# 2. DRAFT_LINEAGE_STALE 是否应该区分合法修订？

必须。

否则会出现一个荒谬结果：

系统为了防篡改，反而禁止合法进化。

建议拆：

| 类型 | 含义 |
|-|-|
| SOURCE_AUTHORIZED_REVISION | 合法升级 |
| SOURCE_UNAUTHORIZED_CHANGE | 异常 |
| SOURCE_DELETED | 丢失 |
| SOURCE_HASH_MISMATCH | 不一致 |

但是：

合法修订 ≠ 自动重新通过。

例如：

L1 v1：

```
trigger=A
```

L1 v2：

```
trigger=B
```

旧 draft 仍然可能历史有效。

但不能自动用于当前版本。

所以输出应该：

```
historical_valid=true

current_consumption=false
```

---

# 3. 12绿2红是不是说明总闸理念应该改变？

方向对，但表述要修正。

不是：

> 总闸不要求全绿。

而是：

> 总闸从“质量评分器”变成“状态控制器”。

区别：

错误模型：

```
红=失败
绿=成功
```

成熟模型：

```
红=当前不可继续某些动作
```

例如：

| 状态 | 可做 |
|-|-|
| 基线 RED | 可开发，不可发布 |
| L1 RED | 可修复，不可提炼 |
| Evidence RED | 可调查，不可消费 |

所以应该增加：

```
allowed_actions
blocked_actions
```

而不是只显示颜色。
