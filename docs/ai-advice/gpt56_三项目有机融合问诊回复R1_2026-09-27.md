结论

这次不该再做“结构合并”，而应做一次写权限融合 + 语义融合 + 因果链融合。建议最终形态是：

一个语义控制平面 + 两个保留自治的原生子系统 + 一份不可变规范基线 + 一套确定性生成视图。

也就是说，本体不接管 10_ 的经验真源，也不接管 20_ 的执行真源；它只负责回答“这个 Demand 现在由谁执行、证据在哪里、学到了什么”。这与 D-003 要求的确定链路及“本体只拥有跨系统语义”完全一致。

核心原则只有一句：

事实在哪里产生，就只在哪里写；跨系统层只保存引用、关系和生成结果，不复制事实。

因此不建议造一个“大一统数据库/大一统 YAML”。那会把现在的三处双写变成第四处集中双写。真正要统一的是对象身份、写权限和传播协议。

30_元智能 的 43 个现有文件本轮一个字节都不应改。它应从“看起来像运行规范但实际上未执行”升级为冻结的规范基线 v1：新增外部绑定器让其四个 Schema 真正参与校验，而不是修改这 43 个文件。现有首页守卫、sentinel 真打开判活、回读、干跑→Apply→健康→再干跑、三档掩码和重建件正典全部原样保留，新机制只作为附加 Gate 接入。

优化后方案
一、对象模型：只让“有独立生命周期的东西”成为一等公民
对象	地位	唯一写口 / 真源	本体保存什么
System	一等	根 project.yaml	系统稳定身份
Component	一等	machine/vault_registry.yaml	子系统身份、角色、adapter、sentinel、源引用
Demand	一等	machine/demands/D-xxx.yaml	用户意图与验收语义
Task	一等	所属原生系统自己的 Task 真源	生成索引、跨树关系，不复制状态
Experiment	一等语义对象	不新设写库；由 Task 的实验字段 + 原生证据生成	生成后的 Experiment 投影
Evidence	一等	原生产物，不可变或内容寻址	source_ref + sha256 + producer + task/demand_ref
Experience	一等	10_ 经验条目	跨树引用及沉淀关系
Skill	一等	10_技能库，安装/晋升继续人审	引用，不复制内容
Contract	一等	20_\contracts	引用及版本/hash
State	退化为生成投影	无人工写口	Demand 的 Current State
Probe	工具/证据生产者	20_	注册能力，不作为业务状态
Drift	Evidence 的一种类型	20_ runtime	不另造 Drift 台账
Human View	纯投影	无人工写口	从 State/索引确定生成
30_规范	不可变规范基线	43 文件冻结	被校验器读取，不参与业务状态写入

关键点是 Experiment 不再为空壳，但也不新增 experiments.yaml 之类的第五写口。

Task 可以增加扁平字段，例如：

kind: experiment、experiment_id、hypothesis、success_rule、evidence_required

这些字段仍写在该 Task 的原生真源。统一生成器看到 kind=experiment 后生成 Experiment 对象，因此：

Experiment 是一等语义实体，但不是一等存储位置。

这恰好绕开“新增状态真源”的红线。

二、项目身份：实际上只有一个 Project

现在层级既然已经裁定为：

元智能 = System；10_/20_ = Component；30_ = System 的规范

那么 10_、20_ 从语义上就不应该再拥有独立 Project 身份。当前三份 project.yaml 确实造成了项目身份与阶段可以独立修改的问题。

建议收敛为：

1 个可写 project.yaml + 1 个现有组件注册表 + 0 个可写子项目身份文件。

根 project.yaml 只保留稳定系统级字段，例如：

schema_version / system_id / name / aliases / demands_dir / registry_ref

尤其建议把 phase/status/stage/milestone 从“项目身份”里剥离。这些不是身份，而是运行状态，应由 Current State 推导。

两棵子树原有字段这样归位：

id/name/type/visibility/local_path/aliases/source/repo/handbook/handoff → vault_registry.yaml 对应 Component 登记；

status/stage/milestone → 从 Task/Demand/State 生成，不允许再手填在 project metadata；

decisions/pilot/pattern_source → 回到 20_ 原生契约、决策或证据语义；

sibling_project → 删除这一语义，改为父系统下 Component 关系；

owner_skill/skill_index 等跨树引用 → 改成逻辑 URI，不再硬编码绝对路径。

原来 10_、20_ 的两个 project.yaml 在迁移期可以保留，但必须变成生成兼容件：

# GENERATED — DO NOT EDIT

并带：

source_sha256 / generated_from

任何手改都由 Gate 报错。

等确认没有消费者依赖后再删除；如果仍有旧工具依赖，就永久生成它们，但它们不再是真源。

注册表仍遵守现有扁平解析器：一行一 key，列表用内联 JSON；本方案不要求修改 registry.mjs 的无嵌套设计。

三、Task：统一“身份与查询”，绝不统一“执行写口”

这里最容易走错。

不要把 17+18 条子树 Task 搬进 machine/TASKS.yaml。

machine/TASKS.yaml 继续只拥有本体自己的 CT；10_ 看板继续拥有 10_ Task 状态；20_ 看板继续拥有 20_ Task 状态。

新增一个只读归一器：

runners/build-task-index.mjs

它读取三种原生 Task 真源，生成：

generated/index/tasks.json

统一逻辑 ID 不需要批量改现有 Task ID，而是生成：

<component_id>::<native_task_id>

例如逻辑上：

growth::T-017
workflow::T-018
core::CT-015

因此将来更换一个子系统，只需要换 adapter；Demand 与逻辑 Task 关系无需改写。

同时加 Task Authority Gate：

一个逻辑 Task 必须恰好有一个 authority_source。

子树 Task 出现在 machine/TASKS.yaml 且携带自己的状态 → FAIL。

CT 出现在子树看板作为可写状态 → FAIL。

§八等“归属节”如果存在状态字段 → FAIL。

§八所列 Task 集合与其原生看板不一致 → FAIL。

Human View 或 State 只能消费 generated/index/tasks.json，禁止自己解析第四套 Task。

同一 component_id + native_task_id 在两个可写源出现 → FAIL。

§八最理想的终态是生成区；若暂时不适合改文档，则至少做机器一致性校验，使它从“第二真源”退化成“受约束投影”。

四、Evidence 是连接三个世界的关键枢纽

真正“有机”的连接点不应是文件路径，而应该是 Evidence。

统一一个逻辑引用协议，例如：

evidence://workflow/<run>/<artifact>
experience://growth/<id>
skill://growth/<id>
contract://workflow/<id>

这些只是稳定 ID，不要求改变三套 runtime 的物理目录。

每份重要执行产物都被 normalizer 描述为：

evidence_id
producer_component
demand_ref
task_ref
experiment_ref
kind
native_source
sha256
observed_at
result

然后生成：

generated/index/evidence.json

只索引，不搬文件。

这样三套 runtime 可以永久保持各自格式；本体获得统一的证据语义。

五、建立真正的执行 → 学习闭环

建议链路变成：

Demand
→ Task / Experiment
→ Contract 执行
→ Probe / self-heal
→ Evidence / Drift
→ Experience Candidate
→ 人审
→ Experience
→ Skill

其中关键的一步是 Experience Candidate。

它应该是生成件，不是真源：

generated/learning/candidates/...

触发条件必须确定，例如：

出现新的 drift signature；

同一自愈路径重复成功；

Probe 从失败恢复且形成可解释措施；

Experiment 达到 success rule；

人工明确标记“值得沉淀”。

生成 Candidate 时必须自动携带：

Demand → Task/Experiment → Contract/Probe → Evidence hash

所以接受为 Experience 后，不可能只剩一句脱离现场的“经验”。

还需要一个 Learning Coverage Gate：

任何满足沉淀触发条件的 Evidence，必须最终出现一种 disposition：

accepted / linked_existing / rejected_with_reason / pending_review

否则 FAIL。

这样“工作流发现问题却永远进不了经验库”从纪律问题变成机器可检测的问题。

六、反向链必须建，但只能建到“提案”

经验 → 契约这条链值得做，但绝不能自动改 Contract。

正确闭环：

Experience
→ Contract Change Proposal（生成件）
→ 人审批准
→ 修改 20_ 原生 Contract
→ 干跑
→ Apply
→ Probe/Health
→ 新 Evidence
→ 回链原 Experience

即：

经验可以建议执行系统改变，但不能自己取得执行系统写权限。

Proposal 至少包括：

experience_ref
target_contract
evidence_refs
proposed_delta
expected_effect
validation_gate

只要没有人工批准，Contract 一个字节都不能变。

这既建立了反向有机反馈，又保留你已经要求的“技能安装需人审、不可逆/共享状态修改逐次批准”。

七、30_ 规范：不修改，而是给它接上执行器

不建议把 30_ 降级成普通文档；也不建议现在修改它的 Schema。

采用第三种关系：

Frozen Normative Baseline + Runtime Binding。

43 个现有文件保持原字节、原 MANIFEST。

在 30_ 外新增：

machine/spec_binding.yaml
runners/check-conformance.mjs

spec_binding.yaml 不是第二套 Schema，只描述：

四个原 Schema 在哪里；

哪个 runtime 对象对应哪个 Schema；

哪个 adapter 做字段映射；

校验模式。

check-conformance.mjs 必须真正调用 JSON Schema validator。

目标分两层：

第一阶段： 当前实现 → adapter → Spec-compatible object → 原 Schema 校验。

第二阶段： 如果证明不会破坏既有消费者，让 generated/state/D-xxx.json 本身直接满足 state.schema.json，逐步消灭 adapter 差异。

不能为了通过 Schema 而编造字段。例如没有真实 Experiment，就应是 schema 允许的空集合；若原 Schema 不允许真实世界状态，则 conformance 必须 FAIL，暴露规范差距，不能偷偷填假值。

这样四份 Schema 第一次成为会让流水线变红的东西。

八、Human View：保留“一套视图系统”，不是“一张文件”

最终用户入口建议固定：

D:\Work\Home.md = 唯一默认入口。

generated\human\ 可以继续包含多个详情页，但它们属于同一个生成视图系统，不是平行真源。

Home 只展示五件事：

当前 Demand → 当前 State → Active Task/Experiment → 最新 Evidence → 已沉淀 Experience

外加一个异常区。

每一条 Task、Experiment、Experience 必须拥有：

稳定逻辑 ID；

原生 source_ref；

Evidence 链；

若存在则 Experience 链。

详情页可以复杂，首页不复杂。

30_\01_HUMAN_VIEW 和 09_OBSIDIAN_ASSETS 保留为冻结设计参考，不再作为第二套现行 Human View。

Obsidian 默认入口应切到根 Home.md；这是一次可逆配置变更，但如果配置属于共享状态，执行时仍应单独请你批准。

外发继续只从掩码投影产生，不能因为内部加了 Evidence 链而绕开现有三档 redaction。

九、确定的全链传播

一次真实 Demand 变化，终态应严格走：

Demand 真源修改
→ Task adapter 读取各原生任务
→ Experiment projection
→ Component health + Contract/Probe Evidence
→ Evidence index
→ Current State
→ Learning candidates / Experience links
→ Human View
→ Masked external projection

任何一步只能读取上一步或者原生真源。

禁止出现：

Human View → 回写 State
State → 回写 Task
Experience → 自动写 Contract

从而保持方向单一。

十、“不值得融合”的边界

三套 runtime 目录不要物理统一：它们属于不同执行生命周期，统一路径只能制造新耦合。

Task 的原生存储格式不要强制统一：统一 adapter 和语义即可；Flash 模型不应承担全库格式迁移风险。

Skill 与 Contract 不要合成一种对象：Skill 是经人审的可复用能力，Contract 是执行约束，生命周期不同。

Probe 不要升级成全局业务对象：它只是证据生产者。

Drift 不要再建独立台账：作为 Evidence 类型足够，否则又产生一份状态。

10_ 与 20_ 的归档/快照策略无需统一：证据只需要统一 hash、来源和可追溯性。

30_ 的 43 文件不要为了“看起来一致”而重写：冻结规范基线本身有审计价值。

外部掩码投影与内部 Human View 不应合并：两者安全边界不同。

不要建中央“大 Task 表”取代三个原生执行真源：本体应统一可见性，而非夺走子系统自治。

不要自动完成 Experience → Skill / Contract 的晋升：知识治理与执行变更继续保留人工批准。

风险

Schema 真实不兼容：一旦首次启用真正校验，现有生成物很可能立即暴露历史字段偏差。

旧工具依赖两个子 project.yaml：直接删除可能造成隐性消费者故障，因此必须先转生成兼容件。

Task 文本格式不够稳定：Markdown 看板若允许自由格式，adapter 需要严格限定机器可解析区。

Evidence 过量：若没有确定触发规则，所有 runtime 日志都进入学习层会把经验库变成垃圾桶。

经验反向污染执行：如果 Proposal 与 Apply 边界不严，学习系统会间接获得工作流写权限。

绝对路径残留：只改显眼的 owner_skill 而漏掉其他路径，会形成半迁移状态。

视图双轨继续存在：Obsidian 不切默认入口时，即使后端完成融合，用户体验仍然表现为两个系统。

生成索引被误当真源：所有 generated/ 产物必须明确禁止人工写入，并用输入指纹证明可重建。

实施步骤
1. 冻结并证明当前基线

记录现有三个 project.yaml、三个 Task 真源、四份 Schema、主要 Contract/Probe/Experience 输入和 30_ MANIFEST hash；跑一次现有完整 干跑 → Apply → 健康 → 再干跑，保存结果。

这步怎么真失败： 30_ 任一现有文件 SHA 与 MANIFEST 不符、现有首页/健康链不绿、sentinel 无法真打开，立即停止迁移。

必须最先做。

2. 先建“事实所有权表”，不改任何真源

实现只读 authority-check.mjs，明确：

Demand → machine/demands
core Task → machine/TASKS
growth Task → 10_看板
workflow Task → 20_看板
Experience/Skill → 10_
Contract/Probe evidence → 20_
State/Human → generated

同时完成三个 project 字段逐项分类。

这步怎么真失败： 任何一个字段或状态事实无法确定唯一 owner，或者同时被两个可写文件认领，检查非零退出。

这一步之后，Task、Identity、Evidence 三条实现可以并行开发。

3. 建 Task 只读统一索引和单写 Gate

写三个 adapter，生成 generated/index/tasks.json；不搬任何 Task。

加入 duplicate/authority/status-location 检查。

这步怎么真失败： 人工把一个 10_ Task 复制进 machine/TASKS.yaml，或者给 §八增加状态并制造不一致，Gate 必须非零。

4. 收敛 Project 身份

把根 project.yaml 定为唯一 System identity，把 Component 元数据归到现有 registry；两个子 project.yaml 首先改成由生成器产生的 compatibility projection。

暂时不删文件。

这步怎么真失败： 手改子 project.yaml 中 name/status/stage 后运行检查，必须报 projection drift；根 identity 与 registry 出现重复可写身份字段也必须失败。

5. 消除硬编码跨树路径

增加逻辑 resolver：

component://、skill://、contract://、evidence://

先让 resolver 能解析现有绝对路径与逻辑 URI，两种模式产出同一目标 hash；验证后再把 20_ Contract 的跨树引用迁成逻辑 URI。

这步怎么真失败： 删除/移动目标后 resolver 仍只因“目录存在”判成功，则测试失败；必须实际打开目标并校验预期内容，与现有 sentinel 原则一致。

6. 建 Evidence Index

先索引现有 20_\runtime、probe/drift 实测产物，不改变其生成方式；为每份证据计算 hash、producer、native source，并关联到 Demand/Task。

这步怎么真失败： 篡改一份证据一个字节后 hash 不变化、证据 source 无法打开、或 State 引用了不存在的 evidence_id，都必须非零退出。

7. 把 Experiment 从空字段变成真实语义

给 Task adapter 支持实验字段；仅在真实 Demand 确有假设/成功规则时创建 kind=experiment Task，由其生成 Experiment projection。

不要为了填满 active_experiments 制造假实验。

这步怎么真失败： 一个 Experiment 没有 Demand、Task、hypothesis、success rule 或 Evidence owner 时，禁止进入 Active State。

测试可用 fixture，生产数据必须是真实实验。

8. 接通 Evidence → Experience

增加 learning-bridge.mjs，根据确定触发条件产生只读 Candidate，并要求 disposition 闭环。

正式 Experience 仍只能在人审后写入 10_。

这步怎么真失败： 制造一个满足学习触发条件的 drift，而系统既没有 Candidate、既有 Experience 链也没有 rejection reason，Health 必须变红。

9. 建 Experience → Contract Proposal

从已审核 Experience 生成 Contract Proposal，但生成器没有写 Contract 的权限。

真正 Apply 必须逐次人工批准。

这步怎么真失败： 未批准 Proposal 能导致 20_\contracts 字节变化，则属于严重 Gate 失败；批准后的 Contract 改动若没有产生新的 Probe/Evidence，也不得标记闭环完成。

10. 让 30_ 四个 Schema 第一次真正执行

不改 43 文件；新增外部 binding 与 validator。

逐一接 Demand、Task、State、Experiment。

这步怎么真失败： 给对象删除必填字段、塞入错误类型，validator 必须返回非零；如果同样错误仍能通过，Schema 仍然只是摆设。

若当前生产对象不通过，先修 adapter/生成器；不能修改冻结 Schema 来迁就实现。

11. 重建 Current State

generated/state/D-xxx.json 的输入扩大为：

Demand + normalized Tasks/Experiments + component health + Evidence + Experience links + human decisions

State 自己仍无写口。

这步怎么真失败： 改一个真实 Task 状态或 Evidence 后 State hash 不变化，或者 State 出现无法回指 owner/source 的 Active Task，立即 FAIL。

12. 收敛 Human View 并切默认入口

让根 Home.md 成为唯一默认用户入口，其他 Human 页面全部由同一生成链产生；每一个 Active 对象必须可以点击/解析回原生 source/evidence。

确认后再切 Obsidian 默认入口。

这步怎么真失败： 手改 Home 继续触发现有 HOME DRIFT；删除一条原生 Evidence 后 Human View 仍显示为有效链接；任何生成行没有 source_ref 时，新 Gate 失败。

13. 把新 Gate 接入现有顺序，而不是另建第二条流水线

最终顺序建议扩成：

新只读 Gate
→ 现有干跑
→ Apply
→ 现有健康 + 新 conformance/authority/provenance/learning Gate
→ 再干跑

不要更改已验证链条之间的相对顺序。现有机制已经证明 drift 会经子进程非零传播为整链失败。

这步怎么真失败： 做一组 canary：重复 Task、手改 Home、破坏 sentinel、篡改 Evidence、非法 Schema 字段、遗漏 Learning Candidate；六种故障任一种没有使整链变红，都不能宣布融合完成。

14. 最后才退役遗留写口

在至少一次真实 Demand 完整跑过：

Demand → Task/Experiment → Evidence → Experience → Human View

并通过 canary 后，才将两个子 project.yaml 正式删除或永久固定为生成兼容件，并把旧 Human View 标记为历史设计参考。

这步怎么真失败： 删除 legacy 文件后仍有 runner/Contract/README 的活动引用，或者任何用户操作又需要进入旧入口修改状态，迁移不算完成。
