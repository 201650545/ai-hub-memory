upstream_outcome 的最小映射按这个优先级做：

LOCAL gate reject                         -> LOCAL_POLICY_SKIP
scheduler says not due                    -> NOT_DUE
socket/DNS/timeout/proxy exception         -> TRANSPORT_ERROR

structured inner provider error first:
  balance/credit/billing/quota exhausted  -> AUTH_OR_POLICY
  rpm/tpm/rate limit/too many requests    -> RATE_LIMITED
  explicit model unknown/not found        -> MODEL_NOT_FOUND
  invalid/unsupported param/schema        -> CONTRACT_ERROR

then outer HTTP:
  valid 2xx payload                       -> OK
  401/403/402                             -> AUTH_OR_POLICY
  429                                     -> RATE_LIMITED
  404 + explicit model-not-found          -> MODEL_NOT_FOUND
  400/415/422                             -> CONTRACT_ERROR
  5xx                                     -> UPSTREAM_ERROR

关键点是账户欠费不要归 RATE_LIMITED。保留九大类不再加第十类，在 AUTH_OR_POLICY 下加 reason_code=AUTH_FAILED / ACCOUNT_BALANCE / ACCOUNT_QUOTA / POLICY_DENIED。OpenRouter 现在官方资料也区分 402 可用余额问题与 429 rate limit；429 属于可重试型，而 400/401/402 不应按同类重试。

我不接受的部分及理由

我不接受把 seat_id 做成独立 data/seats.json。43 席规模完全没有必要付出双真源、同步和回滚复杂度；member 本身就是身份落点。

我也不接受把 quota_guard 免费名单 snapshot 一并强行改成 seat_id。它描述的是“这个上游模型现在是否满足免费条件”，不是“这个模型目前挂在哪个编排位置”。证据里 _allow_via_snapshot 本来就是 runtime 对免费名单的查询点。

第三，我不接受“一个开关翻开就能无痕恢复自动 ADD”。代码当然保留，但恢复必须同时带一个郭老师审批编号进入审计，例如：

OR_FREE_AUTO_ADD=1
OR_FREE_AUTO_ADD_APPROVAL_ID=GR-2026xxxx-xxx

否则几个月后没人能证明自动 ADD 为什么重新获得授权。

第四，我不接受现在就因为 6 天 429 自动把两席永久移到末位，或者自动创建“同席位备胎”。前者改变持久编排策略，后者更直接涉及新增/替换，均应该进入提案。今晚能自动做的是 runtime 429 cooldown，而不是写 model_routes.json。

风险

最大风险不是代码量，而是状态迁移时把旧 (cid,model) 的共享历史错误复制给多个 seat_id。因此重复旧键必须留下 legacy_by_key，新席位开新 epoch，而不是为了“历史连续”硬继承一个本来就无法归属的 streak。

第二个风险是 classifier 过度依赖 message 文本。upstream_outcome 应优先吃结构化 status/code；文本关键字只作最后补充，而且要保留 raw_http_status / upstream_status / upstream_code / reason_code，以后规则错了还能重判历史。

第三是自动 ADD 的 TOCTOU：今天生成 proposal，明天郭老师批准时目录价格可能已经变。执行 proposal 前必须重新做费用安全检查；若价格证据变化则原 proposal 失效，生成新 proposal，而不是照旧 ADD。

第四是 429 circuit breaker 误伤：probe 429 不应直接控制生产流量。只有实际 runtime 请求发生 429 才开 circuit；有 Retry-After 就严格服从，没有再采用本地有限 cooldown。这样六天探针证据可以触发“建议降序”，但不会凭每天一次采样把一个实际上还能服务用户的席位整天禁掉。

需郭老师拍板

现在真正需要郭老师拍板的只剩两件，其他都是实现完整性，可以直接做。

第一，OpenRouter 自动 ADD 的最终授权模型。 当前先保持 AUTO_ADD=off → 自动生成精确提案 → 人批后执行。需要郭老师明确：以后是“每次 ADD 都批”，还是“一次批准恢复持续自动 ADD”。如果是后者，把这次批准编号固定进入 OR_FREE_AUTO_ADD_APPROVAL_ID，之后所有自动 ADD 审计都引用它。

第二，两条 6 天 RATE_LIMITED 席位的持久编排动作。 我的提案给郭老师应该写成：“保留席位，但建议移至各自主链末位；暂不新增备胎。运行时已用 429 cooldown 避免每个请求反复撞限流。” 如果郭老师批准，再经 routes_writer 调整顺序；没批准就只做 runtime cooldown，不动真源。
