我只按你给的 R5 原文裁，不沿用 R1–R4 的摘要。原文已经把几个关键事实钉死：提炼器现在能“先在内存算完再动盘”；运行时 skill loader 只扫描 skillsDir 的一层子目录并寻找顶层 SKILL.md；账面“已安装”已经与实际运行时不一致；而当前融合闸的主要红来自“可变探针产物却被当作 hash 固定证据”。
Q1：Gate 报 FAIL 时还能不能写新草稿
(a) 裁定
你现在这个边界不成立。
GATE|DISTILL|FAIL 之后仍把新草稿写进正式草稿区，再用 exit=1 表示失败，这不是一个真正有约束力的闸门。你给自己的理由——“草稿不改变 Agent 当前行为，因此历史问题不该冻结新增吞吐”——正是这里需要顶回去的地方。
你把“没有立即影响 Agent 行为”偷偷替换成了“没有状态后果”。但草稿区本身就是闭环状态：它会扩大未来待判断、待晋升、待血缘验证的集合。**一个失败闸门如果允许它所控制的主要产物继续增长，FAIL 就逐渐退化成告警。**你自己在 R5 里已经准确指出了这个风险。
尤其是你现在已经实现“所有决策先在内存算完、最后才动盘”，因此这里不存在“技术上很难事务化”的借口。既然可以预先知道本轮会 FAIL，就可以做到零草稿提交。
我的裁定是：
只要本轮最终状态仍叫 FAIL，正式草稿写入数必须为 0。
允许写的只有诊断性产物，例如 gate report、候选清单、原因记录；不能把候选落成闭环认可的 draft。
如果某些旧对象已经被显式退役/隔离，那应通过已有双事实规则把它们排除出当前有效集合。不要再创造“FAIL 但允许写”的第二语义。否则以后每个失败码都会来争取一个吞吐豁免。
(b) 可编码判据
最简单而且最不容易被你以后绕开的规则是：
preflight 全部在内存完成IF final_distill_gate == FAIL:    allowed_mutations = {gate_report, diagnostic_log}    new_draft_count = 0    draft_manifest_mutation = 0ELSE:    才允许原子提交本轮新草稿和合并后的清单
其中在计算 final_distill_gate 前，至少机械检查：
current_effective_set  = 盘上 draft 全集  - 明确 retired 的对象  - 明确 quarantined 的对象IF ∃ x ∈ current_effective_set:       x.lineage_valid == falseTHEN FAILIF ∃ x:       x.promotable == true       AND x.lineage_valid == falseTHEN FAIL
第二条是 R5 明写已经落地的 R4 规则；第一条是我在这里给出的事务边界。
有一个很重要的语义要求：**如果你以后真需要某种“有异常但允许新增”的状态，给它另一个明确状态，不要复用 FAIL。**否则你永远无法仅凭磁盘 artifact 判断“这个红到底有无物质后果”。
证据环 Gate 35/36 是否同规则？
不同，但区别不是“证据环比较宽松”，而是写操作的性质不同。
草稿创建是在增加新的系统声明/候选资产；索引或快照重建则可能只是从既有事实做可重复的派生计算。因此证据 Gate 红时，可以允许一种非常窄的“修复型写入”：
ALLOW_REBUILD =    target 被契约明确标为 derived/regenerable    AND rebuild 只读取既有源事实    AND rebuild 不修改：        contract        baseline        expected hash        原始 probe 输出        任何被钉死的 source evidence
只要重建行为会“顺手更新期望 hash”“重新捕获 baseline”“覆盖产生红灯的原始证据”，就必须拒绝。R5 已经明确：当前主要问题恰恰是可变探针产物被登记为 hash 固定证据，而处置权在契约授权维护方；重建工具无权靠重新钉 hash 把红洗绿。
如果现有磁盘契约没有机器可读字段能区分“可重建派生产物”和“证据/基线”，那这一例外现在就不能安全编码：先 fail-closed，延期裁定例外。
(c) 需要等 runtime 信号的部分
Q1 本身基本不需要 runtime 才能裁。唯一该延期的是：某类 draft 是否真的在运行时完全不可见、是否存在旁路 loader 会读取草稿区。R5 没给这项证据，所以我不会拿“Agent 不读草稿”进一步放宽规则。
而且即便以后证明完全不可见，我仍不会因此改成 FAIL-but-write；最多影响你是否需要把候选保存在一个纯诊断 artifact 中。

Q2：第一条真 skill 的最小“生效”判据
(a) 裁定
这里必须把你现在混在一起的两个状态拆开：
“已安装且可被 loader 发现”现在可以机械裁。
“已经生效”现在不能完整裁。
R5 给了一个非常有价值的反例：有一条自产 skill 已经存在于运行时，却因为没有顶层 SKILL.md 而永远不会被一层 loader 发现。这已经证明“目录存在/复制成功 ≠ 安装成功”。
所以：
允许探针尚未建立时先安装，但只能标记为 installed/loadable；不得标记为 effective。
如果 S3 的完成条件现在把二者统称“装上且生效”，那这个条件本身应拆开，否则你会为了让 S3 过关而制造假绿。
(b) 一次脚本可跑完的静态验收
仅依据 R5 已经能确定的最低检查，我会这样判：


目录层级
realpath(skill_dir).parent == realpath(skillsDir)
必须是 loader 扫描目录的直接子目录。
拦：装进二级/三级目录、肉眼看起来存在但 loader 永远不遍历。


顶层入口
<skillsDir>/<skill>/SKILL.md
必须存在、是普通可读文件。
拦：R5 现场已经出现的“只有 scripts/、无顶层 SKILL.md”。


按真实 loader 算法重新发现
验收器不要自己递归搜索；必须复制运行时已经确认的：
readdirSync(skillsDir) -> path.join(dir,'SKILL.md') 这一发现语义。
最终候选必须出现在这次发现集合内。
拦：验收脚本比真正 loader “聪明”，产生假阳性。


front matter 能解析，且 name 非空
R5 的全盘 census 已经明确使用 front-matter name 去重，因此至少这个字段可以机械检查。
同时要求它在 loader-visible 集合中的身份不产生你无法解释的重复。
拦：入口存在但身份无法稳定识别。


安装版本与预期源版本一致
对即将安装的那一条，用内容 hash/明确的源文件身份做比对：
expected_source_hash == installed_SKILL_hash
拦：真源只有 2 个条目、运行时已有同族 20 条这种情况下，复制错版本或误把旧安装当新安装。


机器生成的安装状态必须来自上述观测
只有 1–5 全绿才可以输出：
installed = trueloadable = true
任何一项红：
installed = false
至少绝不能继续保留人工 README 里的“已安装=true”。


有两项现在不能假装能验：


“触发词根本没注册”：R5 没说明 Loomy 的触发注册到底存在哪个字段/文件，也没给它的解析契约。


“实际被调用”：这是 runtime 事实，纯静态磁盘结构证明不了。


因此我不会替你编一个不存在的 front-matter 字段然后说脚本检查它。
探针未建，能否先装？
能。
但临时状态只能是：
installed = GREENloadable  = GREENeffective = UNKNOWN / NOT_YET_PROVEN
如果你的系统只能接受红/绿二值，那么在探针/运行记录出现以前：
effective = RED
这不是说 skill 已证明失效，而是说**“有效”这个主张尚无证据**。不要把“没证伪”当“已证实”。
这也解掉你说的死锁：skill 不需要等待探针才能进入运行时；探针也不需要伪造一个已经 effective 的 skill。安装后，probe/runtime witness 再把第二个状态翻绿。
“已安装”由谁写？
不能再由真源 README 的人手列写。
它应该由一个读取运行时实际目录的验收/普查程序派生写出。README 最多展示生成结果，不得成为事实源。
建议事实来源明确成：
installed/loadable  <- runtime filesystem + loader-equivalent discovery + exact artifact identityeffective  <- runtime invocation/probe evidence
安装器本身也不应该因为“我复制成功了”就自证 effective=true。
(c) 延期到 runtime 信号
真正的 effective=GREEN 至少要等一条运行时证据能表明：
当前安装的这一个 skill revision    ↓实际被 loader/dispatcher 采用    ↓产生了调用/触发事件
而且这个事件最好能关联到当前安装版本，不只是同名 skill 的某条历史日志。否则旧版本三个月前调用过一次，也会把今天刚装坏的版本误判绿。
R5 没告诉我现有运行事件台账是否保存足够的 revision/hash 关联，所以这一点应明确延期，不能现在假裁。

Q3：owned_by: runtime 排除应该落哪一层
(a) 裁定
权威声明必须落在契约层 contracts/*.yaml。
然后：


triage/census 读取契约并执行；


census 生成物里可以有 owner / excluded / rule_id 等派生列，用于审计；


但生成物里的那一列不能反过来成为政策真源。


原因很直接：owned_by: runtime 不是一次扫描观察到的自然事实，而是“谁负责任、哪些东西不进我们的红”的治理边界。
如果你把它硬编码在判定器里，判定器就在偷偷自写契约，正撞上 R5 引用的 R4 原则——生产者和判定器无权自宣契约内容。
如果只放 census 输出列里，则更糟：生成器可以在产生红之后再给自己加一列把红解释掉；下一次重新生成还可能丢失。
所以结构应该是：
contract       = 权威政策triage/census  = 执行政策census column  = 记录“这条是依据哪个 contract rule 被排除的”
(b) 谁写；写错怎么发现
写的人应是契约授权维护方，不是 census、triage 或 skill 生产器。R5 对另一项契约问题已经用了同一个责任边界：可变探针/hash 冲突的处置权在契约授权维护方。
但“授权的人写”不等于“写错就没办法发现”。至少加三个机械不变量：
1. runtime_excluded_set ∩ our_owned_generated_set == ∅
任何已由你们闭环自产血缘证明为 own 的资产，被 owned_by: runtime 规则吞进去，立即红。这个检查可以防止为了减少 3210 个技能的噪声，把自己的 19 条一起豁免掉。
2. 同一资产不能同时命中冲突 owner 规则
例如同时 owned_by: runtime 和 owned_by: self，契约自身就是红。
3. 无证据匹配的条目保持 UNKNOWN，不得默认 runtime
这是最重要的防“排除范围越写越大”规则。一个 selector 没有依据覆盖的东西，不得因为“看着像程序自带”就被消失掉。
每个 census 行最好保留派生审计信息：
owner=runtimeowner_rule_id=<contract rule id>excluded_from_our_red=true
这样 2576 个废弃/归档项或其他外部项以后为什么没进红，是可追溯的，而不是重新靠人解释。R5 已经显示全盘规模远大于自产族，因此没有这个边界会持续制造噪声。
触发词撞车
只记账不够。
如果外部 active skill 与我们的 skill 存在实际 dispatch 冲突，你已经有行为不确定性；“记录一条 collision”并没有消除它。
在“绝不改对方文件”的边界下，我们能做的最强、同时不越权的动作是：
collision detected    => OUR skill activation/install gate FAIL    => 我们自己的 skill 保持 inactive / quarantine    => 外部 skill 不修改
然后只有通过修改我们自己的触发定义、重新验收且碰撞消失，才能恢复激活。
也就是说责任边界是：

我们不能修别人，但完全可以拒绝让自己的冲突资产进入 active set。

不要靠“运行时也许会选对一个”来赌 dispatcher 优先级。
不过这里还有一个必须延期的部分：R5 没给出触发词的机器可读来源，所以**“如何可靠枚举双方 trigger set”目前还裁不了**。在这件事没有磁盘级可枚举证据前，你只能裁定处置原则，不能声称 collision detector 已经完整可实现。

你说“R4 可能已经裁过”的三处，我认为都没有完全覆盖 R5
第一，血缘双事实规则没有裁到 Q1 的事务语义。
R4 决定了什么对象有效、什么组合必须失败；它没有回答“总体失败后还能不能提交新的主要产物”。所以 Q1 不是重问。我这里补的是：FAIL 必须阻断它所控制的正式 state transition。
第二，“可变产物不能 hash 钉死”已经裁了模型错误，但还没有完成处置。
R5 现在仍有主要业务红来自这件事，说明“裁定正确”与“运行问题解决”是两回事。处置权已经明确属于契约授权方；别让执行器自己更新 hash 把红消掉。
第三，“不重捕 baseline”没有自动回答“能不能重建 index/snapshot”。
重捕基线改变期望事实；重建纯派生索引可能只是重新计算观察结果。这两个操作必须机械区分。否则一句“不重捕”会误伤正常修复，或者反过来被“我只是 rebuild”拿来偷偷改 baseline。
我看到的模式性问题
你在 Q1 的确正在为了吞吐把闸门语义往后挪：先获得产出，再在末尾承认失败。这种实现短期很顺，但会把“红灯”训练成“可以继续做事的红灯”。后面每个团队成员都会合理地问：“既然上一次 FAIL 也写了，为什么这次不能？”
Q2 是另一种同型错误：把文件存在、loader 可见、实际生效三个不同事实压成一个“已安装”字段。 README 漂移不是偶发维护疏忽，而是这个状态模型本身把观察事实交给人手维护的必然后果。
Q3 则是第三种：试图让判定器顺手定义自己的责任边界。 这会让“减少噪声”非常容易滑成“把不想看的红写进排除逻辑”。把 owner 边界放在契约层，判定器只执行，是这里真正重要的防线。
一句话收束这轮：
Q1：FAIL 就不要提交正式草稿；吞吐不能靠削弱 FAIL 获得。
Q2：现在只能证明 installed/loadable，effective 必须等 runtime witness。
Q3：ownership 是契约，不是 census 自己的解释；冲突时最多牺牲我们自己的激活，不能只记账。
