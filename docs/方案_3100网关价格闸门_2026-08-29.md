## 1. 背景与实证（全部 file:line 已复核）

### 1.1 扣费路径事实
网关对外模型列表与可路由模型集合**故意不一致**：

- 对外列表应用渠道策展：`channels.py:1320-1326`——注释原文「渠道模型策展：已选列表存在时，**对外只暴露已选（详情页仍可看全量、按名调用不受限）**」。
- 路由解析用**全量在线目录**：`channels.py:1426-1435` `model_providers` 包含搜索遍历 `st["models"]`（来自 `channel_health` `channels.py:893/896`），不读 `channel_models.json` 的 selected。

后果（S-20260829-05 实测）：190 个可见模型名中 **12 个**会解析到 zenmux 收费款且 eligible=True（claude-sonnet-5→anthropic/claude-sonnet-5、gpt-5.6-sol→openai/gpt-5.6-sol、glm-5.2、hy3、mistral-large-2512 等）。zenmux 166 款中仅 5 款真免费，其余 161 款收费。

### 1.2 现有价格语义为什么兜不住
| 现状 | 位置 | 问题 |
|---|---|---|
| `billing_type` 渠道级硬编码 | `channels.py:48-250`（zenmux 整体标 `free`） | 渠道级标签在 zenmux 上**已经错了**（161/166 收费），不能作放行依据 |
| `_channel_sort_key` 免费优先 | `channels.py:1273` | 只影响**排序**，不做**拦截** |
| `free_models` 字段 | 写入 `channels.py:126`+custom_channels；唯一读取 `_augment_health` `channels.py:940` | 只进健康展示（`/api/channels`），**路由/准入零引用** |
| `rate_limit._is_free_model` | `rate_limit.py:86-88` | 按 `:free` 后缀猜，仅用于分桶 |
| 上游价格 API | 全仓 grep `pricing/price/cost` **0 命中**（仅 `get_balance` `channels.py:767-815` 探余额展示） | 网关**没有任何 per-model 价格数据源** |

启发式不可靠的反例（本机真实配置）：`unified_models.json` 的 deepseek-free 成员 `modelscope: deepseek-ai/DeepSeek-V4-Pro-0813` 名字带 Pro 但在魔搭走积分、积分用完直接不可用而不产生账单；openrouter 成员带 `:free` 后缀但同名的非 `:free` 款收费。**闸门必须基于逐渠道逐模型的已验证定价事实，而非名称猜测。**

### 1.3 准入判定序（闸门插入点）
`api_gateway.py:482-493`（`build_route_plan`）：`disabled → no_key → unreachable → capability_mismatch → blocked → quota`，**无价格项**。能力层哲学（`capabilities.py:129-138`）：仅显式 False 才阻断、未知默认放行（fail-open，向后兼容）。
真实转发唯一入口准入：`api_gateway.py:341` `check_candidate`；`chat_completion` 直连路径 `channels.py:1166` 在 `api_gateway.py:358` 换上游真名后 POST——**闸门加在准入序即可覆盖全部转发路径**（管理端点 smoke 亦走同链）。

## 2. 目标 / 非目标

**目标**
- G1：任何解析到「已验证收费」上游模型的直呼请求，默认不产生转发（消除意外扣费面）。
- G2：「未验证定价」的模型默认不放行（计费面 fail-closed，对齐 wildcard 门先例），可用显式授权放行。
- G3：编排组（fast / deepseek-free）既有调用**零误伤**——注意 M1 后组不再是豁免项，该目标从「结构性保证」降为「**待证伪的经验断言**」：之所以仍预期零误伤，是因为组成员已逐款实测且须登记为 fresh `free`；P2 `observe` 期必须以真实流量证明组内命中为零，才允许 enforce（回归可证）。
- G4：定价数据有唯一真源、可维护、可溯源（记录验证时间与证据），不复制飞书 Base。

**非目标**
- 不做配额/预算管理（余额监控、月度上限另案）。
- 不改「按名调用不受限」的策展语义（见 §3 方案对比；那是另一个决策）。
- 不做自动降级到免费等价模型（Q3 已拍板：不静默降级，见 §7）。
- 不动 :3000 聚合网关。
- **责任边界（评审补入）**：闸门只保证「计费属性正确」，**不保证同名模型跨渠道能力等价**。第三方镜像渠道可能把不同量化/不同上下文/不同底座挂在同一显示名下；被价格维度筛掉后 failover 到另一渠道同名款，实质可能是隐性能力替换。那是策展层的问题，不在本方案范围，但必须写明免得日后算到闸门头上（评审 ③-2 / ④ 反例 1）。

## 3. 方案对比与选择

| 方案 | 内容 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 让路由应用 `channel_models.json` 策展（可路由集=可见集） | 零新数据源，堵住 12 名 | **推翻**「按名调用不受限」既有设计语义；策展外免费名全被误伤；策展清单变成隐式计费开关，职责混乱 | 否 |

## 4. 设计

### 4.1 定价真源：`model_pricing.json`（新文件，`D:\项目\data\search_gateway\`）

```json
{
  "version": 1,
  "channels": {
    "zenmux": {
      "models": {
        "dots-studio/dots3-note-prev": {"class": "free",  "verified_at": "2026-08-28", "evidence": "S-20260829-05 pricings 逐款核算"},
        "anthropic/claude-sonnet-5":  {"class": "paid",  "verified_at": "2026-08-28", "evidence": "S-20260829-05"}
      },
      "default_class": "paid"
    },
    "modelscope": {"models": {"deepseek-ai/DeepSeek-V4-Pro-0813": {"class": "free", "billing_model": "quota", "account_bound": true, "verified_at": "2026-08-29", "note": "名称含 Pro，魔搭积分制：积分用完直接不可用、不产生账单"}}, "default_class": "unknown"}
  },
  "global_default_class": "unknown"
}
```

- `class ∈ {free, paid, unknown}`。分类标准（Q1 已拍板）：闸门语义定义为「**合规使用下不产生账单**」——超额后仍会出账的算 `paid`；额度/积分用完只是**服务被拒而不会产生账单**的算 `free`。
- 配额型（魔搭积分、nvidia 免费 credit 等）归 `free`，但必须显式标注 `"billing_model": "quota"` + `"account_bound": true`：**这类"免费"是当前账号的状态，不是渠道的属性**——充值、换 key、活动到期都可能翻转。对 `account_bound` 条目使用更短的复核窗口（`QUOTA_STALE_DAYS`，默认 7），过期降 `unknown`。
- 每渠道 `default_class` + 全局 `global_default_class` 兜底。已知收费大户（zenmux）渠道级默认 `paid`，新上架模型天然落入被拦侧，需验证后才升级到 free——**默认收紧、白名单放行**的不对称设计。
- `verified_at` 超 `PRICING_STALE_DAYS`（默认 30，可配）自动降为 `unknown`（对齐 TOOLS.md §6.5 新鲜度纪律：陈旧不用）。**陈旧化悬崖缓解（评审 ④ 反例 3，N4 已拍板：两条都做）**：①到期前 7 天先在路由日志/覆盖率面板预警，不当天硬翻转；②P1 首批条目 `verified_at` **人为错开**（实测日期本就分布在 08-28/08-29，登记时按渠道再错峰），避免同一天集体降级造成「昨天正常、今天大面积 403」。
- 数据维护：初期**手工实测登记**（来源即 S-20260828-01 / S-20260829-05 已精测的结论），后续可选上游 pricings API 拉取器（`rate_limit`/健康缓存同款 mtime 热载 `_cached_json` `channels.py:264-281`，改文件免重启）。
- **人工复核节奏量化（M3）**：`PRICING_STALE_DAYS=30` 与 `QUOTA_STALE_DAYS=7` 只保护「已被标记为 stale 的条目」，保护不了这条时间差——**今天人工确认某模型 free，明天上游结束活动转 paid，本地 JSON 在剩余 29 天里仍写着 fresh free，闸门照常放行收费流量**。在拉取器落地前，这个敞口只能靠节奏压：**所有 `class=free` 条目（含非配额型）统一 ≤7 天复核一次**，并在文件里记 `last_reviewed_ok` 时间戳使节奏可被脚本审计（复核脚本据此报「超期未看」）。拉到 P2 观察期数据后再评估是否放宽；拉取器上线后此条由拉取器取代。
- 读取路径唯一真源：本 JSON。**不把价格写进 channels.json 的 free_models**（该字段维持现状仅作展示，避免双真源；**Q4 已裁定：保留字段 + 增加「与定价真源不一致则告警」的漂移检查，不删除**）。

### 4.2 判定：准入序新增 `pricing_gate`

`build_route_plan` 判定序变为：`disabled → no_key → unreachable → capability_mismatch → pricing_gate → blocked → quota`。

- 置于 capability 之后：能力不符的候选连查价格的必要都没有；置于熔断/限流之前：**熔断是运行时保护，闸门是静态属性**，先静态后动态，reason 归因清晰。
- 判定函数（新，建议 `pricing.py` 与 `capabilities.py` 同层同风格）：
  ```
  verdict(channel_id, upstream_model) -> {allow: bool, class: str, reason: str}
  ```
  - `class=free` → allow。
  - `class=paid` → **deny，除非显式授权**（§4.3）。
  - `class=unknown` → 按 `PRICING_UNKNOWN_POLICY` 处理（**默认 deny**，fail-closed，Q2 已拍板）。
- 候选被 deny 时：从候选链剔除、继续下一渠道（failover 语义不变）；**全链皆被 deny → 请求整体 403**（Q3 已拍板，不做静默降级），错误体 `{"error": {"type": "pricing_gate", "code": "model_pricing_blocked", "model": <请求名>, "reason": "class=paid|unknown"}}`。
- 与 Q1 的配合：配额型渠道（魔搭积分等）积分耗尽时是**上游返回错误**而非产生账单，闸门放行后由现有 failover/错误处理自然承接，不需要闸门参与额度判断。
- 跨渠道同名 failover **不属于** Q3 禁止的「静默降级」：Q3 禁止的是整链被拒后偷换**模型身份**；这里请求的模型名从头到尾未变，只是换一个能免费提供该名的上游，与 unreachable/blocked 既有 failover 语义一致（评审 ③-2）。真正的残余风险是「同名不同模型」，已在 §2 责任边界声明。
- 编排组展开（`load_unified` `channels.py:603`）**必须经价格判定（M1 改判，取代 v0.4「组即白名单、完全绕开闸门」的设计）**：组成员由人工登记并逐款实测（先例 S-20260828-01③），但**人工登记是有时间戳的事实，不是永久承诺**。分层控制：① **组配置文件本身闸门永不自动修改**（不静默变更成员）；② 组展开出的每个候选仍走同一 `verdict()`，**只有当前记录为 fresh `free` 的候选才允许转发**，`paid`/`unknown`/`stale` 仅在本次路由中剔除；③ 整组成员皆不可转发 → 显式 403（与 Q3 一致，不偷换成别的模型）。`POST /api/unified`（`channels.py:617` `set_unified_model`）**写成员时**照旧执行一次价格校验：新成员 class≠free 且无授权 → 拒绝写入（400）。
- **B1 + M1（P1 必做）组白名单双层防护**：v0.4 采纳的 Claude 方案是「离线核对 + 只告警、绝不自动摘除」，GPT 复核指出**这不构成控制**——写时校验管不到存量与入组后改价，而「只告警且路由继续无条件放行」的告警必然退化成没人看的噪音，等于整套 fail-closed 在调用量最大的路径上不成立。**改判后**：运行时的 fresh-free 校验（上一条）是防线，**离线组成员核对脚本（7 天周期＝N3）降级为「提前发现 + 留痕」**，用于在人类还能处理的窗口里把即将失效的条目挑出来，不承担兜底职责，同样**绝不自动改组**。**诚实记录代价**：这是本设计唯一改变既有高频行为的一条——`fast` / `deepseek-free` 首次真正受价格约束，一旦某成员被标错或到期降 `unknown`，最高频路径会开始 403。正因如此 §6 的 P2 `observe` 期是硬性前置（只记不拦），先用真实流量验证组内命中为零，才允许 enforce。

### 4.3 授权模型终态（B2：必须在写 schema 前定稿，不留到 P3 返工；**N1 已拍板采纳**）

评审认定原设计有真实 design smell：`API_GATEWAY_ALLOW_PAID` 一个开关身兼两职——「上线期临时观察（有终点的过渡态）」与「长期允许付费」，一旦有人为跑一次付费调用打开就容易忘关，恰好是本项目要消灭的「配置态默认放行」风险。改为两个正交概念：

- **运维态（生命周期）** `PRICING_MODE ∈ {off, observe, enforce}`：
  - `off`＝闸门本身故障时的应急熔断，完全不判定；
  - `observe`＝记日志/打标不拦截，P2 上线期专用，**预期有终点**；
  - `enforce`＝强制模式（缺省目标态）。
  - **`observe` 必须是「有到期时间的临时态」，不是一句约定（M2）**：设 `PRICING_MODE=observe` 时**必须同时**提供 `PRICING_OBSERVE_UNTIL=<日期>`，窗口上限 **7 天**；缺 `OBSERVE_UNTIL` 或超上限 → 按配置错误处理（同 3106 家族，拒绝启动）。**到期后不得静默继续 observe**：网关转入显式的 `pricing-config-invalid` 异常态（健康检查报错 + 告警留痕），要求操作者二选一——改 `enforce` 或重新批准一个新的观察窗口。原 v0.4 只写了「P3 之后只应在 enforce 与临时 off 间切换」，属纯文档约束，挡不住半年后仍挂在 observe 上；GPT 复核把它称为三态设计留下的永久 fail-open 后门，故必须机器化。NSSM 服务改环境变量需提权脚本配合重启（脚本库 `.tools\`，同服务注册先例）——所以命名与语义必须一次定对，否则改语义要再走一轮提权重启。
- **数据态（永久授权）** `model_pricing.json` 条目级 `"authorized": {"by": "user", "at": "...", "note": "...", "revoked_at": null}`：该条 paid 模型放行且日志标 `authorized_paid`。回答的是「这个付费模型是否被明确批准长期放行」，与运维态解耦。**审计记录 append-only，但授权本身必须可撤回（M5）**：`revoked_at` 非空即视为授权失效、该条回到 deny 侧，撤销动作本身作为新记录追加（谁、何时、为何），既保留历史又能真正收回。v0.4 原文只写「只增不删、可审计」，GPT 复核指出那等于一次长期授权永不可撤销——一个当年为跑通而批准的付费例外，之后再也关不掉。
- 配置错误 fail-closed：`model_pricing.json` 存在但**解析失败** → 启动退出码 **3106**（Q5 采纳建议：避开告警事件源 ID 3105 的命名空间，与 3102/3103/3104 同族），NSSM 映射 Exit 不 crash-loop；文件缺失 → 等价于「全部 unknown」，按 Q2 拍板结果默认 deny（观察模式下恒 allow + 记日志）。

### 4.4 可观测性
- 路由日志（`api_gateway.py:323-332`）新增：`pricing_gate: {evaluated: n, denied: [{channel, model, class}]}`；403 全拒时 `errors` 带 `pricing_gate` 类型（上限 200 条沿用现制）。
- `GET /api/health`/`/api/channels` 增补渠道级定价覆盖率（free/paid/unknown 计数），前端展示后人类一眼看出「哪些还在裸奔」。
- 响应头 `X-Routed-Channel` 家族增补 `X-Pricing-Class: free|paid|unknown|authorized_paid`。
- **错误体信息面（评审 ③-6 裁定：维持原设计）**：403 继续回显渠道名与 `class`——当前威胁模型（仅 127.0.0.1、调用方为本机持 key 的第三方 app）下诊断价值明显大于风险，渠道名与 class 不是凭证，暴露它们无助于拿 key 或绕鉴权，而对本机多客户端直呼模型名的排障非常关键。**记为技术债**：若将来监听范围变化（哪怕只是被反代到局域网其他机器可达），细粒度响应体须联动收紧，不等出问题再补。

### 4.5 与告警/审计联动（可选项 P3）
拦截事件计数超阈值（如 1h 内 >10 次同模型）→ 复用 watchdog 告警文件家族（`failclosed_alerts.log` 同款新增 `pricing_gate_alerts.log`），防「客户端配置错了在疯狂撞墙」。默认不做，评审定。

### 4.6 定价真源加载实现（评审 ③-7 结论：照抄自家先例，不发明新模式）
- 直接复用 `_cached_json`（`channels.py:264-281`）的 mtime 热载形态，与 rate_limit/健康缓存同层同风格。
- 重载路径：`os.stat` 取 mtime → 变化则**完整读出并解析出一个新字典对象** → 用**一次引用赋值**把缓存指针切过去。Python 下单次引用赋值在 GIL 下原子，并发读者只会读到完整的旧对象或完整的新对象，不会撕裂，因此**读路径不加锁**。
- 仅在「检查 mtime + 触发重载」一小段加轻量锁（双重检查锁定），或直接容忍偶发重复解析——本文件量级下代价可忽略。
- 单机个人网关 QPS 下每请求一次 `os.stat` 为微秒级，**不做**定时刷新线程等更复杂的方案（过度设计反增维护成本）。
- **写侧必须原子替换（M4）**：人工/脚本直接覆盖 `model_pricing.json` 时，多数编辑器走「截断旧文件 → 写入新内容」，存在一个**半截文件窗口**，恰好触发热载的读者就会解析失败。规定：写临时文件（同目录 `model_pricing.json.tmp.*`）→ 完整序列化 → **校验可读后 `os.replace()` 原子改名**。`os.replace` 在同一文件系统上是原子的，读者只会看到旧文件或新文件。
- **运行中热载失败不得沿用 last-known-good（M4，与 §4.3 启动期 3106 互补）**：v0.4 只定义了「启动时解析失败 → 3106」，没定义「enforce 正在跑、操作者把文件写坏了」怎么办。若此时保留 last-known-good 继续正常判定，最坏的后果恰好是本被改成 `paid` 的渠道仍按旧记录 `free` 放行——**放行错方向的代价不对称**，因此规定：运行期重载解析失败 → 闸门进入显式 `pricing-invalid` 异常态（`enforce` 下 deny、`observe` 下 allow 但打标），同时健康检查报错 + 告警留痕，直到读到下一份合法配置才恢复。此路径必须有测试（§6 P4）。
