# 累计问题与解决方案库（Running Issue → Solution Ledger）

> 目的：把每一轮实操中遇到的问题、根因、解法、证据**累积沉淀**，再带着这份清单与 GPT 对话，使问诊有据可依、结论更严谨、架构更连贯。
> 用法：新问题追加到对应类别；每条必须含【现象】【根因】【解法】【验证】【状态】五要素；**未解决**的条目是下次问诊的优先输入。
> 维护：当值 Agent 即时追加；每轮 GPT 问诊前先通读本文件，把「未解决」与「待 GPT 裁决」的条目带进提示词。

## 类别一：镜像站问诊链路（opencli / 问达宝 / GPT）

### Q1. 提示词对着"死标签"空转，脚本返回成功但消息根本没发出 ★严重
- **现象**：脚本返回 `sent`/`typed: true`，但页面 `userMsgs=0`、URL 未变为 `/c/<uuid>`，GPT 从未收到。
- **根因**：操作的标签早已不在浏览器会话中（报 `Target tab is not part of the current browser session`），脚本未做标签存活探测。
- **解法**：**发送前探活是硬门槛**（不是异常后的补救）。成功判据必须是 `userMsgs>=1` **且** URL 变为 `/c/<uuid>`，仅凭 `sent` 返回值不算。
- **验证**：阶段3 复核用此判据确认真实发出；后续两轮均复现成功。
- **状态**：✅ 已解决，已固化进 SOP 实测补充第 5 条。

### Q2. 固定 `sleep 150s` 会抓到流式中间态，导致存档丢内容 ★严重
- **现象**：150s 时探测 `len=1449`，该消息最终长度 3858 字符——若按固定等待立即提取，丢失约 2/3 正文。
- **根因**：Extended 模式流式输出耗时长，固定时长无法保证生成完毕。
- **解法**：自适应轮询 `scripts/gpt_wait_extract.mjs`，判据 = **连续两次 `len` 相同 且 `stop=false`**；首探 30s，发现内容后缩至 10s；连续 6 次全空才判故障。
- **验证**：实测 100s 完成 vs 固定 150s；某轮 70s 仅 1850 字、90s 完整 3065 字，判据精准抓全。
- **状态**：✅ 已解决并入库，SOP 第 5 步已重写。

### Q3. 不能用 `assistantCount` 比较判断是否生成新回复
- **现象**：`count > baseline` 永不成立，导致轮询无法判定完成。
- **根因**：baseline 在**发送后**采集，已包含新消息的空占位（count 已经 +1）。
- **解法**：放弃 count 比较，改用 `len` 稳定性判据。
- **状态**：✅ 已解决。

### Q4. Extended 模式前 60s `len=0` 被误判为空回复/实例故障
- **现象**：探测连续 `len=0`，一度以为实例故障。
- **根因**：Extended 思考期尚未开始输出，属正常。
- **解法**：连续 6 次（约 180s）探测全为 0 才判定疑似故障并上报，不自动换模型兜底。
- **状态**：✅ 已解决。

### Q5. 实例连续失效（about:blank），vip-12 四十分钟内两次失效
- **现象**：会话变 `about:blank`，`editor=false`。
- **根因**：vip-12 已不在 `panelAccountList` 健康 Plus 列表；**账号健康 ≠ 当前 tab 健康**，是两个维度。
- **解法**：①每次登录前读 `panelAccountList` 取健康 Plus 池；②**在池内轮转，不要把任一账号变成新的永久首选**（否则只是把单点从 vip-12 换成 vip-24）；③某实例连续失效即熔断换号，不反复救同一实例。
- **验证**：改 vip-24 后恢复正常并完成问诊。
- **状态**：✅ 已解决，策略已采纳。

### Q6. `gptreview` session 不在 `opencli profile list` 输出里
- **现象**：profile list 只显示 `n8hh7hyn`，误判 gptreview 不存在。
- **根因**：该命令不列出所有可直接寻址的会话。
- **解法**：直接寻址 `browser gptreview state` 即可，不要据 profile list 否定其存在。
- **状态**：✅ 已解决，已写进 SOP。

### Q7. 在线判据错误：看 `interactive` 计数
- **现象**：vip-12 落地后 `interactive: 0`，误以为页面不可用。
- **根因**：`interactive` 是 SPA 元素树刷新状态，不代表编辑器不可用。
- **解法**：在线判据改用 `editor:true`。
- **状态**：✅ 已解决。

## 类别二：网关 / 渠道 / 计费

### Q8. Agnes「文档写收费，但没充钱也能调用成功」
- **现象**：用户确认 Agnes 2.5 Pro 收费，但实际调用成功且未见扣费入口。
- **根因**：调用的是 **`agnes-2.5-flash`（免费档）**；上游 10 个模型中确有 3 个 pro 变体在架，但 `channel_models.json` 的选用清单（6 项）不含任何 pro，`model_overrides.json` hidden 的是 flash。
- **解法**：无需处理——fast 编排锁死 flash，无扣费路径。
- **证据缺口（如实保留）**：Agnes 上游 `/models` 只返回 id/owned_by/supported_endpoint_types，**不含价格字段**，故"flash 免费、pro 收费"无法由 API 自证，依据是厂商口径 + 用户确认。
- **状态**：✅ 已解答（devel-tools S-20260828-05 与 ai-resources S-20260828-01 双线独立核查、口径一致）。

### Q9. 小红书 dots3-note-prev 严重超时
- **现象**：3 次实测 120s 读超时、120s 读超时、89.7s 才返回；推理型模型在 max_tokens=16 小预算下 content 返回空。
- **根因**：上游劣化，非下架/改名/暂时不可达（渠道健康全 True，`/models` 三次 200）。
- **解法**：已从 fast 摘除（`disabled=[xiaohongshu]`），改由 zenmux 的 `dots-studio/dots3-note-prev` 承接（实测 5.4s/8.6s/5.0s，快 10–20 倍，且 0 价）。
- **状态**：✅ 已解决（另一 Agent 处置）。

### Q10. 全量工作树 secret 扫描报 13 处 finding，是否是泄漏？
- **现象**：扫描命中 `channels.json`/`api_state.json`/`credentials.json`。
- **根因**：三者均为 **UNTRACKED + gitignored** 的本地凭证存储，是网关/调度器的设计内行为。
- **解法**：判据只要求"未泄漏进日志/记忆/commit"，不要求网关不能持有本地凭证。正确扫描范围 = Git 已跟踪文件 + `git log -p` 范围 + STATE.md + 转发日志（`--tracked-only`）。
- **验证**：正确范围重扫 `finding_count=0 / exit 0`；`git ls-files` 与 `git log --all` 证实从未进入提交历史。
- **状态**：✅ 已解决，扫描器已入库 `scripts/secret_scan.py`。

### Q11. 凭证值出现在命令输出中
- **现象**：调试时 `keys.agnes` 的 API key 被打印到对话输出。
- **根因**：扫描输出未对凭证字段脱敏。
- **解法**：输出只报"是否存在/长度"，不报值；已暴露的 key 建议轮换。
- **状态**：⚠️ 需用户轮换该 key（未写入任何文件或记忆，但已出现在对话中）。

### Q12. 逆天项目脚本硬编码直连，能否统一走网关？
- **现象**：73 个脚本中 8 个硬编码多渠道直连。
- **根因**：历史沿革，各脚本自建"微型路由器"。
- **关键约束**：直连上游里 `token.sensenova.cn/v1/images/generations` 是**图像生成**、`apihub.agnes-ai.com` 是**视频生成**，**都不是 chat/completions，改走网关也承载不了**。
- **解法**：只有纯 chat 调用可收敛；先做"硬编码直连清单"，区分"纯 OpenAI Chat 兼容" vs "渠道专属"，再挑一个纯兼容脚本做 canary。风险四条：输出风格影响下游解析、retry 与网关 fallback 叠加放大、专属参数无法透传、免费边界被破坏。
- **状态**：⏳ 待执行（C 线 canary）。

### Q14. 多 Agent 同改记忆仓导致冲突与重复劳动
- **现象**：①两个 ai-resource-hub 副本分叉；②同日两条项目线（devel-tools / ai-resources）独立做了同一项 Agnes 核查；③push 时遇他人提交需 rebase。
- **根因**：缺乏全局唯一真源与任务占用声明。
- **解法**：①副本收敛需设 `AI_RESOURCE_HUB_HOME` 唯一变量（阶段4 Step 0 blocker）；②同日重复核查靠交叉引用条目（S-20260828-02）对齐口径，但治本需任务级占用声明；③冲突一律 `pull --ff-only` → rebase，**禁 force push**。
- **状态**：⚠️ 部分解决，治本方案待设计。

### Q15. inbox 手工放件无法被 resolve/settle
- **现象**：手工放入 `inbox/pending/` 根目录的交接件找不到。
- **根因**：`scripts/memory.py` 的 `inbox_item_path` 只遍历 pending 下的**日期子目录**。
- **解法**：须放入 `pending/YYYY-MM/`。
- **状态**：✅ 已记录（ai-resources S-20260828-02）。

### Q16. 四方同步（飞书/GitHub/本地/夸克）实际只有一环
- **现象**：核查发现只有"本地↔GitHub"通（且靠手动 push），飞书无同步机制，夸克 config 为空。
- **解法（已落地部分）**：`scripts/backup_memory.py` + 每日 21:00 自动备份（git 同步 + 含 .git 历史打包 + 30 天轮转），已实测通过。
- **卡点**：夸克官方 skill 只有语义搜索、无上传能力，qk-list 只能列根目录；需用户扫码登录才可能接入，且上传可行性未验证。
- **状态**：⚠️ 夸克环仍断，需用户决策。

### Q17. 问诊引用了未推送的本地文件，导致 GPT 核验失败并拒绝作答 ★流程失误
- **现象**：提示词要求 GPT 实读 `docs/累计问题与解决方案库_2026-08-28.md` 作为核验项，GPT 报告 raw 路径 404、仓库 docs 目录无此文件，遂按预设规则"读不到即判未实读、本轮作废"停止输出架构方案。
- **根因**：文件只在本地创建，**未 commit + push**，违反了「问诊同频」纪律（每轮问诊前必须先把结论/文档推送到 GitHub，让 GPT 与仓库同频）。
- **解法**：推送后验证 raw 可达（`curl -o /dev/null -w "%{http_code}"` 应为 200），再重发问诊。已推送至 `5ebe4ce`，raw 返回 200。
- **正面收获**：GPT 未被提示词里的摘要糊弄，坚持实读仓库文件才作答——这正是「实读令牌」机制设计的目的，说明该机制有效。
- **状态**：✅ 已解决（本轮第 3 轮重发）。
