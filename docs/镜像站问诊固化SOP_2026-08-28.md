## 实测补充（2026-08-28 阶段3 复核实跑验证；与下表冲突时以本节为准）

1. **`gptreview` 不在 `opencli profile list` 输出里，但确实存在** —— 该命令只列 `n8hh7hyn`（其他 Agent 的共享会话）。**不要据此判定 gptreview 不存在**，直接寻址即可（`browser gptreview state` 正常返回）。误判会退回 n8hh7hyn 与他人争用。
2. **在线判据看 `editor:true`，不看 `interactive` 计数** —— 实测 vip-12 落地后 state 显示 `interactive: 0`，但编辑器已就绪（`editor:true` / `textarea:true`），可直接注入。`interactive:0` 只是 SPA 元素树未刷新。
3. **vip-12 在 gptreview 下 `histLinks=0`**（`a[href*="/c/"]` 计数为 0，等 6 秒复查仍为 0）—— 直接按操作手册 §9.1 例外条款**新开对话**，不要等待或反复重登。
4. **新对话的 `/c/<uuid>` 在发送成功后才出现**，发送前一直是根路径，属正常，不要据此判定未进入会话。
5. **发送成功的硬判据是 `userMsgs>=1` 且 URL 变为 `/c/<uuid>`** —— 仅凭 `sent` 返回值不足以证明消息真的发出（历史误报正源于此：脚本返回 sent 但页面 `userMsgs=0`）。
6. **根路径 ≠ 空闲标签（2026-08-29 事故预演，务必执行第 0 步）** —— 本轮按旧 SOP 只做 `state`，看到 `URL=https://vip-NN.67673.live/`（根路径）即判定空闲并注入 15156 字符，实际该会话**唯一一个活动标签正被另一个 Agent 用于问诊「设计内容过滤故障转移」**，其消息随后以它自己的 2635 字符发出（未受损，纯属对方重打/未被我首块清空命中）。结论：**根路径恰恰可能是对方「已输入未发送」的状态**，`state` 无法区分归属，必须先 `tab list` 看 `title`、再 `tab new` 占自己的标签并全程 `--tab`。配套已落地：`.tools/mirror_eval.mjs`、`.tools/mirror_inject_send.mjs`、`scripts/gpt_wait_extract.mjs` 均已支持 `--tab <targetId>`。
7. **本机无法验证 raw 链接可达性** —— `curl` 与 WebFetch 访问 `raw.githubusercontent.com` 均失败（http=000 / fetch failed），但镜像站**服务端**抓取历史上是通的。为避免把整轮押在对方能否抓取上：**问诊包正文必须整份内嵌进提示词**，raw 链接只作为存档出处附上（明确写「无需访问外网」）。注入 15K 字符实测无损、不触发截断，截断风险在回复侧不在发送侧。
8. **低字符数的「稳定」不是退化，是思考片段（2026-08-29 真实误判）** —— 同一轮里我按旧判据抓到 4 字符稳定，加上随后几次探测 `assistantLens=0`，就把对方定性为「实例退化、回复中途清空」并写了退化存档。**实际对方约 2 分钟后正常输出了 10016 字符完整裁定，首末令牌齐全。** 根因是判据缺陷（详见 §5 三重判据），不是实例故障。**误判代价极高**：白白上报用户、烧掉一轮重投、且差点让一份有效裁定永久丢失。任何「实例故障」结论必须先排除：① 等待次数是否已达新上限；② 探针是否在流式清空与写入之间采样；③ 提取脚本本身是否有缺陷（用 §5 用法里的 `--min/--token` 复跑一次即可自证）。
9. **存档/记录里的会话 URL 必须完整，禁止 `slice` 截断** —— 本轮 `checksent.js` 用 `location.href.slice(0,60)` 记录会话地址，`/c/<36 位 uuid>` 被砍掉尾巴，按截断后的 URL 重开直接跳回根路径，于是误判「对话已被删除」。配套教训：**判定对话存续要用完整 `/c/<uuid>` 或 `tab list` 的 title**，不能用截断 URL；`fetch_conv` 类脚本需带完整会话 id。

## 第 5 步详解：为什么必须用自适应轮询（2026-08-28 实测，含事故复盘）

**固定 `sleep 150s` 有两个已实测确认的缺陷，禁止再用：**

1. **会抓到流式中间态，导致存档丢内容（高危）**。阶段3 第 1 轮复核实测：150s 时探测 `len=1449`，而该消息最终长度为 **3858 字符** —— 若按固定等待立即提取，将丢失约 **2/3 的正文**（含后半段判据与总结论）。该轮存档之所以完整，纯属探测脚本与提取脚本之间有时间差侥幸命中，**不是流程保证**。
2. **慢**。用户实测反馈 GPT 有时 30 秒内即答完，固定等 150s 属无效等待。

**自适应轮询的判据（2026-08-29 修订，已固化进 `scripts/gpt_wait_extract.mjs`）：**

- **完成判据 = 三重同时成立**：① 正文长度 ≥ `--min`（默认 120）；② 连续两次探测 `len` 相同且 `stop=false`；③ 若提示词要求首末输出令牌，`--token <串>` 须已在正文尾部窗口（末 200 字）出现。**缺一律继续等。**
- **为什么不能只看「len 稳定」（本轮事故）**：Extended 思考期会出现「正文先稳定停在极少字符」的状态。2026-08-29 一次 18K 字符问诊，助手节点先稳定在 **4 字符（`P2-`）** 超过 10 秒，旧判据当场判 `STABLE & DONE` 并只存下这 4 字符，被误读为「实例退化、回复中途清空」——实际约 2 分钟后回复正常写完（10016 字符，首末令牌齐全）。**是判据缺陷，不是实例故障。误判会导致无谓上报与重复烧轮次。**
- `0 < len < min` 累计 12 次 → 退出码 `4`（到这一步才真是疑似退化），并打印尾部串供人工判断；正文恒为 0 连续 6 次 → 同样 `4`。
- 正文达标且连续稳定、但令牌始终不出现（模型漏写末行）→ 稳定 3 次后兜底存档并返回退出码 `5`：**已存档但可能不完整，不得当完整裁定使用。**
- 不依赖 `assistantCount` 比较——实测发现 baseline 若在发送后采集，会包含新消息的空占位，导致 `count > baseline` 永不成立。
- **自适应间隔**：首次等待 30s；一旦探测到 `len>0`，间隔缩短为 10s 以加速收敛。
- **上限**：默认探测次数由 14 提到 **36**（Extended 配长提示词常需 3–6 分钟，14 次会在答完前就误报超时）。

**实测数据**（2026-08-28，vip-12 连通性测试）：

```
[30s]  stop=false count=4 len=0     ← 思考中，不是空回复
[60s]  stop=false count=4 len=0     ← 思考中
[90s]  stop=false count=4 len=6     ← 内容出现
[100s] stop=false count=4 len=6     ← 连续两次一致 → STABLE & DONE
```

总耗时 **100s**，较固定 150s 节省约 50s，且内容完整性由判据保证。

**用法**

```bash
node scripts/gpt_wait_extract.mjs --session gptreview --tab <id> --out <存档路径.txt> \
  --token <提示词要求的尾行令牌>
# 可选：--first 30（首次间隔）--fast 10（发现内容后间隔）
#       --max 36（探测上限，默认已 36）--min 120（正文长度下限，低于此值一律不算答完）
```

退出码：`0`=成功已存档且尾令牌齐全；`1`=超时；`2`=探针失败；`3`=提取失败；`4`=疑似退化/空回复（累计 12 次低字符或连续 6 次 0 字，才上报用户，不自动兜底）；`5`=**已存档但缺尾令牌**——内容可能不完整，**不得当作完整裁定使用**。

## 否定性判据补证标准（GPT 阶段3 复核裁定确立，2026-08-28）

**规则**：凡「未泄漏 / 未修改 / 零访问」这类**否定性判据**，必须配机器可验证的 scan / diff / count，**不能只写执行者结论**。单凭"我确认没有"一律判证据不足。

**工具**：记忆仓 `scripts/secret_scan.py`（已入库）

```bash
# 判定「是否泄漏进 commit/记忆/日志」——用 tracked-only，这是正确范围
python scripts/secret_scan.py --tracked-only \
  --repo "D:/项目" \
  --state "D:/ai-hub-memory/projects/devel-tools/STATE.md" \
  --ccswitch-log ~/.cc-switch/logs/cc-switch.log \
  --range 8ec04de1..HEAD --out <报告路径.json>
```

- 覆盖：Git 已跟踪文件 + `git log -p <range>` 全部提交 diff + STATE.md + CC Switch 日志
- 7 类规则：openai_key / anthropic_key / jwt / aws_akid / bearer / private_key / env_assign
- 强制 redaction：**只输出 finding_count 与 exit_code，绝不保存命中的秘密正文**
- 达标线：`finding_count=0` 且 `exit_code=0`

**关键排雷**：全量工作树扫描会命中设计内的本地凭证存储（`data/search_gateway/channels.json`、`api_state.json`、`ai-resource-hub/scheduler/credentials.json` 等）。这些文件是 **untracked + gitignored**，属网关/调度器运行必需的本地凭证信任域，**不构成泄漏**。判定前必须用两条命令验证其性质：

```bash
git ls-files --error-unmatch <path>   # 应报未跟踪
git log --all --oneline -- <path>     # 应为空，证明从未进入历史
```

**GPT 的边界口径**：判据要证明的是"没有泄漏进日志 / 记忆 / commit"，**不是**要求运行中的网关完全不能持有本地凭证。阶段4 起继续维持：credential_ref 可进配置/控制平面，真实 secret 只留本地凭证信任域。
