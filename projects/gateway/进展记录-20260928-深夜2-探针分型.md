## 3 三条限制写明白，别把弱探针当能力探针

1. `realtime_reach` 只验「模型在册 + key 有效」，**不做 WS 全双工音频往返**。
   realtime 的真实使用形态仍未被实测——今天 3 席全 200 只说明没被改名/下线/key 没废。
2. `jev_reach` 是可达性探针，**不证明出得出决策结果**。
3. `video_submit` **真占 agnes 免费额度并排一个视频任务**，所以 `CADENCE_DAYS=3` 天才提交一次；
   失败过就天天追（坏了要尽早知道，不能拿节律当借口）。

## 4 队列满不等于"模型下架"

首轮 agnes 连返两次 `503 video_queue_full`。判定表里 429/5xx 一律**保留席位**，
所以给这类失败单独打 `soft` 标：连续 3 天才报警，文案是「容量受限，席位保留不摘」，
不是「请检查是否下架、是否移出编排待拍板」。

这条线当下的事实：video-gen 是**单席线**且上游队列满 → 此刻不可用，没有备席可退。
这正是此前零覆盖时看不到的东西。

## 5 顺手抓到自己两个「宣告≠事实」

1. **放行名单写了两份 → 分型补了但根本没跑到。** 探针脚本自己列了 `LOCAL_KINDS`
   （edge-tts/typesafe 不是 HTTP 渠道），而统一闸门 `test_gate` 在 dispatch 之前先判
   `unknown_channel` 把它们挡下。第一版跑完 edge-tts/typesafe 的 state 和 perf 都是空的。
   改法：名单只留 `test_gate.LOCAL_PROBE_CHANNELS` 一份，放开位置排在
   禁测渠道/封存/纯付费链**之后**（红线优先），且只放开 `caller="member_probe"`。
2. **覆盖账面自我虚报。** 第一版按「分型 != skip」统计，把被闸门挡下的 2 席也算成已覆盖，
   于是打印「48 席已覆盖」的假绿灯。改法：覆盖数与 dispatch 共用同一个 `dispatchable()` 判据，
   且「不覆盖的每一席」逐条点名进 `daily_summary.probe_coverage`——"没警报"不等于"没事"。
